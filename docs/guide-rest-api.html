Django REST Framework 接口实战指南

面向 Django 5.2 + DRF 3.15。所有关于框架行为的论断均在本机实测验证，所有项目分析均来自本仓库 Chapter15~17/educa/courses/api/ 的真实代码。

Django 5.2 · DRF 3.15.1 含 6 张架构示意图 6 个已复现的缺陷

本文结论速览

三条最重要的结论

  1. 本仓库 API 最贵的那个端点有严重的 N+1。 实测 /api/courses/1/contents/ 对一门 5 模块 30 内容项的课程发出 39 条 SQL，其中 30 条是逐个解 GenericForeignKey。用 Django 5.0+ 的 GenericPrefetch 重写后是 5 条。详见 F-01。
  2. SubjectViewSet 的分页目前是不稳定的。 annotate() 引入 GROUP BY，Django 会静默丢弃 Meta.ordering，生成的 SQL 里没有 ORDER BY——DRF 每次请求都在打印 UnorderedObjectListWarning，而无序查询的分页可能跨页重复或漏掉记录。详见 F-02。
  3. 两个自定义端点意外关掉了 session 认证。 @action 上写 authentication_classes=[BasicAuthentication] 是替换而非追加，于是同一个浏览器 session 能读 /api/courses/（200）却在 /api/courses/1/contents/ 上收到 401。详见 F-03。

本文的结构与缓存指南一致：先讲 Django 5.2 + DRF 3.15 的配置与选型，再逐处分析本仓库的 API 代码，然后是六个已验证的缺陷及修复、性能与认证鉴权专题，最后是上线清单与 Spring / Hono.js 对比。所有关于框架行为的论断都在本机 Django 5.2 + DRF 3.15.1 上跑通验证，实测输出以绿色标题的终端块标注。

一点前提说明：本仓库的 API 代码位于 Chapter15~17/educa/courses/api/，我逐字节比对过——三章完全一致，说明它在 Chapter15 引入后就没再改动。所以下文说「本项目」时，指的是这份从 Ch15 到 Ch17 都相同的代码。

一、DRF 在 Django 5.2 下的配置与接线

DRF 不在 Django 标准库里，需要单独安装并注册。本仓库 requirements.txt 锁的是 djangorestframework==3.15.1，配 Django 5.2 是当前的稳定组合。

1.1 本项目的实际配置：只有一行

python
# educa/settings/base.py

    ...
    'rest_framework',
    ...
]

REST_FRAMEWORK = {
    'DEFAULT_PERMISSION_CLASSES': [
        'rest_framework.permissions.DjangoModelPermissionsOrAnonReadOnly'

}

除了这一项，其余全部走 DRF 默认值。这些默认值是什么，实测打印如下：

实测 · 本项目生效的 DRF 配置
DEFAULT_AUTHENTICATION_CLASSES   ['SessionAuthentication', 'BasicAuthentication']
DEFAULT_RENDERER_CLASSES         ['JSONRenderer', 'BrowsableAPIRenderer']
DEFAULT_THROTTLE_CLASSES         []  <- 空
DEFAULT_PAGINATION_CLASS         None  <- 未启用
DEFAULT_VERSIONING_CLASS         None  <- 未启用

其中 DEFAULT_PAGINATION_CLASS 为 None 值得注意：本项目的分页是逐视图配的（两个 ViewSet 各写了一次 pagination_class = StandardPagination），所以任何新加的视图如果忘了配，就会一次性返回全表。这正是应该用全局默认值兜底的场景。

1.3 可浏览 API 在生产是开着的

DRF 默认的 DEFAULT_RENDERER_CLASSES 包含 BrowsableAPIRenderer，它不看 DEBUG——只要请求头带 Accept: text/html（浏览器直接访问就是这样），就会返回一整套 HTML 调试界面：

实测 · DEBUG=False 下请求 API
Accept: text/html -> 200 text/html; charset=utf-8
返回的是 HTML 页面 : True

这不算漏洞，但它会把完整的字段结构、可用方法、分页参数暴露给任何访问者，而且每次渲染都要跑一遍模板，比返回 JSON 慢得多。生产环境应当按 1.2 那样只保留 JSONRenderer，或者用 DEBUG 做条件切换。

1.4 URL 接线

python
# courses/api/urls.py
from rest_framework import routers

app_name = 'courses'

register() 没传 basename，DRF 会从 ViewSet 的 queryset 属性反推（这里得到 course / subject）。如果哪个 ViewSet 只重写了 get_queryset() 而没有类级 queryset，这里就会直接抛错，必须显式传 basename——这是 Router 最常见的报错来源。

二、请求流水线与视图选型

2.1 一个请求在 DRF 里经过什么

理解这条流水线能解释很多「为什么」。比如：权限检查在视图代码之前，所以「无权限」返回 403 而不是让你查出空结果；而对象级权限必须等 get_object() 拿到对象，所以它是在视图体内部触发的，这就是为什么 IsEnrolled 只能写 has_object_permission。

401 与 403 的区别也由这条流水线决定：DRF 在权限不足时，如果当前请求没有通过任何认证就返回 401（告诉你「你需要先登录」），已认证但权限不够才返回 403。本项目实测正好覆盖了这三种状态，见 第六节。

2.2 视图的四层抽象

本仓库 courses/api/urls.py 里还留着一段注释掉的旧代码，正好记录了这个演进过程：

python
urlpatterns = [
    # path('subjects/', views.SubjectListView.as_view(), name='subject_list'),
    # path('subjects/<pk>/', views.SubjectDetailView.as_view(), name='subject_detail'),
    # path('courses/<pk>/enroll/', views.CourseEnrollView.as_view(), name='course_enroll'),
    path('', include(router.urls)),
]

三个独立的 generics 视图 + 手写 URL，被一个 ReadOnlyModelViewSet + Router 取代。代码是少了，但也要清楚代价：URL 不再出现在代码里，想知道有哪些端点得去看 Router 的生成规则或跑 show_urls。

写法一个类对应适合不适合
APIView一个 URL，方法自己写不是 CRUD 的端点：登录、导出、Webhook 回调标准 CRUD——会写一堆重复代码
generics.*一个 URL 的一组方法端点之间差异较大、需要各自定制的场景——是最平衡的选择，很多团队全程只用这层
ViewSet一组 URL资源型 CRUD，配 Router 使用端点之间要用不同认证/权限/序列化器时，覆盖会变得零碎
ModelViewSet一组 URL 的全部 CRUD后台管理类接口、内部工具对外 API——它默认把增删改全开了，很容易超出你本意暴露的范围

本项目用的是 ReadOnlyModelViewSet（只生成 list 与 retrieve），这是个好选择——需要写操作时再用 @action 精确加一个 enroll 端点，而不是直接上 ModelViewSet 把 POST/PUT/PATCH/DELETE 全开。实测 DELETE /api/courses/2/ 返回 403，正是因为这些方法压根没被注册。

三、本仓库 API 代码逐处分析

3.1 序列化器：五个类，三种典型手法

手法一：用 SerializerMethodField 塞入计算字段。

python
class SubjectSerializer(serializers.ModelSerializer):
    total_courses = serializers.IntegerField()
    popular_courses = serializers.SerializerMethodField()

    def get_popular_courses(self, obj):
        courses = obj.courses.annotate(
            total_students=Count('students')
        ).order_by('-total_students')[:3]
        return [f'{c.title} ({c.total_students} students)' for c in courses]

    class Meta:
        model = Subject
        fields = ['id', 'title', 'slug', 'total_courses', 'popular_courses']

这一个类里藏了三个值得注意的点：

  • total_courses = serializers.IntegerField() 声明了一个模型上并不存在的字段，它依赖 ViewSet 的 queryset 事先 annotate() 出来。这是一个隐式契约——序列化器和 queryset 被绑死了，但代码里没有任何地方写明这件事。
  • get_popular_courses() 每次被调用都会执行一次数据库查询，而它对列表里每个对象都会调用一次——这就是 N+1（见 F-01）。
  • 返回的是拼好的字符串 "Course A (12 students)"，而不是 {"title": ..., "students": ...}。客户端想单独拿学生数就得正则解析字符串。这是把展示层逻辑塞进了 API 契约。
实测 · 隐式契约的脆弱性
A) 用 ViewSet 里那个带 annotate 的 queryset：
    {'id': 1, 'title': 'Subject 0', ..., 'total_courses': 1, 'popular_courses': [...]}

B) 换成普通 queryset（比如在别处复用这个序列化器）：
    AttributeError: Got AttributeError when attempting to get a value for
    field `total_courses` on serializer `SubjectSerializer`.
    Original exception text was: 'Subject' object has no attribute 'total_courses'.

更稳妥的写法是让序列化器自己声明这个依赖，而不是默默假设：total_courses = serializers.IntegerField(read_only=True, default=0)，或者干脆用 SerializerMethodField 配合 obj.courses.count()（虽然那样会引入另一个 N+1）。真正干净的做法是把 annotate 收进序列化器的 setup_eager_loading() 类方法，让两者绑在一起。

手法二：嵌套序列化器表达层级。

python
class CourseSerializer(serializers.ModelSerializer):
    modules = ModuleSerializer(many=True, read_only=True)      # 一层嵌套

class ModuleWithContentsSerializer(serializers.ModelSerializer):
    contents = ContentSerializer(many=True)                     # 两层

class CourseWithContentsSerializer(serializers.ModelSerializer):
    modules = ModuleWithContentsSerializer(many=True)           # 三层：课程→模块→内容→item

用两套序列化器区分「列表视图的轻量表示」和「详情视图的完整表示」，这个思路是对的——列表页不该把每门课的全部内容都吐出来。问题在于第二套嵌套了三层，而 queryset 只 prefetch_related('modules') 一层，剩下两层全是 N+1。

手法三：自定义 RelatedField 处理多态关联。

python
class ItemRelatedField(serializers.RelatedField):
    def to_representation(self, value):
        return value.render()          # 返回渲染好的 HTML 字符串


class ContentSerializer(serializers.ModelSerializer):
    item = ItemRelatedField(read_only=True)

    class Meta:
        model = Content
        fields = ['order', 'item']

Content.item 是个 GenericForeignKey，可能指向 Text、Video、Image、File 四种模型中的任意一种。用自定义 RelatedField 统一处理多态是标准做法，但这里 to_representation 返回的是 value.render()——也就是把模板渲染出来的 HTML 塞进 JSON：

实测 · 响应体里 item 字段的实际内容
type: str
值  : '<div class="text">T0</div>\n'

这是一个需要清醒对待的设计取舍。 好处是客户端拿到就能直接插进 DOM，教材里做演示很方便。代价有三条：其一，API 的消费方被限定为「能渲染 HTML 的客户端」——iOS/Android 原生应用、另一个后端服务拿到这段 HTML 基本无法使用；其二，服务端模板变更会直接改变 API 响应，API 契约和前端模板耦合在一起；其三，render() 里如果模板没有正确转义用户输入，就等于把 XSS 载荷通过 JSON 分发出去。

面向真实客户端的 API 应该返回结构化数据（{"type": "text", "content": "..."}），把「怎么渲染」留给客户端决定。

3.2 视图：两个 ViewSet 与两个自定义端点

python
class CourseViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Course.objects.prefetch_related('modules')
    serializer_class = CourseSerializer
    pagination_class = StandardPagination

    @action(detail=True, methods=['post'],
            authentication_classes=[BasicAuthentication],
            permission_classes=[IsAuthenticated])
    def enroll(self, request, *args, **kwargs):
        course = self.get_object()
        course.students.add(request.user)
        return Response({'enrolled': True})

    @action(detail=True, methods=['get'],
            serializer_class=CourseWithContentsSerializer,
            authentication_classes=[BasicAuthentication],
            permission_classes=[IsAuthenticated, IsEnrolled])
    def contents(self, request, *args, **kwargs):
        return self.retrieve(request, *args, **kwargs)

@action(detail=True) 会生成 /api/courses/{id}/enroll/ 这样的 URL。contents 直接复用 self.retrieve()，只是换了个序列化器——这是很漂亮的复用。

但这两个装饰器参数里埋着 F-03 和 F-04：authentication_classes 是替换不是追加；而 enroll 除了「已登录」之外没有任何业务校验。

3.3 分页与权限：两个小而正确的类

python
class StandardPagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = 'page_size'      # 允许客户端调整
    max_page_size = 50                       # 但设上限，防止 ?page_size=999999


class IsEnrolled(BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.students.filter(id=request.user.id).exists()

这两个类都写得不错。max_page_size 是很多人会忘的一项——不设上限，客户端就能用 ?page_size=1000000 把分页彻底绕过去。IsEnrolled 用 .filter(...).exists() 而不是 request.user in obj.students.all()，避免把整个学员列表拉进内存，也是对的。

实测 · IsEnrolled 的三种状态都正确
匿名                              -> 401
已登录但未报名 (outsider)          -> 403
已报名 (student)                  -> 200

四、六个已验证的缺陷与修复

以下六条全部在本机 Django 5.2 + DRF 3.15.1 上用仓库的真实代码结构复现，测试数据规模为 10 学科 / 30 课程 / 150 模块 / 900 内容项。

F-01嵌套序列化器与 GenericForeignKey 造成 N+1已复现 · 性能
位置
courses/api/serializers.py + courses/api/views.py
触发
任何一次 /api/subjects/ 或 /api/courses/{id}/contents/ 请求
影响
查询数随数据量线性增长；单次请求 39 条 SQL，其中 30 条可以合并成 2 条
实测 · 查询数随分页大小线性增长
/api/subjects/?page_size=2   -> 4 条查询   (1 count + 1 list + 2 popular_courses)
/api/subjects/?page_size=5   -> 7 条查询   (1 count + 1 list + 5 popular_courses)
/api/subjects/?page_size=10  -> 12 条查询  (1 count + 1 list + 10 popular_courses)

单门课含 5 个模块 / 30 个内容项
/api/courses/1/contents/  -> 39 条查询
  其中 30 条是逐个解 GenericForeignKey 的 item 查询

同样取全部内容，加上 GenericPrefetch 之后 -> 5 条查询

根因有两处。其一，SerializerMethodField 里的查询对列表每个元素都会执行一次，DRF 不会、也无法帮你合并。其二，GenericForeignKey 无法被普通的 prefetch_related 覆盖——因为要先读出 content_type 才知道该去查哪张表。

修复。 Django 5.0 起内置了 GenericPrefetch，正是为这个场景设计的：

✗ 现状：只预取一层
class CourseViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Course.objects.prefetch_related('modules')
✓ 按 action 提供各自的 queryset
from django.contrib.contenttypes.prefetch import GenericPrefetch
from django.db.models import Prefetch

class CourseViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Course.objects.prefetch_related('modules')

    def get_queryset(self):
        qs = super().get_queryset()
        if self.action == 'contents':
            qs = Course.objects.prefetch_related(
                Prefetch('modules', queryset=Module.objects.prefetch_related(
                    Prefetch('contents', queryset=Content.objects.prefetch_related(
                        GenericPrefetch('item', [
                            Text.objects.all(), Video.objects.all(),
                            Image.objects.all(), File.objects.all(),
                        ])
                    ))
                ))
            )
        return qs

popular_courses 那处则要换思路——SerializerMethodField 里做查询几乎必然 N+1。可行的做法是在 queryset 上一次性把需要的数据取出来，序列化器只负责读：

python
# 用一次 Prefetch 把每个 subject 的热门课程取出来，再在序列化器里读缓存
class SubjectViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = (
        Subject.objects
        .annotate(total_courses=Count('courses'))
        .prefetch_related(
            Prefetch(
                'courses',
                queryset=Course.objects.annotate(
                    total_students=Count('students')
                ).order_by('-total_students'),
                to_attr='ranked_courses',      # 预取结果挂到这个属性上
            )
        )
        .order_by('title')                     # 顺带修掉 F-02
    )


class SubjectSerializer(serializers.ModelSerializer):
    def get_popular_courses(self, obj):
        # 不再查库，直接读预取好的列表
        return [
            f'{c.title} ({c.total_students} students)'
            for c in obj.ranked_courses[:3]
        ]

怎么在开发期就发现 N+1？ 本仓库已经装了 django-debug-toolbar，但它只对 HTML 页面生效，看不到 API 的 JSON 响应。给 API 加一层保护的实用做法是写测试断言查询数：with self.assertNumQueries(5): self.client.get('/api/courses/1/contents/')——这样以后谁改序列化器引入了 N+1，CI 会直接失败。

F-02annotate() 静默丢弃 Meta.ordering，分页失去稳定顺序已复现 · 正确性
位置
courses/api/views.py · SubjectViewSet.queryset
触发
任何一次分页的 /api/subjects/ 请求
影响
跨页记录可能重复或被跳过；DRF 每次请求都打印 UnorderedObjectListWarning

根因。 Subject 明明有 Meta.ordering = ['title']，但 annotate(Count(...)) 会引入 GROUP BY，而 Django 对此有一条明确规则——直接看 QuerySet.ordered 的源码，注释是 Django 自己写的：

python
# django/db/models/query.py（5.2 源码）
@property
def ordered(self):
    if isinstance(self, EmptyQuerySet):
        return True
    if self.query.extra_order_by or self.query.order_by:
        return True
    elif (
        self.query.default_ordering
        and self.query.get_meta().ordering
        and
        # A default ordering doesn't affect GROUP BY queries.
        not self.query.group_by          # ← 有 GROUP BY 就不认 Meta.ordering
    ):
        return True
    else:
        return False
实测 · Meta.ordering 被静默丢弃
Subject.Meta.ordering        = ['title']

Subject.objects.all()                     .ordered = True
Subject.objects.annotate(Count('courses')).ordered = False   <-- 仓库现状
...再 .order_by('title')                   .ordered = True

annotate 后的 SQL 结尾：
   ...GROUP BY "courses_subject"."id", "courses_subject"."title", "courses_subject"."slug"
   含 ORDER BY : False

加了 .order_by('title') 之后：
   ...GROUP BY ... ORDER BY "courses_subject"."title" ASC
   含 ORDER BY : True

没有 ORDER BY 的查询，数据库不保证两次 LIMIT/OFFSET 返回相同顺序。PostgreSQL 在并发写入、计划变更或并行扫描时确实会改变返回顺序，结果就是用户翻到第 2 页时看到第 1 页出现过的记录，而另一些记录一次都没出现。

✗ 现状
queryset = Subject.objects.annotate(
    total_courses=Count('courses'))
✓ 显式排序
queryset = Subject.objects.annotate(
    total_courses=Count('courses')
).order_by('title')

顺带一条通用建议：凡是要分页的 queryset，都应该有一个确定且唯一的排序键。按 title 排序在标题重复时仍可能不稳定，更稳妥的是 .order_by('title', 'id')——加上主键做最终决胜，保证顺序完全确定。

F-03@action 覆盖 authentication_classes 意外关掉了 session 认证已复现 · 一致性

session 登录后 GET contents/      -> 401   <- 同一个浏览器、同一个登录态
✗ 现状：替换掉了全局认证方式

        serializer_class=CourseWithContentsSerializer,

✓ 认证交给全局配置，这里只管权限

        permission_classes=[IsAuthenticated, IsEnrolled])
def contents(self, request, *args, **kwargs):
    return self.retrieve(request, *args, **kwargs)

认证方式应该是全站统一的策略，配在 DEFAULT_AUTHENTICATION_CLASSES；权限才是逐端点的决策。把两者混在同一个装饰器里，就很容易在调整其一时误伤另一个。

# 补一个退课端点，并让报名走业务校验
@action(detail=True, methods=['post'], permission_classes=[IsAuthenticated])
def enroll(self, request, *args, **kwargs):
    course = self.get_object()
    if not course.is_open_for_enrollment:
        return Response({'detail': '该课程当前不开放报名'},
                        status=status.HTTP_409_CONFLICT)
    if course.requires_payment and not course.has_paid(request.user):
        return Response({'detail': '请先完成支付'},
                        status=status.HTTP_402_PAYMENT_REQUIRED)
    course.students.add(request.user)
    return Response({'enrolled': True})


@action(detail=True, methods=['post'], permission_classes=[IsAuthenticated])
def unenroll(self, request, *args, **kwargs):
    self.get_object().students.remove(request.user)
    return Response({'enrolled': False})

class ItemRelatedField(serializers.RelatedField):
    def to_representation(self, value):
        base = {
            'type': value._meta.model_name,     # 'text' / 'video' / 'image' / 'file'
            'id': value.id,
            'title': value.title,
        }
        if isinstance(value, Text):
            base['content'] = value.content
        elif isinstance(value, Video):
            base['url'] = value.url
        elif isinstance(value, (Image, File)):
            base['file'] = value.file.url if value.file else None
        return base

5.1 本项目的认证现状

全局是 DRF 默认的 [SessionAuthentication, BasicAuthentication]，两个 @action 覆盖成只有 BasicAuthentication。Basic 认证意味着客户端每一次请求都要把用户名和密码原样发过来（仅做 base64 编码，不是加密）。这在 Ch17 的生产配置里勉强可接受，因为 prod.py 设了 SECURE_SSL_REDIRECT = True 强制 HTTPS，传输层是加密的。但它仍有两个固有问题：客户端必须长期持有明文密码，且服务端无法在不改密码的情况下吊销单个客户端的访问权。

python
# 生产 API 的推荐起点：JWT
# pip install djangorestframework-simplejwt
REST_FRAMEWORK = {
    'DEFAULT_AUTHENTICATION_CLASSES': [
        'rest_framework_simplejwt.authentication.JWTAuthentication',
    ],
}

from rest_framework_simplejwt.views import TokenObtainPairView, TokenRefreshView
urlpatterns += [
    path('api/token/', TokenObtainPairView.as_view()),
    path('api/token/refresh/', TokenRefreshView.as_view()),
]

SIMPLE_JWT = {
    'ACCESS_TOKEN_LIFETIME': timedelta(minutes=15),
    'REFRESH_TOKEN_LIFETIME': timedelta(days=7),
    'ROTATE_REFRESH_TOKENS': True,
    'BLACKLIST_AFTER_ROTATION': True,     # 支持吊销，需装 token_blacklist app
}

JWT 不是银弹。它的核心特性是「无状态」——服务端不查库就能验证，代价是签发后无法直接吊销。用户改密码、账号被封禁，已签发的 access token 在过期前依然有效。所以 access token 的有效期要短（15 分钟量级），并配合 refresh token 轮换 + 黑名单。如果你的业务要求「封禁立即生效」，那么带状态的 Token 认证反而更合适。

5.2 权限的两个层级

python
class BasePermission:
    def has_permission(self, request, view):
        # 类级：视图执行之前就检查，拿不到具体对象
        return True

    def has_object_permission(self, request, view, obj):
        # 对象级：get_object() 取到对象之后才检查
        return True

对象级权限有一个必须知道的限制：它只在 get_object() 被调用时触发。也就是说 list 这类返回集合的动作完全不会调用 has_object_permission——DRF 不会替你逐条过滤列表。列表的可见性必须靠 get_queryset() 过滤来实现。这是 DRF 权限系统最常被误解的一点：写了 has_object_permission 不等于列表也安全了。

python
# 列表可见性靠 queryset 过滤，不靠权限类
def get_queryset(self):
    qs = super().get_queryset()
    if self.action == 'list' and self.request.user.is_authenticated:
        return qs.filter(students=self.request.user)
    return qs

5.3 限流

本项目完全没有限流。DRF 内置的三种节流类覆盖大部分需求：

类按什么计数典型用途
AnonRateThrottle匿名请求的 IP防止未登录用户批量抓取公开数据
UserRateThrottle已认证用户的 id给每个账号一个总体配额
ScopedRateThrottle视图上声明的 throttle_scope给昂贵端点单独设更严的限额
python
# 给最贵的那个端点单独限流
class CourseViewSet(viewsets.ReadOnlyModelViewSet):
    @action(detail=True, methods=['get'],
            throttle_classes=[ScopedRateThrottle],
            permission_classes=[IsAuthenticated, IsEnrolled])
    def contents(self, request, *args, **kwargs):
        return self.retrieve(request, *args, **kwargs)
    contents.throttle_scope = 'course_contents'

# settings
REST_FRAMEWORK['DEFAULT_THROTTLE_RATES'] = {
    'anon': '60/hour',
    'user': '1000/hour',
    'course_contents': '30/min',
}

DRF 的限流实现是基于缓存的（默认用 default 缓存），所以它天然需要一个共享缓存后端才能在多进程/多机部署下正确工作——本仓库已经配了 Redis 缓存，正好可以直接用。这也是缓存指南里提到的「Redis 承载多类负载」的又一例。注意限流计数器丢失只会导致配额被重置，属于可容忍的缓存语义。

六、上线前检查清单

  • 01配 DEFAULT_PAGINATION_CLASS 和 PAGE_SIZE。逐视图配置意味着新加的视图忘了就会返回全表。
  • 02分页的 queryset 必须有确定排序，且最好带上主键做决胜：.order_by('title', 'id')。见 F-02。
  • 03给 page_size_query_param 设 max_page_size。本项目做对了这一点。
  • 04用 assertNumQueries 给关键端点上查询数断言。这是防止 N+1 回归最有效的手段，比事后用 APM 发现要早得多。见 F-01。
  • 05嵌套序列化器有几层，prefetch_related 就要覆盖几层；GenericForeignKey 用 GenericPrefetch（Django 5.0+）。
  • 06不要在 SerializerMethodField 里查数据库。要么在 queryset 上预取，要么接受 N+1 —— 没有第三条路。
  • 07认证配全局，权限配单点。在 @action 上覆盖 authentication_classes 是替换而非追加。见 F-03。
  • 08记住 has_object_permission 对 list 无效。列表可见性必须靠 get_queryset() 过滤。
  • 09默认权限设成拒绝（IsAuthenticated），再逐视图放开，而不是默认放开再逐个收紧。
  • 10开启限流，并给昂贵端点单独设 ScopedRateThrottle。
  • 11生产关掉 BrowsableAPIRenderer。它不看 DEBUG，默认一直开着。
  • 12API 返回结构化数据，不返回 HTML。让客户端决定怎么渲染。见 F-05。
  • 13上线即带版本号。/api/v1/ 的成本是零，事后补版本的成本极高。
  • 14用 drf-spectacular 生成 OpenAPI 文档，并在 CI 里检查 schema 变更，把破坏性改动挡在合并之前。
  • 15序列化器用 fields 白名单，不用 exclude。用 exclude 时，将来给模型加的任何字段都会自动泄露到 API 里。

最后一条值得展开：本项目所有序列化器都用了显式 fields 列表，这是对的。exclude = ['password'] 这种写法看起来更省事，但它是黑名单——半年后有人给模型加了 internal_note 字段，它会毫无声息地出现在 API 响应里。白名单则相反：忘了加字段最多是功能缺失，不会变成数据泄露。

仍用本仓库的真实场景横向对比：「课程资源的只读 REST 接口，带分页」，以及「只有已报名学员才能读到课程完整内容」这个对象级权限需求。

9.1 资源序列化与路由

Django REST Framework

序列化器同时承担「字段声明」「校验」「模型映射」三件事；Router 由 ViewSet 反推出整组 URL。

class CourseSerializer(serializers.ModelSerializer):
    modules = ModuleSerializer(many=True, read_only=True)

    class Meta:
        model = Course
        fields = ['id', 'title', 'overview', 'modules']


class CourseViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Course.objects.prefetch_related('modules')
    serializer_class = CourseSerializer

router.register('courses', CourseViewSet)
  • ModelSerializer 从模型自动推字段类型与校验规则
  • 输出结构与模型结构默认耦合，解耦要靠手写字段
  • 路由是约定生成的，读代码看不到完整 URL 列表

Spring Boot 3.x

DTO、Controller、Mapper 三者分离，路由用注解显式声明在方法上。

public record CourseDto(
    Long id, String title, String overview,
    List<ModuleDto> modules) {}

@RestController
@RequestMapping("/api/courses")
class CourseController {

  @GetMapping
  Page<CourseDto> list(Pageable pageable) {
      return service.findAll(pageable).map(mapper::toDto);
  }

  @GetMapping("/{id}")
  CourseDto one(@PathVariable Long id) {
      return mapper.toDto(service.find(id));
  }
}
  • DTO 与实体天然分离，输出契约不受模型改动影响
  • 样板代码多，通常靠 MapStruct 生成 mapper
  • Page<T> 是框架一等公民，分页无需额外配置

Hono.js

没有序列化器概念，用 Zod 这类 schema 库同时做校验和类型推导。

import { zValidator } from '@hono/zod-validator'
import { z } from 'zod'

const CourseDto = z.object({
  id: z.number(),
  title: z.string(),
  modules: z.array(ModuleDto),
})

app.get('/api/courses/:id', async (c) => {
  const course = await db.course(c.req.param('id'))
  return c.json(CourseDto.parse(course))
})
  • schema 即类型：z.infer 直接得到 TypeScript 类型
  • 端到端类型安全，配合 hc 客户端连前端调用都有类型
  • 全部手写，没有任何「从模型自动生成」的便利

9.2 对象级权限

Django REST Framework

class CourseViewSet(viewsets.ReadOnlyModelViewSet):

    @action(detail=True, methods=['get'],
            permission_classes=[IsAuthenticated, IsEnrolled])
    def contents(self, request, *args, **kwargs):
        return self.retrieve(request, *args, **kwargs)


class IsEnrolled(BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.students.filter(
            id=request.user.id).exists()

对象级权限要等 get_object() 取到对象之后才触发，和类级权限是两个时机。

@action 上的 permission_classes 是整体替换而非追加——本项目 F-03 正是因为把 authentication_classes 一并替换掉了。

Spring Boot 3.x

@GetMapping("/{id}/contents")
@PreAuthorize("@enrollment.isEnrolled(#id, authentication)")
CourseWithContentsDto contents(@PathVariable Long id) {
    return mapper.toFullDto(service.find(id));
}

@Component("enrollment")
class EnrollmentChecker {
  boolean isEnrolled(Long courseId, Authentication auth) {
      return repo.existsByCourseIdAndStudentUsername(
          courseId, auth.getName());
  }
}

@PreAuthorize 里的 SpEL 可以直接调用 Spring Bean，把业务判断写成可复用组件。

方法级安全是叠加在类级配置之上的，不会意外覆盖掉全局认证方式。

Hono.js

const isEnrolled = createMiddleware(async (c, next) => {
  const user = c.get('user')
  const ok = await db.isEnrolled(
    c.req.param('id'), user.id)
  if (!ok) return c.json({ error: 'Not enrolled' }, 403)
  await next()
})

app.get('/api/courses/:id/contents',
  jwtAuth, isEnrolled, handler)

权限就是普通中间件，执行顺序即代码顺序，一眼能看出先认证后鉴权。

没有「对象级权限」这种抽象，要在中间件里自己查库——啰嗦，但没有隐式行为。

三句话概括

  • DRF 的强项是「从模型到 API 的距离最短」。一个 ModelSerializer 加一个 ModelViewSet，四个端点就出来了，还自带一个可浏览的调试界面——本仓库整个 API 只有 5 个文件、不到 200 行。代价是这种便利建立在「输出结构 ≈ 模型结构」的假设上，一旦要偏离，或者要给单个端点定制认证/权限/序列化器，就得靠类属性覆盖去打补丁，而覆盖的语义是替换而非追加，F-03 就是这么产生的。
  • Spring 的强项是显式与解耦。DTO 和实体天然分开，URL 写在方法上，@PreAuthorize 叠加而不覆盖全局安全配置，Page<T> 让分页不必每个视图重配。代价是样板代码显著更多，简单 CRUD 要写的量大概是 DRF 的三到五倍。
  • Hono 的强项是类型贯通与零隐式行为。Zod schema 既是运行时校验又是编译期类型，配合 hc 客户端可以做到从数据库到前端调用点的端到端类型安全，这是前两者都做不到的。代价是什么都没有——分页、过滤、限流、文档全部自己搭，适合团队清楚自己要什么、且愿意为类型安全付出手工成本的场景。
