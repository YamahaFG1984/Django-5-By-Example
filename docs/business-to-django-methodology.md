# 从业务需求到 Django 系统设计的方法论

这份文档面向同时承担项目经理、产品经理和开发者职责的人。目标不是从 Django 特性出发寻找应用场景，而是把真实业务现场中的需求，稳定地翻译成可落地的 Django 系统设计。

核心路径：

```text
业务对象 -> 业务动作 -> 业务规则 -> 业务关系 -> 状态流 -> 用户工作台 -> Django 实现
```

## 1. 核心思考框架

面对任何业务，不要先问“这个 Django 特性能用在哪里”，而要先问：

```text
这个业务里有哪些对象、动作、规则、关系、状态、通知、统计、权限、协作、交易和实时性？
```

当这些内容被整理清楚后，Django 的实现方式通常会自然浮现。

你需要同时建立三个模型：

| 模型 | 关注点 | 产出 |
|---|---|---|
| 业务模型 | 业务世界里有哪些对象和规则 | 名词、关系、状态、约束 |
| 交互模型 | 用户如何完成工作 | 页面、表单、列表、详情、工作台 |
| 技术模型 | Django 如何实现 | Model、View、Form、Permission、Task、API |

优秀的端到端交付者，本质上是在这三个模型之间不断翻译。

## 2. 第一步：找业务对象

先问：

```text
这个业务里反复出现、被创建、被修改、被审批、被统计的东西是什么？
```

这些通常会成为 Django 的 `Model`。

判断一个业务名词是否应该成为模型，可以看它是否满足以下条件：

- 是否需要长期保存？
- 是否会被多人查看？
- 是否会发生状态变化？
- 是否需要查询、筛选、统计？
- 是否会关联其他对象？
- 是否有权限边界？
- 是否有负责人、时间、状态、附件、备注？

新能源汽车售后场景里的模型候选：

- 技师
- 服务站
- 车辆
- 车型
- 故障码
- 维修案例
- 技术公告
- 培训课程
- 报名记录
- 工单
- 配件申请
- 订单
- 证书

不要急着设计字段。先把业务名词列全，再判断哪些是核心对象，哪些只是字段或枚举。

## 3. 第二步：找业务动作

问一线人员：

```text
你们每天会在这些对象上做什么？
```

业务动作通常会变成：

- `View`
- `Form`
- `ModelForm`
- API endpoint
- Admin action
- Celery task
- WebSocket message
- 导入导出功能

推荐用这个句式记录需求：

```text
谁，在什么条件下，对什么对象，做什么动作，得到什么结果？
```

例子：

```text
区域技术专家在案例审核通过后发布维修案例，系统通知关注该车型的服务站技师。
```

可以翻译成：

- 用户角色：区域技术专家
- 对象：维修案例
- 状态：审核通过
- 动作：发布
- 副作用：通知相关用户
- Django 能力：权限、状态字段、视图、消息、异步任务、关注关系查询

## 4. 第三步：找业务规则

业务规则是系统复杂度的主要来源。调研时重点问：

- 谁能看？
- 谁能创建？
- 谁能修改？
- 谁能删除？
- 什么状态下能改？
- 什么情况下不能删？
- 是否需要审批？
- 是否有时效？
- 是否有数量限制？
- 是否需要留痕？
- 是否要通知别人？
- 是否影响别的对象？

这些规则会映射到：

- 字段约束
- `Model.clean()`
- Form 校验
- View 权限
- `PermissionRequiredMixin`
- 自定义 QuerySet 过滤
- 状态机
- Signal
- Celery task
- 操作日志
- 审批记录

例子：

```text
只有总部专家能发布技术公告；服务站技师只能查看自己品牌和车型权限内的公告；已发布公告不能直接删除，只能下线。
```

Django 设计：

- `TechnicalBulletin.status`
- `TechnicalBulletin.allowed_models`
- `User.profile.organization`
- `PermissionRequiredMixin`
- 自定义 `get_queryset()`
- 后台 action：发布、下线
- 使用状态字段代替物理删除

## 5. 第四步：找业务关系

业务关系决定数据结构。

常见映射：

| 业务关系 | Django 设计 |
|---|---|
| 一个用户一个档案 | `OneToOneField` |
| 一个作者多篇文章 | `ForeignKey` |
| 一门课程多个学生 | `ManyToManyField` |
| 一个订单多个订单项 | `Order` + `OrderItem` |
| 一个对象可以评论多种对象 | `GenericForeignKey` |
| 课程内容有多种类型 | `ContentType` + 多态模型 |
| 一个流程有多个状态 | 状态字段或状态机 |
| 一个对象有父子结构 | 自关联 `ForeignKey` |
| 一个列表需要排序 | `order` 字段或自定义排序字段 |

关键问题：

```text
A 和 B 是一对一、一对多，还是多对多？
这个关系本身有没有属性？
```

如果关系本身有属性，不要直接使用普通 `ManyToManyField`，而应设计中间模型。

例子：

```text
技师参加课程。
```

如果只需要知道“谁参加了哪门课”，可以是：

```text
Course.students = ManyToManyField(User)
```

但真实业务里通常还需要：

- 报名时间
- 学习进度
- 完成时间
- 考试分数
- 证书编号
- 是否过期

这时应该设计：

```text
Enrollment(user, course, enrolled_at, progress, score, certificate_no, status)
```

## 6. 第五步：画状态流

企业系统里，状态往往比页面更重要。

你需要画出核心对象的生命周期。

例子：维修案例

```text
草稿 -> 提交审核 -> 审核中 -> 已发布 -> 已归档 -> 已下线
```

每个状态都要问：

- 谁能进入这个状态？
- 从哪个状态可以进入？
- 进入前要校验什么？
- 进入后要通知谁？
- 是否要生成记录、证书、订单、日志？

对应 Django 设计：

- `status` 字段
- transition 方法
- 权限判断
- 审批记录
- 通知任务
- 操作日志

如果状态流不清楚，代码里很容易散落大量 `if status == ...`，后期维护成本会很高。

## 7. 第六步：设计用户工作台

不要先从页面菜单开始设计，而要先问每类用户：

```text
你每天打开系统，最想先看到什么？
哪些事情需要你处理？
哪些异常必须马上发现？
```

然后为不同角色设计工作台。

总部专家工作台：

- 待审核案例
- 高频故障码
- 待回复问题
- 新车型资料更新
- 本周热门案例

服务站技师工作台：

- 我关注车型的公告
- 我的培训进度
- 我收藏的案例
- 最近搜索的故障码
- 待完成认证

对应 Django 能力：

- `ListView`
- `DetailView`
- 筛选和分页
- Dashboard 查询
- 权限过滤
- 缓存
- 消息通知

## 8. 业务需求到 Django 特性的映射表

| 业务需求 | Django / 技术特性 |
|---|---|
| 保存业务对象 | `Model` |
| 对象之间有关联 | `ForeignKey` / `ManyToManyField` / `OneToOneField` |
| 关系本身有属性 | 中间模型 |
| 用户填写信息 | `Form` / `ModelForm` |
| 用户操作流程 | View / CBV |
| 管理员维护数据 | Django Admin |
| 角色权限 | auth / groups / permissions |
| 只看自己的数据 | QuerySet 过滤 / OwnerMixin |
| 审批流 | `status` 字段 / transition 方法 |
| 上传图片和文件 | `FileField` / `ImageField` |
| 评论、点赞、收藏 | M2M / 中间模型 / Ajax |
| 活动动态 | `GenericForeignKey` |
| 搜索 | `icontains` / PostgreSQL full-text search / trigram search |
| 热门排行 | Redis counter / sorted set |
| 异步通知 | Celery |
| 支付或结算 | 订单模型 + 支付回调 |
| PDF 单据 | WeasyPrint |
| API 对接 | Django REST Framework |
| 实时协作 | Django Channels |
| 高访问内容 | Django cache framework |
| 多语言 | i18n / model translation |
| 生产部署 | Docker / Nginx / uWSGI / Daphne |

## 9. 用业务闭环组织需求

不要把需求写成纯功能清单：

```text
用户管理
文章管理
评论管理
订单管理
权限管理
```

这只是程序员视角，容易丢失业务价值。

更好的方式是按业务闭环组织：

```text
发现问题 -> 查找知识 -> 发起求助 -> 专家处理 -> 沉淀案例 -> 推送学习 -> 完成认证 -> 形成统计
```

新能源汽车售后平台示例：

1. 技师遇到故障。
2. 输入故障码搜索案例。
3. 查看相关技术公告。
4. 仍未解决则创建求助工单。
5. 上传现场图片和诊断日志。
6. 专家远程回复。
7. 问题解决后转为标准案例。
8. 推送给相同车型服务站。
9. 关联培训课程。
10. 统计该故障高发区域。

这个闭环明确后，系统边界、核心模型和优先级都会更清楚。

## 10. 一个人端到端交付时的版本策略

不要一开始做“大平台”。每一版只完成一个最小可用闭环。

示例路线：

### V1：技师搜索故障码并查看维修案例

需要：

- 用户登录
- 车型模型
- 故障码模型
- 案例模型
- 案例列表和详情
- 标签和搜索
- 后台录入

### V2：技师提交案例，总部审核发布

增加：

- 案例状态
- 提交流程
- 审核权限
- 审核记录
- 通知

### V3：案例和培训联动

增加：

- 课程模型
- 报名模型
- 学习进度
- 相关课程推荐
- 未完成提醒

### V4：实时专家支持

增加：

- 工单
- 附件
- 回复
- 聊天
- 活动流
- 热门故障排行

每一版都要能独立产生业务价值。

## 11. 一线调研问题清单

### 对象问题

- 你们每天处理哪些单据、记录、资料或对象？
- 哪些东西需要长期保存？
- 哪些东西经常被查询？
- 哪些东西会被多人协作处理？

### 动作问题

- 你在这些对象上会做哪些操作？
- 哪些操作最频繁？
- 哪些操作最容易出错？
- 哪些操作现在依赖微信群、Excel 或人工转发？

### 规则问题

- 谁能做这个操作？
- 什么情况下不能做？
- 有没有审批、时限或例外？
- 操作完成后是否需要留痕？

### 痛点问题

- 现在最浪费时间的是哪一步？
- 哪些信息经常找不到？
- 哪些问题重复发生？
- 哪些问题一旦出错影响最大？

### 结果问题

- 做完以后谁要知道？
- 需要生成什么单据、通知或报表？
- 怎么判断这件事完成了？
- 这些数据最终会被谁统计或追责？

## 12. 示例：从一线问题到 Django 设计

一线描述：

```text
现在服务站遇到电池故障，经常在群里问，总部专家重复回答，后面其他服务站也找不到之前的处理方法。
```

不要直接结论为“做个论坛”。先拆解。

业务对象：

- 故障问题
- 车辆型号
- 故障码
- 诊断图片
- 专家回复
- 标准案例

业务动作：

- 技师提问
- 上传图片
- 专家回复
- 标记标准答案
- 关闭问题
- 转为维修案例
- 其他人搜索

业务规则：

- 只有认证技师能提问
- 只有专家能标记标准答案
- 已关闭问题不能继续修改主描述
- 标准案例需要审核后发布

Django 实现：

- `Issue`
- `IssueAttachment`
- `Reply`
- `RepairCase`
- `status`
- `ImageField`
- `PermissionRequiredMixin`
- `ModelForm`
- `ListView` / `DetailView`
- PostgreSQL search
- Celery 通知
- Redis 热门故障排行

最终业务闭环：

```text
提问 -> 专家回复 -> 解决问题 -> 转为案例 -> 审核发布 -> 后续复用
```

## 14. 关键原则

1. 先理解业务，再选择 Django 特性。
2. 先找对象和动作，再设计数据库表。
3. 先画状态流，再写审批代码。
4. 先做最小闭环，再扩展平台能力。
5. 只要业务里有对象、关系、状态、权限、通知、统计、协作、交易和实时性，就能映射到 Django 的能力。

Django 是工具箱。业务分析的关键，是把现场混乱的语言整理成：

```text
对象、关系、状态、动作、规则、结果
```

整理到这个程度，系统设计和代码实现都会清晰很多。
