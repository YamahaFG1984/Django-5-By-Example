## 1. 背景与问题陈述

### 1.1 背景

个人/小团队需要一个轻量的内容发布平台，用于撰写和分享技术文章。目标用户是希望有自己独立博客（而非依赖第三方平台如公众号、掘金）、并希望完全掌控内容、域名、SEO 表现的内容创作者。

### 1.2 要解决的问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 没有独立的内容发布渠道 | 内容分散在第三方平台，无法自定义排版和数据 | 品牌沉淀弱，无法沉淀私域流量 |
| 读者无法方便地找到相关内容 | 没有标签、没有搜索 | 内容利用率低，旧文章石沉大海 |
| 无法和读者互动 | 没有评论、没有分享入口 | 缺少反馈闭环，内容改进无依据 |
| 搜索引擎收录差 | 没有 sitemap、没有 RSS | 自然流量获取困难 |

### 1.3 成功标准（North Star）

- 访客可以在 3 次点击以内，从任意一篇文章找到与其相关的其他内容（标签 / 相似推荐）。
- 站内搜索能容忍拼写误差找到目标文章（模糊匹配命中率）。
- 站点被搜索引擎正常收录（sitemap 可访问、RSS 可订阅）。

## 2. 目标与非目标

### 2.1 目标（In Scope）

1. 支持文章的创建、编辑、发布状态管理（草稿/已发布）。
2. 支持文章列表分页浏览、详情页阅读。
3. 支持按标签对文章分类和筛选。
4. 支持基于标签重合度的"相似文章"推荐。
5. 支持读者对文章发表评论。
6. 支持通过邮件分享文章给他人。
7. 支持站内模糊搜索（标题）。
8. 支持 RSS 订阅（最新文章）。
9. 支持 sitemap 自动生成，便于搜索引擎收录。
10. 支持站点统计信息展示（总发布数、最新文章、热门评论文章）。

### 2.2 非目标（Out of Scope，本期不做）

- 用户注册/登录体系（评论目前是匿名留言，不做账号绑定）。
- 富文本/所见即所得编辑器（内容通过 Markdown + Admin 后台录入）。
- 多作者协作审核流（作者即管理员，无需审批流）。
- 支付、订单、电商相关能力（不属于博客场景）。
- 实时聊天 / WebSocket 能力（不属于博客场景）。
- 评论的点赞、回复楼中楼（后续版本可考虑）。
- 文章浏览量统计、热度排行（后续版本可考虑）。

## 3. 用户角色

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| 访客（匿名读者） | 未登录的公开网站访问者，占绝大多数流量 | 快速找到感兴趣的内容、方便地阅读和分享 |
| 评论者 | 在文章下留言的访客 | 留言便捷，不需要注册账号 |
| 站点管理员 / 作者 | 通过 Django Admin 后台管理内容的运营者 | 高效地创建/编辑/发布文章，管理不合规评论 |

> 备注：当前版本中"管理员"和"作者"是同一角色（复用 Django 内建 `auth.User` + Admin 后台），未来若要支持多作者，需要单独设计作者档案和权限体系。

## 4. 功能需求（Functional Requirements）

每条需求采用"谁、在什么条件下、对什么对象、做什么、得到什么结果"的格式描述，并标注对应的验收标准（AC）。

### FR-1 文章发布与状态管理

**用户故事**：作为管理员，我希望文章有"草稿"和"已发布"两种状态，以便我可以先保存草稿，确认无误后再对外发布。

- AC1：新建文章默认状态为"草稿"（Draft）。
- AC2：只有状态为"已发布"（Published）的文章会出现在前台列表、搜索结果、RSS、sitemap 中。
- AC3：管理员可以在 Admin 后台批量修改文章状态。
- AC4：Admin 列表页需要支持按状态筛选、按标题/内容搜索、按发布日期做日期层级导航。

### FR-2 文章列表与分页

**用户故事**：作为访客，我希望看到按时间倒序排列的文章列表，并且能翻页浏览历史文章，以便我可以系统性地浏览博客内容。

- AC1：列表默认按发布时间倒序排列。
- AC2：每页展示固定数量的文章（当前定义为 3 篇/页，可配置）。
- AC3：请求超出最大页码或页码参数非法（非数字）时，系统应friendly降级（分别展示最后一页或第一页），不应报错。
- AC4：翻页链接需保留当前的筛选条件（如标签）在 query string 中。

### FR-3 文章详情页

**用户故事**：作为访客，我希望点击文章标题后能看到完整内容、作者、发布时间、评论和相关推荐，以便获得完整的阅读体验。

- AC1：详情页 URL 需包含发布年月日和 slug，兼顾可读性与 SEO（如 `/2026/7/4/my-post/`）。
- AC2：同一天内文章 slug 不能重复（约束在数据层面保证），但允许不同日期出现相同 slug。
- AC3：正文内容以 Markdown 撰写，前台展示时渲染为 HTML。
- AC4：详情页展示该文章的评论列表和"相似文章"推荐区块。

### FR-4 标签系统

**用户故事**：作为访客，我希望能通过标签筛选出某一类主题的文章，以便快速定位我感兴趣的内容。

- AC1：一篇文章可以关联零到多个标签。
- AC2：点击某个标签后，列表页只展示包含该标签的已发布文章，同时页面需要明确提示当前处于"按标签筛选"状态。
- AC3：访问不存在的标签 slug 时返回 404。

### FR-5 相似文章推荐

**用户故事**：作为访客，我希望在读完一篇文章后，看到与之标签重合度最高的其他文章，以便继续阅读相关内容，提高站内停留时长。

- AC1：推荐结果按"共同标签数量"降序，标签数量相同时按发布时间新旧排序。
- AC2：推荐结果不包含当前文章本身。
- AC3：最多展示 4 篇推荐文章；若无标签重合的文章，展示"暂无相似文章"的空状态提示。

### FR-6 评论功能

**用户故事**：作为访客，我希望能在文章下方留下姓名、邮箱和评论内容，以便和作者/其他读者互动。

- AC1：评论表单包含姓名、邮箱、正文三个必填字段（姓名/邮箱做基础校验：姓名非空、邮箱格式合法）。
- AC2：评论提交仅接受 POST 请求；非 POST 方式访问评论提交地址应被拒绝。
- AC3：评论提交成功后，需要将评论正确关联到所属文章。
- AC4：详情页只展示"已审核通过（active=True）"的评论；默认新评论状态需要在数据层面明确定义（当前实现默认可见，后续若需要人工审核可在此基础上调整默认值）。
- AC5：评论展示需对用户输入的内容做安全转义（不允许注入 HTML/脚本），区别于文章正文（作者可信内容允许渲染 Markdown/HTML）。

### FR-7 邮件分享文章

**用户故事**：作为访客，我希望可以把喜欢的文章通过邮件分享给朋友，以便帮助作者扩大传播。

- AC1：分享表单包含：我的称呼、我的邮箱、对方邮箱、留言（选填）。
- AC2：提交后系统发送一封包含文章标题、文章链接（绝对 URL）、以及推荐语的邮件到目标邮箱。
- AC3：邮件发送失败（如 SMTP 异常）需要有明确的错误反馈，不能让用户以为分享成功。
- AC4：表单校验失败时，需要保留已填内容并展示错误提示，不清空重填。

### FR-8 站内搜索

**用户故事**：作为访客，我希望即使记不清文章标题的确切拼写，也能通过关键词搜到相关文章，以便节省查找时间。

- AC1：搜索基于文章标题做模糊相似度匹配，允许一定程度的拼写误差。
- AC2：搜索结果按相似度降序排列，仅返回相似度超过最低阈值的结果，避免完全不相关的内容混入。
- AC3：无搜索词时展示搜索表单；有搜索词但无结果时展示"无结果"的空状态提示，而非空白页面。
- AC4：搜索结果需展示命中数量、文章标题（可点击进入详情）、内容摘要。

### FR-9 RSS 订阅

**用户故事**：作为访客，我希望可以用 RSS 阅读器订阅这个博客，第一时间获取更新，而不需要每天手动访问网站。

- AC1：提供标准 RSS/Atom 格式的订阅源，包含站点名称、描述、最新若干篇已发布文章。
- AC2：每条订阅项包含标题、摘要、发布时间、指向详情页的链接。
- AC3：站点页面需要有明显的订阅入口链接。

### FR-10 站点地图（Sitemap）与 SEO

**用户故事**：作为站点运营者，我希望搜索引擎能够完整、及时地收录所有已发布文章，以便获取自然搜索流量。

- AC1：`sitemap.xml` 需要包含所有已发布文章的 URL、最近更新时间、更新频率、优先级权重等信息。
- AC2：文章更新后，sitemap 中的 `lastmod` 应同步更新，帮助搜索引擎判断是否需要重新抓取。

### FR-11 侧边栏统计信息

**用户故事**：作为访客，我希望在任意页面都能看到"最新文章"和"热门评论文章"，以便发现除当前浏览内容外的其他好文章。

- AC1：全站页面侧边栏统一展示：文章总数（已发布）、最新 N 篇文章列表、按评论数排序的热门文章列表。
- AC2：这些统计信息应仅统计"已发布"状态的文章，草稿不计入。

## 5. 非功能需求（NFR）

| 类别 | 要求 |
|---|---|
| 性能 | 列表页、详情页在正常数据量（数千篇文章）下应在数据库层完成分页/过滤，不做全表加载到内存；搜索和推荐类查询需要考虑索引优化（如相似度搜索所需的 GIN 索引）。 |
| SEO | URL 需保持稳定、语义化（年月日+slug）；提供 sitemap 与 RSS 支撑收录。 |
| 安全 | 评论等用户输入内容必须转义防止 XSS；表单提交需要 CSRF 防护（Django 默认能力）；生产环境的邮箱、数据库等密钥不得硬编码或提交到代码仓库。 |
| 可用性 | 移动端和桌面端均可正常浏览（响应式布局）；分页、搜索、标签筛选等操作应有明确的空状态和错误状态提示，不能出现无提示的报错或空白页。 |
| 可维护性 | 数据模型变更需通过迁移（migration）管理，且需评估迁移对生产数据库的锁表/性能影响。 |
| 合规 | 评论功能收集访客的姓名和邮箱，需要明确告知用途，并具备基本的信息安全保护（不对外公开邮箱等敏感字段）。 |

## 6. 核心数据模型概览

> 完整字段和实现细节参见 `docs/chapter01-blog-teaching.md` ~ `docs/chapter03-blog-teaching.md`，此处仅从产品视角描述实体关系。

```text
User (系统内建用户) ──1:N── Post (文章)
Post ──1:N── Comment (评论)
Post ──M:N── Tag (标签，中间表包含标签归属信息)
```

| 实体 | 关键属性（产品视角） | 备注 |
|---|---|---|
| Post（文章） | 标题、slug、正文（Markdown）、作者、发布时间、创建/更新时间、状态（草稿/已发布）、标签 | 状态和发布时间共同决定是否对外可见 |
| Comment（评论） | 姓名、邮箱、正文、创建时间、是否审核通过 | 当前无需登录即可发表 |
| Tag（标签） | 名称、slug | 由第三方标签库统一管理，支持多篇文章复用同一标签 |

## 8. 后续迭代需求规划（V4 及以后）

本节整理当前 V1~V3 之外、后续可以纳入排期的迭代需求。按主题分组，每项标注：

- **优先级**：P0（高价值/应尽早做）、P1（重要但不紧急）、P2（锦上添花，可延后）。
- **工作量**：T恤码估算，S（<3 天）、M（3 天~2 周）、L（2~4 周）、XL（>4 周，通常需要拆分为多个子任务）。
- **依赖**：需要先完成的前置能力。

### 8.1 账号与社区

| 功能 | 用户故事（简述） | 优先级 | 工作量 | 依赖 |
|---|---|---|---|---|
| 读者注册/登录 | 作为常来的读者，我希望有账号，以便我的评论能显示身份、我能管理自己的历史评论 | P0 | M | 无（Django 内建 auth 即可起步） |
| RBAC 权限体系（角色与权限管理） | 作为站点负责人，我希望能定义不同角色（如超级管理员、主编、作者、审核员）并为每个角色分配明确的操作权限，以便团队扩大后仍能清楚地控制谁能做什么，而不用给每个人开超级管理员权限 | P0 | L | 依赖读者注册/登录（需要账号体系作为权限主体） |
| 评论人工审核工作流 | 作为管理员，我希望新评论默认待审核，审核通过后才对外可见，以避免垃圾/攻击性内容直接展示 | P0 | S | 依赖 `Comment.active` 字段（已存在）；审核权限归属需依赖 RBAC 权限体系 |
| 文章收藏（登录版重做） | 作为登录读者，我希望能收藏文章，以便之后在"我的收藏"里快速找回 | P1 | M | 依赖读者注册/登录 |
| 评论点赞 | 作为读者，我希望能给认同的评论点赞，帮助优质评论被更多人看到 | P2 | S | 依赖读者注册/登录（防刷需要身份） |
| 评论回复（楼中楼） | 作为读者，我希望能针对某条评论直接回复，而不是都平铺在最外层 | P1 | M | 无（评论表自关联即可，登录可选） |
| 用户个人主页 | 作为登录读者，我希望有一个页面汇总"我的评论""我的收藏" | P2 | M | 依赖读者注册/登录、文章收藏 |
| 多作者投稿与审核流 | 作为站点运营者，我希望能邀请多位作者投稿，由主编审核后发布 | P1 | L | 依赖读者注册/登录、RBAC 权限体系（区分作者/主编角色）、文章状态机需要新增"待审核"状态 |

**RBAC 角色建议（供设计参考）：**

- **超级管理员（Superuser）**：系统配置、用户与角色管理、全部权限，通常只有 1~2 人。
- **主编（Editor）**：审核/发布所有作者的文章、审核评论、管理分类和标签，但不管用户账号本身。
- **作者（Author）**：创建、编辑自己名下的文章；草稿状态可自由编辑，已发布文章的修改/下线需要主编权限（对象级权限校验，而非仅角色级）。
- **审核员（Moderator，可选角色）**：只负责评论审核，无文章发布权限——用于把"内容治理"和"评论治理"职责分开，避免所有管理动作都挤在主编一个角色上。
- **普通读者（Reader）**：登录后可评论、收藏、点赞，无任何后台权限。

对应验收标准：

- AC1：角色和权限组合可在后台配置调整，而非硬编码在代码逻辑里（建议基于 Django `Group`/`Permission` 框架搭建，对象级权限如"只能编辑自己的文章"可引入 `django-guardian` 一类方案）。
- AC2：作者只能编辑/删除自己创建的草稿；已发布文章的编辑/下线操作需要主编及以上权限。
- AC3：审核员角色只能访问评论审核相关后台入口，无法访问文章发布、用户管理等功能模块。
- AC4：角色分配变更需要留有操作记录（谁在何时把谁设为什么角色），便于事后追溯。
- AC5：若已开放 REST API，接口返回的数据范围需要按调用者角色/权限收窄，避免普通读者身份的请求拿到管理端专属数据。

### 8.2 内容运营与分发

| 功能 | 用户故事（简述） | 优先级 | 工作量 | 依赖 |
|---|---|---|---|---|
| 定时发布 | 作为管理员，我希望能设置文章在未来某个时间点自动发布，而不用到点手动操作 | P1 | M | 依赖异步任务队列（Celery） |

### 8.6 迭代排期建议

在没有额外业务信号（如某功能被用户强烈反馈缺失）的前提下，建议按以下顺序推进，遵循"先补足互动闭环和基础设施，再做增长和开放能力"的逻辑：

| 版本 | 主题 | 核心交付 |
|---|---|---|
| V4 | 互动闭环补全 | 读者注册/登录、RBAC 权限体系、评论人工审核工作流、封面图/图床、日志监控告警 |
| V5 | 内容体验与稳定性 | 全文检索升级（标题+正文）、浏览量统计与热度排行、页面缓存、异步任务队列（Celery） |
| V6 | 内容组织与运营效率 | 分类目录、定时发布、草稿预览链接、评论回复楼中楼、文章收藏（登录版） |
| V7 | 增长与开放能力 | 开放 REST API、管理员数据看板、评论反垃圾、社交平台一键分享、多作者投稿审核流 |
| V8（长期） | 深度个性化与规模化 | 个性化推荐、多语言国际化、Webhook、数据库读写分离/CDN |

> 排期原则：P0 且工作量为 S/M 的功能优先；凡依赖 Celery/Redis 等新基础设施的功能尽量集中在同一版本引入，避免反复搭建部署环境；RBAC 权限体系作为账号能力的地基，需在多作者协作、管理员看板、开放 API 等功能之前就位，因此提前排入 V4；P2 且工作量 XL 的功能（如个性化推荐、多语言）默认放到长期规划，除非有明确的业务驱动信号。

## 9. 待决问题（Open Questions）

以下问题在当前代码实现中存在但尚未在需求层面明确拍板，建议在正式评审时逐条决策：

1. **评论默认是否需要人工审核？** 当前 `Comment.active` 字段存在，但新评论创建时的默认可见策略需要产品明确：是"默认可见、事后抽查下架"还是"默认隐藏、审核通过后可见"？两种策略对读者体验和管理员工作量影响完全不同。
2. **收藏功能是否要保留、且是否需要登录？** V1 出现的收藏能力涉及匿名用户能否收藏的权限问题，需要产品明确收藏功能的目标用户和最终去留（当前该功能在 V2/V3 中已不再出现，需确认是被有意移除还是遗留技术债）。
3. **搜索能力是否要从"标题模糊匹配"升级为"标题+正文全文检索"？** 当前范围仅覆盖标题，若用户反馈搜不到内容多在正文中，需要评估升级为正文全文检索的成本与收益。
4. **是否需要多作者协作？** 当前"作者=管理员"的假设在个人博客场景成立，若产品定位扩展为多人博客/团队博客，则需要重新设计作者档案、投稿审核流程和权限模型。
