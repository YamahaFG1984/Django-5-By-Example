Django 分页实战指南

面向 Django 5.2。性能数字均在本机 20 万行数据上实测得到，代码分析来自本仓库 Chapter02~03、Chapter06~07、Chapter15~17 的四处真实分页实现。

Django 5.2 · DRF 3.15.1 含 6 张架构示意图 8 个已验证的问题

本文结论速览

三条最重要的结论

  1. OFFSET 分页的代价随翻页深度线性增长。 实测 20 万行的表，第 10000 页比第 1 页慢 58 倍（16.03 ms vs 0.28 ms）；同样深度换成键集分页是 0.35 ms，与第 1 页持平。详见 F-01。
  2. 翻页期间只要有人写入，OFFSET 分页就会重复或漏掉记录。 已复现两种情形：新发一篇文章导致「文章 08」在第 1 页和第 2 页各出现一次；删掉一篇导致「文章 07」用户永远看不到。本仓库四处分页全部受影响。详见 F-02。
  3. 每翻一页都要 COUNT 一次全表。 实测 20 万行时 COUNT(*) 占单次请求耗时的 90%——而 bookmarks 的无限滚动根本不需要总数，这笔钱是白花的。详见 F-05。

本文结构与缓存指南、DRF 指南一致：先讲 Django 5.2 的分页机制与三套 API，再逐处分析本仓库的四处分页代码，然后是八个已验证的问题及修复、键集分页专题，最后是上线清单与 Spring / Hono.js 对比。所有性能数字都在本机 Django 5.2 上实测得到，实测输出以绿色标题的终端块标注。

关于测试环境：性能实测用的是 SQLite（本机没有 PostgreSQL），数据量 20 万行、排序列带索引。SQLite 与 PostgreSQL 在 LIMIT/OFFSET 上的行为是一致的——都必须沿索引走过并丢弃 OFFSET 指定的行数，所以趋势和量级可以外推，但绝对毫秒数不要直接套用到你的生产库上。逻辑类结论（重复、漏项、排序不确定）与数据库无关。

一、Django 的分页机制：两条 SQL

Paginator 本身是个惰性的包装器，构造时不查库。真正触发 SQL 的是两个动作：

  • 访问 .count / .num_pages → SELECT COUNT(*)。这是 cached_property，同一个 Paginator 实例只算一次。
  • 调用 .page(n) → LIMIT page_size OFFSET (n-1)*page_size。
实测 · 1000 篇文章、每页 3 条，观察实际 SQL
请求第 1 页 -> 2 条 SQL
    [COUNT]
    [SELECT 数据] ...FROM "blog_post" ORDER BY "blog_post"."publish" DESC LIMIT 3

请求第 2 页 -> 2 条 SQL
    [COUNT]
    [SELECT 数据] ...ORDER BY "blog_post"."publish" DESC LIMIT 3 OFFSET 3

请求第 50 页 -> 2 条 SQL
    [COUNT]
    [SELECT 数据] ...ORDER BY "blog_post"."publish" DESC LIMIT 3 OFFSET 147

注意「cached_property 只算一次」是实例级的缓存。而 Web 请求里每次都会新建一个 Paginator，所以实际效果是每翻一页都重新 COUNT 一次全表。

1.2 get_page()：本仓库还没用上的简化写法

仓库里三处都手写了同一段三分支容错：

现状：手写三分支（三处各写一遍）
paginator = Paginator(post_list, 3)
page_number = request.GET.get('page', 1)
try:
    posts = paginator.page(page_number)
except PageNotAnInteger:
    posts = paginator.page(1)
except EmptyPage:
    posts = paginator.page(paginator.num_pages)
get_page()：语义完全相同，一行
paginator = Paginator(post_list, 3)
posts = paginator.get_page(request.GET.get('page'))

# 非整数 -> 第 1 页
# 超出范围 -> 最后一页
# 空 queryset -> 允许空第 1 页

这不是「教材写错了」——书里手写三分支是为了讲清楚 PageNotAnInteger 和 EmptyPage 这两个异常什么时候抛。理解之后，生产代码用 get_page() 即可。实测确认：默认配置下（allow_empty_first_page=True），空 queryset 上 get_page(1)、get_page('abc')、page(1) 都能正常返回一个空的第 1 页；get_page() 的价值在于把「页码不是整数」和「页码超出范围」这两种情况也一并兜住，永不抛异常。注意如果显式设了 allow_empty_first_page=False，空 queryset 上 get_page() 同样会抛 EmptyPage——它兜底的是页码本身，不是「结果集为空」这件事。

二、本仓库四处分页逐处分析

2.1 blog · post_list()：最标准的一处

python
def post_list(request, tag_slug=None):
    post_list = Post.published.all()
    tag = None
    if tag_slug:
        tag = get_object_or_404(Tag, slug=tag_slug)
        post_list = post_list.filter(tags__in=[tag])
    # Pagination with 3 posts per page
    paginator = Paginator(post_list, 3)
    page_number = request.GET.get('page', 1)
    try:
        posts = paginator.page(page_number)
    except PageNotAnInteger:
        posts = paginator.page(1)
    except EmptyPage:
        posts = paginator.page(paginator.num_pages)
    return render(request, 'blog/post/list.html', {'posts': posts, 'tag': tag})

逻辑本身没问题。三个隐患：排序键 -publish 不唯一（F-03）；分页链接会丢查询参数（F-08）；以及配套模板与 CBV 不兼容（F-04）。

2.2 blog · post_search()：完全没有分页

python
def post_search(request):
    form = SearchForm()
    query = None
    results = []
    if 'query' in request.GET:
        form = SearchForm(request.GET)
        if form.is_valid():
            query = form.cleaned_data['query']
            results = (
                Post.published.annotate(
                    similarity=TrigramSimilarity('title', query),
                )
                .filter(similarity__gt=0.1)
                .order_by('-similarity')
            )
    return render(request, 'blog/post/search.html',
                  {'form': form, 'query': query, 'results': results})

模糊搜索匹配多少就返回多少，没有任何上限。similarity__gt=0.1 是一个很低的阈值——在一个几千篇文章的博客上，一个常见词可能命中数百条，全部渲染进一个页面。这是整个仓库里最需要分页、却唯一完全没有分页的视图（F-07）。

2.3 bookmarks · image_list()：一个视图两种返回

python
@login_required
def image_list(request):
    images = Image.objects.all()
    paginator = Paginator(images, 8)
    page = request.GET.get('page')
    images_only = request.GET.get('images_only')
    try:
        images = paginator.page(page)
    except PageNotAnInteger:
        images = paginator.page(1)
    except EmptyPage:
        if images_only:
            # If AJAX request and page out of range return an empty page
            return HttpResponse('')
        images = paginator.page(paginator.num_pages)
    if images_only:
        return render(request, 'images/image/list_images.html',
                      {'section': 'images', 'images': images})
    return render(request, 'images/image/list.html',
                  {'section': 'images', 'images': images})

这是全书分页写得最巧的一处：同一个视图根据 images_only 参数决定返回整页还是只返回列表片段。首屏走完整模板，滚动加载时前端只要那一小段 HTML 直接拼接——不需要单独写一个 API，也不需要前端做模板渲染。EmptyPage 分支返回空字符串，前端用「收到空响应」当作没有更多数据的信号，这个约定也很干净。

问题在配套的前端状态机上（F-06），以及无限滚动场景下 COUNT 查询纯属浪费（F-05）。

2.4 educa · StandardPagination：配置最完整的一处

python
class StandardPagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = 'page_size'   # 允许客户端调整每页条数
    max_page_size = 50                    # 但设上限

max_page_size 这一项很多人会漏。不设上限，客户端一个 ?page_size=999999 就把分页彻底绕过去了——这在对外 API 上等于给了任何人一个免费的全表导出接口。这处写对了。

但它只在两个 ViewSet 上逐个配置，没有配 DEFAULT_PAGINATION_CLASS 全局默认值。这意味着新加的视图忘了配就会返回全表——这一点在 DRF 指南里详细讨论过。

三、八个已验证的问题与修复

前六条经过实测复现，后两条是代码阅读所得（已在标签里注明）。

F-01OFFSET 深翻页的代价随深度线性增长已实测 · 性能
位置
四处分页全部适用
触发
用户翻到较深的页，或爬虫顺序遍历全部页面
影响
20 万行表上第 10000 页比第 1 页慢 58 倍；数据量越大差距越大
实测 · 20 万行，publish 上有索引，每页 20 条
     页码    OFFSET       中位耗时    相对第 1 页
--------------------------------------------------
        1         0       0.28 ms       1.0×
       10       180       0.28 ms       1.0×
      100     1,980       0.34 ms       1.2×
    1,000    19,980       1.01 ms       3.7×
    5,000    99,980       7.10 ms      25.8×
   10,000   199,980      16.03 ms      58.2×

改用键集分页（WHERE publish < ? ORDER BY publish DESC LIMIT n）：
    等效深度        中位耗时
         1 页       0.39 ms
     1,000 页       0.35 ms
    10,000 页       0.35 ms

根因。 OFFSET n 不是「跳到第 n 行」，而是「读出前 n 行然后全部丢掉」。数据库没有办法直接定位到第 n 行——即使有索引，也得沿着索引一个一个数过去。所以代价是 O(offset)，而不是 O(page_size)。

修复。 见第四节的键集分页。对模板视图的一个折中办法是限制最大页码，把深翻页挡在门外：

python
MAX_PAGE = 100

paginator = Paginator(post_list, 20)
page_number = request.GET.get('page', 1)
try:
    if int(page_number) > MAX_PAGE:
        raise Http404('页码超出范围，请使用搜索或筛选缩小结果')
except (TypeError, ValueError):
    pass
posts = paginator.get_page(page_number)

「限制最大页码」听起来粗暴，但它符合真实用户行为：几乎没有人会手工翻到第 100 页，翻那么深的基本是爬虫。Google 搜索结果最多给你翻到大约第 40 页，也是同样的取舍。

F-02翻页期间数据变动导致记录重复或被跳过已实测 · 正确性
位置
四处分页全部适用；bookmarks 无限滚动最容易触发
触发
用户从第 1 页翻到第 2 页的间隙，有人插入或删除了排在前面的记录
影响
同一条记录在两页里都出现；或某条记录一次都不出现
实测 · 10 篇文章、每页 3 条、按 -publish 排序
初始状态：
  第 1 页: ['文章 10', '文章 09', '文章 08']
  第 2 页: ['文章 07', '文章 06', '文章 05']

场景 A · 看完第 1 页后有人发布了新文章
  第 1 页（插入前读的）: ['文章 10', '文章 09', '文章 08']
  第 2 页（插入后读的）: ['文章 08', '文章 07', '文章 06']
  -> 重复出现的文章: ['文章 08']

场景 B · 看完第 1 页后第 1 页里有一篇被删除
  第 1 页（删除前读的）: ['文章 10', '文章 09', '文章 08']
  第 2 页（删除后读的）: ['文章 06', '文章 05', '文章 04']
  -> 用户从未见过的文章: ['文章 07']

场景 C · 同样的插入，改用键集分页
  第 1 页: ['文章 10', '文章 09', '文章 08']
  第 2 页（游标 = 上一页最后一条的 publish）: ['文章 07', '文章 06', '文章 05']
  -> 重复出现的文章: 无

根因。 OFFSET 记录的是「跳过多少行」这个位置，而位置会随着前面的行增减而漂移。键集记录的是「从哪个值之后开始」，这个值不会因为别处的插入删除而改变。

本仓库最容易踩到的是 bookmarks 的无限滚动。 Image.Meta.ordering = ['-created']——最新的在最前面，而新收藏的图片正是从最前面插入的。一个活跃的站点上，用户一边往下滚、别人一边在收藏新图，重复项几乎是必然出现的。而无限滚动的界面又恰好会把重复项并排显示在同一屏里，比传统翻页更容易被用户直接看到。

F-03排序键不唯一，并列行的顺序不由 SQL 决定已实测 · 正确性
位置
Post.Meta.ordering = ['-publish']、Image.Meta.ordering = ['-created']、post_search 的 order_by('-similarity')
触发
存在排序值相同的记录（批量导入、定时发布、相似度并列）
影响
并列行的相对顺序由执行计划决定，换计划就可能变，进而导致翻页重复或漏项
实测 · 6 行 publish 完全相同，只按 publish DESC 排序
  计划 A（走 -publish 索引）
    计划: SCAN blog_post USING INDEX blog_post_publish_bb7600_idx
    顺序: ['并列文章 0', '并列文章 1', ..., '并列文章 5']
  计划 B（额外用 rowid 决胜）
    计划: SCAN ... | USE TEMP B-TREE FOR RIGHT PART OF ORDER BY
    顺序: ['并列文章 5', '并列文章 4', ..., '并列文章 0']

  A 与 B 顺序相同? False

说明一下这条实测的边界：本次 SQLite 在同一个执行计划下的多次读取是稳定的，我没有观察到同一查询自发变序。真正的问题在于 SQL 层面没有为并列行规定任何顺序，数据库返回什么都算合法——上面 A 与 B 的对比说明，只要执行计划变了，顺序就变了。换成 PostgreSQL、启用并行扫描、加一个改变计划的过滤条件，都可能触发。这是契约层面的不确定，不该赌某个引擎当前的实现细节。

✗ 现状：单一非唯一排序键
class Meta:
    ordering = ['-publish']
✓ 补一个主键做决胜键
class Meta:
    ordering = ['-publish', '-id']
    indexes = [
        models.Index(fields=['-publish', '-id']),
    ]

索引也要跟着改成复合索引，否则新增的排序键会让数据库多做一次排序。凡是要分页的 queryset，排序键必须能唯一确定每一行的位置——最省事的做法就是在末尾追加主键。

F-04pagination.html 与 PostListView 不兼容，且失败时无声无息已实测 · 功能
位置
Chapter02~03/mysite/blog/templates/pagination.html
触发
把 URL 切换到注释里那行 PostListView
影响
翻页控件整体消失，页面显示「Page of .」，没有任何报错

模板期待的是一个 Page 对象：

html
{% if page.has_previous %}
  <a href="?page={{ page.previous_page_number }}">Previous</a>
{% endif %}
<span class="current">
  Page {{ page.number }} of {{ page.paginator.num_pages }}.
</span>
html
<!-- list.html 里是这样传的 -->
{% include "pagination.html" with page=posts %}

函数视图 post_list 里 posts = paginator.page(n) 确实是 Page，所以能用。但 PostListView 设了 context_object_name = 'posts'，而 ListView 把这个名字绑到的是 object_list——也就是当前页的数据集合，不是 Page：

实测 · 同一个模板，两种视图
=== A) 函数视图：posts = paginator.page(2)，是 Page 对象 ===
   传入对象类型: Page
   渲染结果:
      <a href="?page=1">Previous</a>
      Page 2 of 4.
      <a href="?page=3">Next</a>

=== B) 类视图 PostListView ===
   context 里的 key : ['is_paginated', 'object_list', 'page_obj', 'paginator', 'posts']
   posts 的类型     : QuerySet
   page_obj 的类型   : Page

   把 posts 当 page 传给 pagination.html（模板里就是这么写的）：
      Page  of .          <- 翻页链接全部消失，且没有任何报错

   正确写法是传 page_obj：
      <a href="?page=1">Previous</a>
      Page 2 of 4.
      <a href="?page=3">Next</a>

为什么不报错？ Django 模板对不存在的属性是静默失败的——page.has_previous 解析不出来就返回空字符串，{% if %} 判为假，链接直接不渲染。这类问题不会出现在日志里，只能靠肉眼看页面发现。

html
<!-- 修复：让模板同时兼容两种传法 -->
{% include "pagination.html" with page=page_obj %}

更稳妥的做法是在开发环境把 string_if_invalid 设成一个显眼的标记，让这类静默失败变得可见：

TEMPLATES[0]['OPTIONS']['string_if_invalid'] = '【模板变量缺失: %s】'

注意这只适合本地开发——它会让所有正常的空值也显示出标记。

F-05每翻一页都 COUNT 一次全表，而无限滚动根本不需要总数已实测 · 性能
位置
三处手写 Paginator + DRF 的 PageNumberPagination
触发
每一次分页请求
影响
20 万行时 COUNT 占单次请求耗时的 90%；无限滚动场景下完全是浪费
实测 · 20 万行表
COUNT(*) 全表             :    3.28 ms
取第 1 页 20 行（无 COUNT）:    0.38 ms
-> COUNT 占一次「第 1 页」请求总耗时的 90%

页码分页需要总数来算「共 N 页」，这笔开销有其价值。但 bookmarks 的无限滚动从头到尾没有用过总数——前端只关心「还有没有下一批」，而这个问题用「多取一条看看有没有」就能回答，成本几乎为零：

python
@login_required
def image_list(request):
    page = int(request.GET.get('page', 1))
    per_page = 8
    offset = (page - 1) * per_page
    # 多取一条：能取到第 9 条就说明还有下一页
    images = list(Image.objects.all()[offset:offset + per_page + 1])
    has_next = len(images) > per_page
    images = images[:per_page]

    if request.GET.get('images_only'):
        if not images:
            return HttpResponse('')
        return render(request, 'images/image/list_images.html',
                      {'section': 'images', 'images': images})
    return render(request, 'images/image/list.html',
                  {'section': 'images', 'images': images, 'has_next': has_next})

DRF 侧对应的做法是换成 CursorPagination，它的响应里就没有 count 字段：

实测 · DRF 三种分页类的 SQL 开销
=== PageNumberPagination ===   响应字段: ['count', 'next', 'previous', 'results']
  SQL 条数: 2  (其中 COUNT 查询 1 条)

=== LimitOffsetPagination ===  响应字段: ['count', 'next', 'previous', 'results']
  SQL 条数: 2  (其中 COUNT 查询 1 条)

=== CursorPagination ===       响应字段: ['next', 'previous', 'results']
  SQL 条数: 1  (其中 COUNT 查询 0 条)
F-06无限滚动的 fetch 没有 catch 分支，一次网络失败就永久卡死代码阅读 · 健壮性
位置
Chapter06~07/bookmarks/images/templates/images/image/list.html
触发
任意一次 fetch 失败：网络抖动、服务端 5xx、请求超时
影响
blockRequest 永远保持 true，此后再怎么滚动都不会加载；且 page 已自增，重试会跳过一页
javascript
window.addEventListener('scroll', function(e) {
  var margin = document.body.clientHeight - window.innerHeight - 200;
  if(window.pageYOffset > margin && !emptyPage && !blockRequest) {
    blockRequest = true;          // 上锁
    page += 1;                    // 页码先自增

四、键集分页：F-01 与 F-02 的共同解

前面两个最严重的问题——深翻页变慢、翻页期间重复漏项——根因是同一个：OFFSET 用「位置」定位，而位置是会漂移的。键集分页（keyset pagination，也叫游标分页、seek method）改用「值」定位，两个问题一起解决。

4.1 原理

OFFSET：记住跳过多少行
-- 第 1 页
SELECT * FROM blog_post
ORDER BY publish DESC
LIMIT 20;

-- 第 2 页：跳过 20 行（要先读出来再丢掉）
SELECT * FROM blog_post
ORDER BY publish DESC
LIMIT 20 OFFSET 20;
键集：记住上一页最后一行的值
-- 第 1 页
SELECT * FROM blog_post
ORDER BY publish DESC, id DESC
LIMIT 20;

-- 第 2 页：从那个值之后继续（索引直接定位）
SELECT * FROM blog_post
WHERE (publish, id) < ('2026-08-01 10:00', 12345)
ORDER BY publish DESC, id DESC
LIMIT 20;

注意右边用的是复合游标 (publish, id)，不是单独的 publish。原因正是 F-03：publish 可能并列，只用它做游标会在并列处跳过或重复记录。行值比较 (a, b) < (x, y) 是 PostgreSQL 支持的写法，能直接用上 (publish, id) 复合索引。

4.2 Django ORM 里怎么写

python
from django.db.models import Q

def get_page_after(cursor_publish=None, cursor_id=None, limit=20):
    qs = Post.published.order_by('-publish', '-id')
    if cursor_publish is not None:
        qs = qs.filter(
            Q(publish__lt=cursor_publish)
            | Q(publish=cursor_publish, id__lt=cursor_id)
        )
    # 多取一条判断有没有下一页，省掉 COUNT
    rows = list(qs[:limit + 1])
    has_next = len(rows) > limit
    rows = rows[:limit]
    next_cursor = (rows[-1].publish, rows[-1].id) if has_next and rows else None
    return rows, next_cursor

PostgreSQL 上还可以用行值比较，让数据库更容易走复合索引：

qs = qs.extra(where=["(publish, id) < (%s, %s)"], params=[cursor_publish, cursor_id])

extra() 是老 API 且官方不推荐，更现代的等价写法是用 django.db.models.expressions 里的 RowRange 或直接 RawSQL。多数场景下上面那个 Q 组合已经够快，先测再优化。

4.3 DRF 里一行就能换

python
from rest_framework.pagination import CursorPagination

class FeedPagination(CursorPagination):
    page_size = 20
    ordering = '-publish'        # 必须是稳定、带索引的排序
    cursor_query_param = 'cursor'


class PostViewSet(viewsets.ReadOnlyModelViewSet):
    pagination_class = FeedPagination

游标是 base64 编码的，客户端应当把它当成不透明字符串原样回传。编码不是为了安全（它可以被解开），而是为了明确「这是实现细节，别去解析它」——这样服务端将来换排序字段时不会破坏客户端。

4.4 键集分页的代价

能力OFFSET 分页键集分页
跳到任意第 N 页可以不行，只能一页页往前后走
显示「共 N 页 / 共 M 条」可以（代价是 COUNT）不行，除非额外查一次
深翻页性能线性退化常数
数据变动时的正确性会重复 / 漏项稳定
排序字段要求无（但应当唯一）必须唯一且带索引
能否任意换排序可以换排序等于换游标语义，旧游标失效

所以这不是「键集分页更好」，而是两者服务于不同的界面形态：需要页码、需要跳页、需要总数的传统列表页只能用 OFFSET；信息流、无限滚动、「加载更多」、后台批量导出则应该用键集。本仓库的 bookmarks 无限滚动是最典型的、也最该改的一处——它的界面从来没提供过跳页和总数，却付着 OFFSET 的全部代价。

五、上线前检查清单

  • 01分页的 queryset 必须有排序，且排序键必须唯一。最省事的做法是在末尾追加主键：order_by('-publish', '-id')。见 F-03。
  • 02排序键要有匹配的索引，复合排序就要复合索引，顺序和方向都要对上。
  • 03用 get_page() 代替手写三分支 try/except。语义相同，少三行且不会漏掉分支。
  • 04给最大页码设上限，或者干脆换键集分页。不设限等于给爬虫开了一个能拖垮数据库的接口。见 F-01。
  • 05无限滚动、信息流、「加载更多」一律用键集分页。这类界面既不需要总数也不需要跳页，用 OFFSET 是纯亏。见第四节。
  • 06不需要总数时就别 COUNT。「多取一条判断有无下一页」的成本几乎为零。见 F-05。
  • 07允许客户端调整每页条数时必须设上限（max_page_size）。本仓库 DRF 那处做对了。
  • 08分页链接要保留现有查询参数，别用裸的 ?page=N。见 F-08。
  • 09模板里传 page_obj 而不是 object_list。Django 模板对不存在的属性静默失败，这类错误不会进日志。见 F-04。
  • 10前端分页/滚动的失败路径要处理：解锁、回滚页码、给用户一个重试入口。见 F-06。
  • 11任何可能增长的列表都要分页，包括搜索结果、关联对象列表、导出接口。见 F-07。
  • 12游标对客户端是不透明字符串。编码它，并在文档里写明不要解析——这样你以后换排序字段时不会破坏调用方。
  • 13DRF 配 DEFAULT_PAGINATION_CLASS 全局默认值，别指望每个新视图都记得配。
  • 14用 assertNumQueries 给列表端点上查询数断言，顺便就能发现分页里混进来的 N+1。

六、同样的分页：Spring 与 Hono.js 怎么做

仍用本仓库的真实场景对比：「按发布时间倒序的文章列表，每页 20 条」，以及它在数据量变大后必然要面对的「换成游标分页」。

6.1 基础分页

Django 5.2 / DRF

三套并存：手写 Paginator、CBV 的 paginate_by、DRF 的 pagination_class。都是 OFFSET 系。

# 手写：Django 5.2 的 Paginator
paginator = Paginator(Post.objects.order_by('-publish', '-id'), 20)
page = paginator.get_page(request.GET.get('page'))
# get_page 已内建三分支容错，无需自己 try/except

# CBV：一个属性搞定
class PostListView(ListView):
    paginate_by = 20

# DRF
class StandardPagination(PageNumberPagination):
    page_size = 10
    page_size_query_param = 'page_size'
    max_page_size = 50
  • get_page() 内建容错，比本仓库的三分支 try/except 更省事
  • 分页与排序是两件独立的事，框架不会提醒你排序键必须唯一
  • CursorPagination 只在 DRF 里有，模板视图没有对应物

Spring Boot 3.x

Pageable / Page<T> 是框架一等公民，从 Controller 参数一路贯通到 Repository。

// Repository 直接接受 Pageable，返回 Page<T>
public interface PostRepository
        extends JpaRepository<Post, Long> {
    Page<Post> findByPublishedTrue(Pageable pageable);
}

@GetMapping("/api/posts")
Page<PostDto> list(
    @PageableDefault(size = 20, sort = "publish",
                     direction = DESC) Pageable pageable) {
    return repo.findByPublishedTrue(pageable)
               .map(mapper::toDto);
}
// GET /api/posts?page=1&size=20&sort=publish,desc
  • 排序作为参数随分页一起传递，两者天然绑在一起
  • Page<T> 带 count，Slice<T> 不带——一个类型切换就能省掉 COUNT
  • 分页参数的解析、校验、默认值全部由框架负责

Hono.js

没有任何分页抽象。查询参数校验交给 Zod，分页逻辑自己写。

// 全手写；用 Zod 校验分页参数
const Query = z.object({
  limit: z.coerce.number().min(1).max(50).default(20),
  cursor: z.string().optional(),
})

app.get('/api/posts', zValidator('query', Query),
  async (c) => {
    const { limit, cursor } = c.req.valid('query')
    const rows = await db.select().from(posts)
      .where(cursor ? lt(posts.publish, cursor) : undefined)
      .orderBy(desc(posts.publish), desc(posts.id))
      .limit(limit + 1)          // 多取一条判断有没有下一页

    const hasMore = rows.length > limit
    return c.json({
      items: rows.slice(0, limit),
      nextCursor: hasMore
        ? rows[limit - 1].publish : null,
    })
  })
  • 「多取一条判断有无下一页」是手写分页的标准技巧，省掉 COUNT
  • 游标天然就是键集式的——手写反而不容易掉进 OFFSET 的坑
  • 每个端点都要重写一遍，除非自己抽一个辅助函数

6.2 换成游标 / 键集分页

Django 5.2 / DRF

# DRF 内置游标分页，开箱即用
class FeedPagination(CursorPagination):
    page_size = 20
    ordering = '-publish'        # 必须是稳定且带索引的排序
    cursor_query_param = 'cursor'

class PostViewSet(viewsets.ReadOnlyModelViewSet):
    pagination_class = FeedPagination

# 响应里没有 count 字段，只有 next / previous 两个不透明游标
# 实测：单次请求 1 条 SQL，0 条 COUNT

DRF 的 CursorPagination 是三者里唯一开箱即用的游标实现，实测单请求 1 条 SQL、0 条 COUNT。

但它只服务于 DRF 视图。模板渲染的列表页（本仓库的 blog 和 bookmarks）要用键集分页，只能自己写 WHERE 条件。

Spring Boot 3.x

// Spring Data 没有内置游标分页。两个选择：

// ① Slice<T>：去掉 count 查询，但仍是 OFFSET
Slice<Post> findByPublishedTrue(Pageable pageable);

// ② 键集：自己写查询条件
@Query("SELECT p FROM Post p "
     + "WHERE p.publish < :cursor "
     + "ORDER BY p.publish DESC, p.id DESC")
List<Post> findAfter(@Param("cursor") Instant cursor,
                     Pageable limit);

// Spring Data 3.1+ 另有 ScrollPosition / keyset API：
Window<Post> findFirst20By(
    ScrollPosition position, Sort sort);

Slice<T> 是个很实用的中间态：仍是 OFFSET，但去掉了 COUNT 查询，改动成本只有一个返回类型。

Spring Data 3.1 起提供了 ScrollPosition / Window<T> 的键集 API，是三者里对键集分页支持最正式的。

Hono.js

// Hono 没有分页抽象，游标就是上面那段代码本身。
// 游标通常要编码，避免暴露内部字段：
const encode = (v: Date, id: number) =>
  btoa(JSON.stringify([v.toISOString(), id]))

const decode = (s: string) =>
  JSON.parse(atob(s)) as [string, number]

// 复合游标（值 + 主键）才能处理并列行：
.where(or(
  lt(posts.publish, pv),
  and(eq(posts.publish, pv), lt(posts.id, pid)),
))

游标要编码后再暴露，否则等于把内部排序字段和数据分布泄露给客户端。DRF 的游标是 base64 编码的，同理。

并列行必须用复合游标（排序值 + 主键）才能正确处理——这正是本文 F-03 讲的决胜键问题在游标场景下的对应版本。

三句话概括

  • Django 的分页覆盖面最广但最零散。它是三者里唯一同时照顾了「模板渲染的列表页」和「JSON API」的——paginate_by 一个属性就能给 ListView 分页，这在 Spring 和 Hono 里都没有对应物。代价是三套机制各自独立：Paginator、paginate_by、DRF 的 pagination_class 互不相通，本仓库就同时用了前两套的手写变体和第三套，四个地方写了四遍。而且排序和分页在 Django 里是完全独立的两件事，框架不会在你分页一个无序 queryset 时拦住你。
  • Spring 把排序绑进了分页契约里。Pageable 同时承载页码、页大小和排序，从 HTTP 参数一路传到 Repository，这个设计让「分页时忘了排序」几乎不可能发生。Page<T> 与 Slice<T> 的区分也很务实——想省掉 COUNT 只需改返回类型。3.1 起的 ScrollPosition 让键集分页也进了官方 API。
  • Hono 什么都不给，反而不容易写错。没有 Paginator 可以顺手一调，你必须自己想清楚排序键、游标编码、有没有下一页怎么判断——而认真想过这几件事的人，写出来的基本就是键集分页。这正是本文的核心观点：OFFSET 分页之所以到处都是，很大程度上是因为框架把它做成了阻力最小的那条路。
