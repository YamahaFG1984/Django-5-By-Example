00 · Overview

概述与设计目标

本设计文档面向 docs/blog-prd.md 中定义的 V1–V4 需求做详细落地，并为 V5–V8（RBAC、搜索升级、缓存/异步、开放 API）预留清晰的扩展点，避免后续迭代推倒重来。

设计原则

能放进数据库层解决的问题不写应用代码；能同步返回的响应不引入队列；能用 Django 内建能力表达的规则不引入第三方框架。

不做的事

本期不引入微服务拆分、不引入 Elasticsearch/Solr；搜索仍以 PostgreSQL 原生能力为主，个性化推荐（V8）留待有真实行为数据后再评估算法选型。

01 · System

总体架构

应用层保持无状态、可水平扩展；PostgreSQL 承担数据存储与部分搜索能力，Redis 同时承担缓存与 Celery 消息代理，异步任务与定时任务从请求路径中彻底剥离。

组件职责关键设计决策
NginxTLS 终止、静态/媒体文件直出、反向代理Django 只处理业务请求，不经手静态文件 I/O
Django 应用层业务逻辑、鉴权、序列化Gunicorn 多进程，容器内不持有本地状态，可任意扩缩容
PostgreSQL唯一数据源，含模糊搜索与全文检索pg_trgm + tsvector 双索引，见 §05
Redis缓存 + Celery 消息代理/结果后端按 db index 隔离缓存（db0）与队列（db1），互不干扰
Celery Worker/Beat邮件发送、定时发布、摘要生成与 Web 进程分开部署，慢任务不占用请求处理能力
对象存储封面图、正文图床通过 django-storages 接入，避免图片落在容器本地磁盘

02 · Data

数据模型设计

在现有 Post / Comment / Tag 基础上，补齐 RBAC 所需的角色关联、内容组织所需的分类、以及收藏与修订历史两类"轻量关联表"。

TSD 建议

自定义 User 模型必须在项目第一次 migrate 之前引入。《Two Scoops of Django》把这条列为最容易被忽视、但事后代价最高的决策——一旦有了历史数据，再从 auth.User 切到自定义模型需要手工搬迁用户表和所有外键，几乎等同于重建。本设计据此调整：不再单独设计 Profile（1:1 表），而是直接建立 accounts.User(AbstractUser)，把 bio、avatar 等资料字段并入同一张表，减少一次 join。这一步需要排在 V4 引入 RBAC 之前完成。

关键实体设计说明

实体设计要点对应能力
User自定义模型（继承 AbstractUser），不单独拆 Profile 表TSD 建议
Post状态机字段 + 分类（新增）+ 标签（沿用 taggit）+ 搜索向量列GeneratedField 自动维护 tsvector 列
Category自关联树形结构，最多建议 2 级，避免导航过深UniqueConstraint(fields=["slug","parent"])
Comment新增 parent_id 自关联支持楼中楼；active 默认值下推到数据库db_default=False，配合审核工作流
Bookmark纯粹的"用户收藏文章"关联，无自增 id 意义，直接用联合主键models.CompositePrimaryKey("user", "post")
PostRevision每次发布/编辑写入一条快照（JSON），支持回滚与审计TSD 建议：显式写入，不用 signal

class User(AbstractUser):
    bio = models.TextField(blank=True)
    avatar = models.ImageField(upload_to="avatars/", blank=True)

# mysite/settings.py
AUTH_USER_MODEL = "accounts.User"

# blog/models.py —— 关键片段
class Bookmark(models.Model):
    pk = models.CompositePrimaryKey("user", "post")
    user = models.ForeignKey(settings.AUTH_USER_MODEL, on_delete=models.CASCADE)
    post = models.ForeignKey("blog.Post", on_delete=models.CASCADE)
    created = models.DateTimeField(auto_now_add=True)

class PostQuerySet(models.QuerySet):
    # TSD 建议：把过滤逻辑写成可链式调用的 QuerySet，而不是塞在 Manager 方法里
    def published(self):
        return self.filter(status=Post.Status.PUBLISHED)

    def by_tag(self, tag_slug):
        return self.filter(tags__slug=tag_slug)

class Post(models.Model):
    ...
    objects = PostQuerySet.as_manager()
    search_vector = models.GeneratedField(
        expression=SearchVector("title", weight="A") + SearchVector("body", weight="B"),
        output_field=SearchVectorField(),
        db_persist=True,
    )

    def save(self, *args, **kwargs):
        # TSD 建议：显式调用，不用 post_save 信号——调用链在这里一眼可见
        is_update = self.pk and Post.objects.filter(pk=self.pk).exists()
        super().save(*args, **kwargs)
        if is_update:
            PostRevision.objects.create(post=self, snapshot=self.to_snapshot())

    class Meta:
        constraints = [
            models.UniqueConstraint(
                fields=["slug", "publish"],
                name="unique_slug_per_publish_date",
            )
        ]

调用 Post.objects.published().by_tag("django") 即可链式组合，比在 Manager 上堆叠专用方法更灵活（TSD 建议）；search_vector 由 GeneratedField 自动维护；修订记录改为在 save() 内显式创建。

03 · Access

RBAC 权限设计

沿用 Django 内建的 auth.Group / Permission 做角色级权限，行级（对象级）权限用 django-guardian 补充——避免自研一套权限框架。

角色可见范围关键权限典型场景
超级管理员全站is_superuser系统配置、用户与角色管理
主编全部文章/评论blog.publish_post
blog.moderate_comment		审核他人文章、下线违规内容
作者仅自己的文章blog.add_post
blog.change_post（对象级）		撰写草稿、编辑自己未发布/已发布内容
审核员评论队列blog.moderate_comment只处理评论审核，不接触文章发布
普通读者公开内容 + 自己的互动记录blog.add_comment评论、收藏、点赞
 
# blog/permissions.py —— 对象级权限校验
class PostEditPermission(PermissionRequiredMixin):
    permission_required = "blog.change_post"

    def has_permission(self):
        post = self.get_object()
        user = self.request.user
        if user.groups.filter(name="主编").exists():
            return True
        return post.author_id == user.id and super().has_permission()

主编拥有跨作者的编辑权限；普通作者仅当权限点 + 对象归属同时满足才放行。

设计取舍：不引入独立的 Role 模型，直接复用 Django Group——角色数量少（5 个）且不需要动态创建角色，用内建能力足够，避免过度设计。若未来角色需要按团队/项目动态创建，再评估自定义 Role 模型。

04 · Interface

URL 与 API 设计

前台页面沿用现有 FBV 路由；新增能力（收藏、点赞、开放 API）统一走 /api/v1/，使用 Django REST Framework，按角色收窄可见字段与可执行动作。

路径方法说明权限
/api/v1/posts/GET文章列表（分页、标签/分类筛选）公开
/api/v1/posts/{slug}/GET文章详情公开（已发布）/ 作者本人（草稿）
/api/v1/posts/{slug}/bookmark/POST · DELETE收藏 / 取消收藏登录用户
/api/v1/posts/{id}/comments/POST提交评论（进入待审核队列）登录用户
/api/v1/comments/{id}/moderate/PATCH审核通过 / 驳回审核员 / 主编
/api/v1/search/GET全文检索（见 §05）公开
 
# blog/api/viewsets.py
class PostViewSet(viewsets.ReadOnlyModelViewSet):
    serializer_class = PostSerializer
    lookup_field = "slug"

    def get_queryset(self):
        user = self.request.user
        if user.is_authenticated and user.groups.filter(name__in=["主编", "作者"]).exists():
            return Post.objects.filter(Q(status=Post.Status.PUBLISHED) | Q(author=user))
        return Post.published.all()

05 · Search

搜索设计

沿用现有 TrigramSimilarity 做标题模糊匹配，新增标题+正文的加权全文检索（SearchVector/SearchRank），两者互为补充：全文检索负责"语义相关"，Trigram 负责"拼写容错"。

09 · Quality

非功能指标

性能

列表/详情页 P95 < 200ms（命中缓存）；搜索接口 P95 < 400ms；数据库连接池上限按实例数 × 20 设置。

安全

评论内容强制转义防 XSS；表单 CSRF 保护默认开启；生产密钥全部走 Secret 管理，不落 git；RBAC 遵循最小权限原则。

可观测性

结构化日志（JSON）+ Sentry 错误采集；关键任务（邮件发送、定时发布）失败需触发告警，而非静默重试耗尽。

可维护性

所有 Schema 变更走 migration，大表加索引评估是否需要 CONCURRENTLY，避免锁表影响线上写入。

10 · Ship

部署架构

在现有 docker-compose 基础上拆分为独立服务，密钥改由环境变量注入而非硬编码，新增 worker/beat 两个长驻进程。

服务镜像/命令说明
webgunicorn mysite.wsgi多实例，滚动发布，健康检查探活
workercelery -A mysite worker独立扩缩容，和 web 分开部署
beatcelery -A mysite beat单实例，避免定时任务重复触发
db / redis托管服务优先生产环境建议使用云厂商托管实例，而非自建容器

TSD 建议

当前 mysite/settings.py 是单文件配置。改为 settings/base.py + dev.py + production.py 三段式，公共配置放 base，环境差异（DEBUG、ALLOWED_HOSTS、缓存/邮件后端）分别覆盖，全部敏感值继续走 python-decouple 读环境变量，不因为拆分文件就把密钥写死在某一段里。
