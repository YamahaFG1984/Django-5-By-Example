面向 Django 5.2。所有关于框架内部行为的论断均在本机实测验证，所有项目分析均来自本仓库 Chapter07、Chapter10~11、Chapter14~17 的真实代码。

本文结论速览

三条最重要的结论

  1. 本仓库的 cache_page 用法存在越权数据泄露，不是理论风险——我用仓库里的真实视图结构复现出：匿名访客可以完整读到已报名学员的付费课程页。根因是中间件顺序导致 Vary: Cookie 写得太晚，缓存 key 退化为「只按 URL 分片」。详见 缺陷 F-01。
  2. Redis 里装的东西，只有一小部分是「缓存」。 本仓库把 Django 缓存、Channels 通道层、推荐引擎、浏览计数四类负载塞进同一个 Redis 实例，但后三类丢失即数据丢失。给缓存配的 allkeys-lru 淘汰策略会静默吃掉它们。详见 第六节。
  3. 本项目的失效手段只有「等 TTL 到期」一种。 讲师改完课件，学生最长 15 分钟看不到更新，且三层缓存的 TTL 互相叠加。需要即时一致时应改用版本化 key。详见 第五节。

本文覆盖四部分：Django 5.2 下以 Redis 为后端的配置与选型、本仓库现有缓存代码的逐处分析、三个已验证的缺陷及修复，以及同样场景在 Spring 与 Hono.js 下的处理方式对比。所有涉及 Django 内部行为的论断都在本机 Django 5.2 上实测验证过，实测输出以绿色标题的终端块标注。

一、Django 5.2 + Redis：配置与连接

Django 从 4.0 起内置了 Redis 缓存后端（django.core.cache.backends.redis.RedisCache），5.2 沿用同一实现。它底层直接用 redis-py，不再需要 django-redis 第三方包——这是相比几年前教程的最大变化，本仓库 requirements.txt 里也只有 redis==5.0.4，没有 django-redis。

1.1 最小可用配置

本仓库 Chapter17/educa/educa/settings/base.py 里就是最小形态：

python
CACHES = {
    'default': {
        'BACKEND': 'django.core.cache.backends.redis.RedisCache',
        'LOCATION': 'redis://127.0.0.1:6379',
    }
}

CACHE_MIDDLEWARE_ALIAS = 'default'
CACHE_MIDDLEWARE_SECONDS = 60 * 15   # 站点级缓存的默认 TTL
CACHE_MIDDLEWARE_KEY_PREFIX = 'educa'

三个 CACHE_MIDDLEWARE_* 只对站点级缓存中间件生效，其中 KEY_PREFIX 也会被 cache_page 用上（它内部复用同一套 key 生成逻辑）。本项目的中间件是注释掉的，所以前两项目前只是摆设，第三项仍在 cache_page 的 key 里出现。

1.2 生产配置：把该显式声明的都写出来

最小配置能跑，但生产环境有六个字段值得显式写死，否则你依赖的都是隐式默认值：

python
import os

REDIS_URL = os.environ['REDIS_URL']          # 例如 redis://cache:6379/1

CACHES = {
    'default': {
        'BACKEND': 'django.core.cache.backends.redis.RedisCache',
        'LOCATION': REDIS_URL,

        # 默认 300 秒。不写 = 5 分钟，几乎肯定不是你想要的值，
        # 而且会让每一处不带 timeout 的 cache.set() 行为变得不可见。
        'TIMEOUT': 60 * 10,

        # 所有 key 自动加前缀，多个项目/环境共用一个 Redis 时必须设。
        'KEY_PREFIX': 'educa',

        # 改数据结构时把 VERSION + 1，旧 key 立刻全部失去引用，
        # 无需 FLUSHDB，也不会误删别人的数据。
        'VERSION': 1,

        'OPTIONS': {
            # 连接池上限。uWSGI/Gunicorn 每个 worker 进程一个池，
            # 总连接数 = worker 数 × max_connections，别超过 Redis 的 maxclients。
            'pool_class': 'redis.BlockingConnectionPool',
            'max_connections': 50,
            'timeout': 20,                    # 池满时的等待秒数

            # 网络层超时：不设的话 Redis 卡住会把 web worker 一起拖死。
            'socket_connect_timeout': 2,
            'socket_timeout': 2,
            'retry_on_timeout': True,
            'health_check_interval': 30,
        },
    }
}

关于 LOCATION 的两个细节：其一，URL 末尾的 /1 是 Redis 数据库编号，用它把缓存和其他负载分开（见第六节）。其二，LOCATION 可以传列表——Django 会把第一个当写节点，其余随机轮询作读节点：

'LOCATION': ['redis://primary:6379', 'redis://replica-1:6379', 'redis://replica-2:6379']

注意这只是客户端侧的读写分流，不做故障转移。真要高可用得上 Redis Sentinel 或 Cluster，而内置后端不支持——那时才需要回到 django-redis 或自己包一层。

1.3 序列化：默认是 pickle，这有代价

内置后端默认用 pickle 序列化，只有整数例外（保持原样存，这样 incr()/decr() 才能走 Redis 原生的原子命令）。这带来两个必须知道的后果：

  • 缓存里的数据不能被非 Python 程序读取。如果你的 Redis 还要给 Node 服务、监控脚本读，就得换 JSON 序列化器。
  • 反序列化 pickle 等于执行任意代码。这意味着 Redis 实例必须被当成可信内网组件对待——绝不能暴露公网、必须设 requirepass。任何能往你 Redis 写数据的人，都等于能在你的 web 进程里执行代码。
python
# 换成 JSON：跨语言可读，且反序列化不会执行代码
'OPTIONS': {
    'serializer': 'django.core.cache.backends.redis.RedisSerializer',  # 默认，pickle
    # 自定义 JSON 序列化器需自己实现 dumps/loads，
    # 代价是只能缓存 JSON 可表达的类型（QuerySet、model 实例就不行了）。
}

二、四个缓存层级与选型决策

Django 提供四个层级的缓存，区别在于请求生命周期里的拦截时机。越早拦截省得越多，但粒度越粗、越容易出错。

层级写法缓存的东西适合绝不要用在
① 站点级UpdateCacheMiddleware + FetchFromCacheMiddleware整个响应纯匿名的内容站、营销页任何有登录态的站点。本项目已注释停用，是对的
② 视图级@cache_page(ttl)整个响应对所有匿名访客一致的页面、公开 API响应内容随用户变化的视图——除非显式加 vary_on_cookie，见 F-01
③ 模板片段{% cache ttl name vary %}一段 HTML页面里「重且公共」的局部，如渲染开销大的内容块片段内含用户私有信息，且 vary 参数没带上用户标识
④ 低级 APIcache.get/set/get_or_set任意 Python 对象昂贵查询结果、外部 API 响应、计算结果——最安全，key 完全自己掌控；代价是视图和模板仍要执行

选型的一条实用原则

Two Scoops of Django 反复强调的一点在这里特别适用：缓存粒度应当与「这份数据对谁一致」精确对齐。问一个问题——「这份缓存内容，能不能原样给任何一个访客看？」

  • 能 → 上层级 ①②，省得最多。
  • 不能，但能给「同一类人」看 → 用层级 ③④，把区分维度显式写进 key（用户 id、课程 id、语言）。
  • 不能，且每个用户都不同 → 通常不该缓存整页，而是缓存那些跨用户共享的中间结果（层级 ④）。

本项目的 StudentCourseDetailView 属于第三类却用了第二类的手段，这正是 F-01 的来源。而 CourseListView 里的 cache.get/set 属于第一类用第四类手段，偏保守但安全——这个对比本身就是很好的教材。

3.1 educa：三层缓存叠在同一个页面上

第一层，整页缓存（students/urls.py）——注意 cache_page 是包在 as_view() 外面的，这是 CBV 的标准写法：

python
path(
    'course/<pk>/',
    cache_page(60 * 15)(views.StudentCourseDetailView.as_view()),
    name='student_course_detail',
),
path(
    'course/<pk>/<module_id>/',
    cache_page(60 * 15)(views.StudentCourseDetailView.as_view()),
    name='student_course_detail_module',
),

两条 URL 指向同一个视图，但 URL 不同 → 缓存 key 不同，这部分是对的。问题出在这个视图本身是 LoginRequiredMixin 且按用户过滤 queryset——见 F-01。

第二层，模板片段缓存（students/templates/students/course/detail.html）：

html
{% load cache %}
...
<div class="module">
  {% cache 600 module_contents module %}
    {% for content in module.contents.all %}
      {% with item=content.item %}
        <h2>{{ item.title }}</h2>
        {{ item.render }}
      {% endwith %}
    {% endfor %}
  {% endcache %}
</div>

缓存这一段是有道理的：item.render 会对每个内容项做一次 GenericForeignKey 解引用并渲染子模板，是这个页面上最贵的部分。但 vary 参数用了 module 对象本身——见 F-02。

第三层，低级 API（courses/views.py 的 CourseListView）：

python
def get(self, request, subject=None):
    subjects = cache.get('all_subjects')
    if not subjects:
        subjects = Subject.objects.annotate(total_courses=Count('courses'))
        cache.set('all_subjects', subjects)
    all_courses = Course.objects.annotate(total_modules=Count('modules'))
    if subject:
        subject = get_object_or_404(Subject, slug=subject)
        key = f'subject_{subject.id}_courses'
        courses = cache.get(key)
        if not courses:
            courses = all_courses.filter(subject=subject)
            cache.set(key, courses)
    else:
        courses = cache.get('all_courses')
        if not courses:
            courses = all_courses
            cache.set('all_courses', courses)
    return self.render_to_response({'subjects': subjects, 'subject': subject, 'courses': courses})

这一段有三点值得说：

  • 缓存 QuerySet 是可行的，但要理解发生了什么。 cache.set 会 pickle 这个 QuerySet，而 pickle 一个 QuerySet 会强制求值并把整个结果集连同 _result_cache 一起序列化。所以存进 Redis 的是全部行数据，不是那条 SQL。数据集大时这会是个不小的 value。
  • cache.set() 没传 timeout，走的是 CACHES['default']['TIMEOUT']；本项目没配 TIMEOUT，因此是 Django 的默认值 300 秒。这个「5 分钟」完全是隐式的，代码里一个字都看不到——正是 1.2 节建议显式写死 TIMEOUT 的原因。
  • if not subjects: 是个真实的坑——见 F-03。

3.2 bookmarks Ch07 与 myshop Ch10/11：这些不是缓存

这两处绕过 Django 缓存框架，直接用 redis-py，因为它们要的是 Redis 的数据结构（原子计数器、有序集合），而缓存框架只提供 key-value 存取：

python
# Chapter07/bookmarks/images/views.py
r = redis.Redis(host=settings.REDIS_HOST, port=settings.REDIS_PORT, db=settings.REDIS_DB)

def image_detail(request, id, slug):
    image = get_object_or_404(Image, id=id, slug=slug)
    total_views = r.incr(f'image:{image.id}:views')      # 原子自增
    r.zincrby('image_ranking', 1, image.id)              # 有序集合累加分值
    ...

def image_ranking(request):
    image_ranking = r.zrange('image_ranking', 0, -1, desc=True)[:10]
    image_ranking_ids = [int(id) for id in image_ranking]
    most_viewed = list(Image.objects.filter(id__in=image_ranking_ids))
    most_viewed.sort(key=lambda x: image_ranking_ids.index(x.id))   # 按 Redis 的顺序重排

最后那行 sort 是个值得记住的模式：filter(id__in=[...]) 返回的顺序由数据库决定，与 Redis 给出的排名顺序无关，所以必须在 Python 侧按原始 id 列表重新排一次。myshop 的 Recommender.suggest_products_for() 用了完全相同的手法。

python
# Chapter11/myshop/shop/recommender.py —— 用有序集合做「买了又买」
def products_bought(self, products):
    product_ids = [p.id for p in products]
    for product_id in product_ids:
        for with_id in product_ids:
            if product_id != with_id:
                r.zincrby(self.get_product_key(product_id), 1, with_id)

这些 key 里装的是业务数据，不是缓存。 image:*:views 是站点的浏览统计，product:*:purchased_with 是靠历史订单一单一单累积出来的推荐权重——两者都无法从数据库重建（订单表虽然还在，但需要重跑全量历史才能还原）。把它们和缓存放同一个 Redis 实例、又给这个实例配上 allkeys-lru，内存一紧张就会被静默淘汰，而且不会有任何报错。第六节给出隔离方案。

四、三个已验证的缺陷与修复

以下三条都在本机 Django 5.2 上用仓库的真实代码结构复现过，不是纸面推演。

F-01 cache_page 让匿名访客读到已报名学员的付费页 已复现 · 越权访问
位置
Chapter14~17/educa/students/urls.py
触发
任一已报名学员访问过课程页后的 15 分钟内，任何人访问同一 URL
影响
付费内容泄露；LoginRequiredMixin 与按学员过滤的 queryset 全部被绕过

根因。 cache_page 的 key 并不是只按 URL 算的，它还会把 Vary 响应头点名的那些请求头的值一起哈希进去。流程分两步：

关键在于 Vary: Cookie 这个头是谁、什么时候加上的。加它的是 SessionMiddleware.process_response()（只要 session 被读过就会加）。但响应阶段是由内向外回流的：cache_page 包在视图上，属于最内层，它执行 learn_cache_key() 的时刻，外层的 SessionMiddleware 还没来得及加 Vary。于是 Django 记下的 headerlist 是空的 []，最终 key 里那段本该区分用户的哈希，哈希的是一个空字符串。

实测 · Django 5.2 · 复刻 students 应用的视图结构
$ python3 t2.py
1. alice (enrolled)       -> 200 | [PAID CONTENT] Django Mastery ($99) / viewer=alice
2. mallory (NOT enrolled) -> 200 | [PAID CONTENT] Django Mastery ($99) / viewer=alice
3. anonymous (logged out) -> 200 | [PAID CONTENT] Django Mastery ($99) / viewer=alice

view actually rendered: 1 time(s) for 3 requests

三个不同身份，三次请求，视图只执行了一次——后两次直接从缓存返回了 Alice 的页面。未报名的 Mallory 本应得到 404，匿名访客本应被重定向到登录页。

修复。 让 Vary: Cookie 在 cache_page 记 key 之前 就存在，也就是把 vary_on_cookie 放在内层。装饰器的嵌套顺序在这里是决定性的，写反了完全无效：

✗ 无效：vary_on_cookie 在外层
# 响应回流顺序：view -> cache_page 记 key -> vary_on_cookie 加头
# 加头时 key 已经记完了，等于没加
path(
    'course/<pk>/',
    vary_on_cookie(
        cache_page(60 * 15)(View.as_view())
    ),
),
✓ 有效：vary_on_cookie 在内层
from django.views.decorators.vary import vary_on_cookie

# 响应回流顺序：view -> vary_on_cookie 加头 -> cache_page 记 key
path(
    'course/<pk>/',
    cache_page(60 * 15)(
        vary_on_cookie(View.as_view())
    ),
),
实测 · 同一份代码，仅调整装饰器嵌套顺序
$ python3 t4.py      # cache_page(vary_on_cookie(view))
1. alice (enrolled)       -> 200 | [PAID CONTENT] Django Mastery ($99) / viewer=alice
2. mallory (NOT enrolled) -> 404
3. anonymous (logged out) -> 302 | redirect->/accounts/login/?next=/course/1/

$ python3 t5.py      # 确认缓存本身仍然生效
alice 1st render count: 1 -> alice 2nd render count: 1 => CACHE HIT
bob (also enrolled) render count -> 2 => got his OWN entry
bob content: [PAID CONTENT] Django Mastery ($99) / viewer=bob

修好之后权限恢复正常，缓存也仍然有效——Alice 的第二次请求命中缓存，Bob 拿到属于自己的那一份。

但「修好了」不代表「应该这么用」。 按 Cookie 分片意味着缓存 key 哈希的是整个 Cookie 请求头。这有两个后果：每个登录用户各存一份整页副本，缓存体积随用户数线性膨胀；而且只要任何一个 Cookie 变了（CSRF token 轮换、新增一个统计 Cookie），key 就变了，旧副本立刻变成永远不会再被命中的垃圾，白占内存直到过期。

所以对这类「每个用户都不同」的页面，Two Scoops of Django 的建议是根本不要缓存整页，而是往下走一层：把页面里真正跨用户共享、且渲染昂贵的部分（这里就是模块内容 HTML）用片段缓存或低级 API 缓起来，用户相关的外壳每次照常渲染。本项目其实已经有这个片段缓存了（第二层），所以最干净的修法是直接删掉 cache_page，只保留下面两层。

F-02 模板片段缓存的 key 会跨课程碰撞 已复现 · 内容串号
位置
Chapter14~17/educa/students/templates/students/course/detail.html
触发
两门不同课程里，存在 order 与 title 都相同的模块（如两门课都有「0. Introduction」）
影响
A 课程的学员看到 B 课程的模块内容

根因。 {% cache 600 module_contents module %} 的 key 由 make_template_fragment_key() 生成，它对每个 vary 参数取的是 str(arg)：

python
# django/core/cache/utils.py（5.2 源码）
def make_template_fragment_key(fragment_name, vary_on=None):
    hasher = md5(usedforsecurity=False)
    if vary_on is not None:
        for arg in vary_on:
            hasher.update(str(arg).encode())     # ← 取的是 str()，不是主键
            hasher.update(b":")
    return TEMPLATE_FRAGMENT_KEY_TEMPLATE % (fragment_name, hasher.hexdigest())

而本项目的 Module.__str__ 返回的是 f'{self.order}. {self.title}'——课程之间完全可能重复：

python
class Module(models.Model):
    course = models.ForeignKey(Course, related_name='modules', on_delete=models.CASCADE)
    title = models.CharField(max_length=200)
    order = OrderField(blank=True, for_fields=['course'])

    def __str__(self):
        return f'{self.order}. {self.title}'     # 「0. Introduction」在每门课里都会出现

修复。 vary 参数改用主键，并把「内容何时变过」也编进去，顺带解决失效问题：

✗ 现状：按 str(module) 分片
{% cache 600 module_contents module %}
  ...
{% endcache %}
✓ 按主键分片
{% cache 600 module_contents module.id %}
  ...
{% endcache %}

更普适的一条规则：永远不要把模型实例直接当作 {% cache %} 的 vary 参数，因为它取的是 __str__，而 __str__ 是给人看的、随时可能被改、且几乎从不保证唯一。传 obj.pk，或者传一个你能控制的显式元组。

F-03 空结果永远不会被缓存，每次请求都打数据库 已确认 · 性能
位置
Chapter14~17/educa/courses/views.py · CourseListView.get()
触发
某个 subject 下暂时没有课程，或系统刚上线还没有任何 subject
影响
该 URL 的缓存完全失效，每次请求都执行一次 annotate 聚合查询

根因。 cache.get() 未命中时返回 None，但代码判断的是 if not subjects:。一个空的 QuerySet 是 falsy 的，于是「缓存里存着一个空结果」和「缓存未命中」这两种情况被混为一谈——空结果每次都被判定成未命中，重新查库、重新写入、下次再判定成未命中，无限循环。

✗ 现状：falsy 值与未命中不可区分
subjects = cache.get('all_subjects')
if not subjects:            # 空 QuerySet 也是 falsy
    subjects = Subject.objects.annotate(
        total_courses=Count('courses'))
    cache.set('all_subjects', subjects)
✓ 用 is None 精确判断未命中
subjects = cache.get('all_subjects')
if subjects is None:
    subjects = Subject.objects.annotate(
        total_courses=Count('courses'))
    cache.set('all_subjects', subjects, 60 * 10)

更简洁的写法是用 get_or_set()，它内部就是按「未命中」而非「falsy」判断的，还少一次往返：

python
subjects = cache.get_or_set(
    'all_subjects',
    lambda: Subject.objects.annotate(total_courses=Count('courses')),
    60 * 10,
)

这个坑在缓存代码里极其常见，因为 0、''、[]、False、空 QuerySet 全都是 falsy。凡是用 cache.get()，判断未命中一律写 is None——除非你能确定被缓存的值永远不可能是 falsy。

五、失效策略：本项目最薄弱的一环

Phil Karlton 那句老话——「计算机科学只有两个难题：缓存失效和命名」——在本项目里体现得很直接：整个 educa 没有任何一处主动清除缓存。唯一的失效手段是等 TTL 到期。

5.1 这在本项目意味着什么

讲师在管理后台改完一节课的内容后：模板片段缓存要 10 分钟才过期，外层整页缓存要 15 分钟才过期，而且外层没过期时，里层过没过期根本不重要——整页缓存直接返回旧 HTML，模板压根不会重新渲染。所以真实的陈旧窗口是最外层的 15 分钟。

对课件这种更新频率低、且晚几分钟看到也无所谓的内容，这个取舍是可以接受的，教材也明确是这么设计的。但如果换成「讲师发布了一条课程公告」，15 分钟的延迟就不可接受了。

5.2 三种做法的取舍

A · 纯 TTL（现状）

最简单，零额外代码。适用前提是业务能容忍最长一个 TTL 的陈旧。选 TTL 时别只想「多久算新鲜」，也要想「击穿时数据库扛不扛得住」——TTL 越短，缓存重建越频繁。

B · 写时主动失效

用信号在数据变更时精确删除对应的 key：

python
# courses/signals.py
from django.core.cache import cache
from django.db.models.signals import post_save, post_delete
from django.dispatch import receiver

from .models import Content, Module, Subject


@receiver([post_save, post_delete], sender=Content)
def invalidate_module_fragment(sender, instance, **kwargs):
    # 与模板里 {% cache 600 module_contents module.id %} 的 key 保持一致
    from django.core.cache.utils import make_template_fragment_key
    cache.delete(make_template_fragment_key('module_contents', [instance.module_id]))


@receiver([post_save, post_delete], sender=Subject)
def invalidate_subject_list(sender, **kwargs):
    cache.delete('all_subjects')

主动失效的三个陷阱。其一，QuerySet.update() 和 bulk_create() 不触发 post_save——本项目的 ModuleOrderView 用的正是 .update()，信号方案会漏掉它。其二，key 必须能从被改的对象反推出来，这就要求 key 的构造规则在模板和信号两处保持同步，改一处忘一处就会静默失效。其三，删除和写入之间存在竞态：删除后、新值写入前，可能有请求把旧值又读回来重新缓存。

C · 版本化 key（推荐）

不删任何东西，而是让 key 本身随数据变化。旧 key 立刻失去引用，由 Redis 的淘汰机制自然回收：

python
# 模型上加一个 updated 时间戳
class Module(models.Model):
    ...
    updated = models.DateTimeField(auto_now=True)

    @property
    def cache_version(self):
        return int(self.updated.timestamp())
html
{% cache 600 module_contents module.id module.cache_version %}
  ...
{% endcache %}

这个方案的好处是没有失效竞态，也不需要枚举所有写路径——只要数据变了，updated 就变，key 就变。代价是新旧两份内容会在 Redis 里短暂并存，多占一点内存，直到旧的被 TTL 或 LRU 清掉。

Django 的 CACHES['VERSION'] 提供了同样思路的全局版本：改数据结构时把它加一，所有旧 key 一次性失去引用，不需要 FLUSHDB，也不会误伤同一实例上的其他数据。

5.3 三个经典失效故障

现象成因应对
缓存穿透
查一个不存在的 key		查询结果为空，从不写入缓存，每次都打到数据库把「空结果」也缓存起来（用短 TTL），并用 is None 区分未命中——正是 F-03
缓存击穿
热点 key 到期瞬间		大量并发同时未命中，一起去重建同一份数据加分布式锁（cache.add() 天然是原子的，可当锁用），或让重建单例化
缓存雪崩
大批 key 同时到期		同一时刻批量写入的缓存，TTL 也在同一时刻集体过期TTL 加随机抖动，如 600 + random.randint(0, 120)
python
# 用 cache.add() 做重建锁：只有第一个请求能拿到锁去查库
def get_expensive_data(key):
    data = cache.get(key)
    if data is not None:
        return data
    lock_key = f'{key}:lock'
    if cache.add(lock_key, '1', 30):        # add 只在 key 不存在时成功，是原子的
        try:
            data = expensive_query()
            cache.set(key, data, 600 + random.randint(0, 120))   # 顺带抖动 TTL
        finally:
            cache.delete(lock_key)
        return data
    time.sleep(0.05)                        # 没抢到锁，短暂等待后重读
    return cache.get(key) or expensive_query()

六、把缓存和业务数据分开

本仓库 prod.py 把 CACHES 和 CHANNEL_LAYERS 指向了同一个 redis://cache:6379（都是默认的 db 0），而 myshop 的推荐引擎用 REDIS_DB = 1。这意味着一旦给这个实例配上适合缓存的淘汰策略，通道层数据会和缓存一起被淘汰。

6.1 为什么这件事容易被忽略

因为不会报错。Redis 在内存达到 maxmemory 时按策略淘汰 key，被淘汰的推荐权重、浏览计数只是「读出来是 0」，业务逻辑照常运行，只是数据悄悄归零了。等发现推荐结果变差时，历史数据已经找不回来了。

6.2 三种隔离方式，按推荐程度排序

方式做法评价
独立实例缓存一个 Redis，业务数据另一个最干净。淘汰策略、持久化配置、内存上限、监控指标全部可以独立设定，也便于缓存实例随时清空重建
同实例不同 dbredis://cache:6379/0 与 /1能防误删（FLUSHDB 只影响当前 db），但防不住淘汰——maxmemory-policy 是实例级的，allkeys-* 会跨所有 db 淘汰
同 db 靠前缀KEY_PREFIX 区分只解决命名冲突，不解决任何运维问题。当前项目基本处于这个状态

6.3 淘汰策略怎么选

bash
# 纯缓存实例：内存满了就按 LRU 淘汰，这正是我们想要的
maxmemory 2gb
maxmemory-policy allkeys-lru

# 存业务数据的实例：只淘汰显式设了过期时间的 key，
# 没设 TTL 的（推荐权重、浏览计数）永远不动；
# 内存真的满了宁可写入报错，也不要静默丢数据
maxmemory 1gb
maxmemory-policy volatile-lru      # 或 noeviction

noeviction 在内存满时会让写命令直接返回错误。听起来很糟，但对业务数据来说，一个响亮的错误远好过静默的数据丢失——前者会立刻触发告警，后者可能几个月都没人发现。

6.4 顺带一提：session 后端

把 session 也放 Redis 是常见做法，但要注意 django.contrib.sessions.backends.cache（纯缓存）和 cached_db（缓存 + 数据库兜底）的区别：前者在 Redis 被清空或 key 被淘汰时会让所有用户瞬间登出。如果用纯 cache 后端，就更不能和会被 FLUSHDB 的缓存共用实例。

七、上线前检查清单

  • 01显式写 TIMEOUT。不写就是 300 秒，而这个数字在代码里完全不可见，读代码的人无从得知。
  • 02设 KEY_PREFIX 和 VERSION。前者隔离环境（dev/staging/prod 共用一个 Redis 是很常见的），后者让你能在改缓存结构时一键作废旧数据。
  • 03设 socket 超时。不设的话 Redis 一卡，web worker 会跟着一起挂住，缓存反而成了可用性的单点。
  • 04缓存不可用时应用要能降级。Redis 挂掉应该是「变慢」，不是「500」。内置后端在连接失败时会抛异常，关键路径需要自己包 try/except 兜底。
  • 05用 is None 判断未命中，不要用 if not value。见 F-03。
  • 06任何 cache_page 都要先回答「这个响应能给任何人看吗」。答案是否定的就别用，或至少加内层 vary_on_cookie。见 F-01。
  • 07{% cache %} 的 vary 参数传 pk，不传模型实例。见 F-02。
  • 08缓存和业务数据分实例，至少要保证淘汰策略不会误伤业务数据。见第六节。
  • 09TTL 加随机抖动，避免批量写入的缓存集体到期造成雪崩。
  • 10Redis 必须设密码且不暴露公网。默认 pickle 序列化意味着能写你 Redis 的人 = 能在你的 web 进程里执行代码。
  • 11监控命中率。redis-cli INFO stats 里的 keyspace_hits / keyspace_misses。命中率长期偏低说明 key 设计有问题（比如 F-01 修复后按 Cookie 分片就会导致这种情况）。
  • 12别缓存已经很快的东西。Two Scoops 的原话是先测量再缓存——缓存本身有序列化、网络往返和一致性成本，给一个 2ms 的查询加缓存往往是净亏。

八、同样的场景：Spring 与 Hono.js 怎么做

用同一个具体场景横向对比：「课程详情页，内容对所有人一致，渲染昂贵，希望缓存 10 分钟」，以及它的变体「同一个页面，但要按登录用户区分」。

8.1 基础缓存：把一次昂贵查询的结果缓起来

Django 5.2

装饰器（视图级）或命令式 API（低级）。缓存后端由 CACHES 全局配置决定，业务代码里看不到 Redis。

from django.core.cache import cache

def get_course(pk):
    key = f'course:{pk}'
    course = cache.get(key)
    if course is None:
        course = Course.objects.get(pk=pk)
        cache.set(key, course, 600)
    return course

# 或一行搞定
course = cache.get_or_set(
    f'course:{pk}',
    lambda: Course.objects.get(pk=pk),
    600)
  • 序列化默认 pickle，可以直接缓存模型实例乃至 QuerySet
  • 失效要自己写，框架不提供任何声明式支持

Spring Boot 3.x

声明式注解，靠 AOP 代理拦截方法调用，缓存逻辑完全不进业务代码。

@Service
public class CourseService {

  @Cacheable(value = "courses", key = "#id")
  public Course getCourse(Long id) {
      return repo.findById(id).orElseThrow();
  }

  @CacheEvict(value = "courses", key = "#c.id")
  public Course update(Course c) {
      return repo.save(c);
  }
}
  • @Cacheable / @CachePut / @CacheEvict 覆盖读、写、失效
  • 失效是声明式的，这是相对 Django 最大的优势
  • 依赖 AOP 代理：同类内部自调用不走缓存，经典陷阱

Hono.js

没有内置的数据缓存抽象，一切手写。边缘环境通常配 Upstash 这类走 HTTP 协议的 Redis。

import { Redis } from '@upstash/redis/cloudflare'

app.get('/course/:id', async (c) => {
  const redis = Redis.fromEnv(c.env)
  const id = c.req.param('id')
  const key = `course:${id}`

  const hit = await redis.get(key)
  if (hit) return c.json(hit)

  const course = await db.course(id)
  await redis.set(key, course, { ex: 600 })
  return c.json(course)
})
  • 值必须是 JSON，没有 pickle 那种「什么都能存」
  • Serverless 无常驻连接池，所以走 HTTP 而非 TCP 长连接

8.2 整页 / 响应级缓存与「按用户区分」

Django 5.2

path('course/<pk>/',
  cache_page(600)(
    vary_on_cookie(View.as_view())
  ))

用 Vary 响应头驱动分片，装饰器嵌套顺序决定成败——正是 F-01 的坑。

框架不会警告你把 cache_page 加到了一个 LoginRequiredMixin 视图上。

Spring Boot 3.x

@Cacheable(
  value = "coursePages",
  key = "{#id, authentication.name}")
public String renderPage(Long id) { ... }

用户维度是显式写进 SpEL key 的，读代码时一眼能看出这份缓存按什么分片——比 Django 依赖隐式 Vary 头透明得多，也更难写错。

HTTP 层缓存另有 CacheControl 与 ShallowEtagHeaderFilter，与数据缓存是两套独立机制。

Hono.js

import { cache } from 'hono/cache'

app.get('/course/*', cache({
  cacheName: 'courses',
  cacheControl: 'max-age=600',
}))

内置 cache() 中间件走的是 Web Cache API（Cloudflare Workers / Deno），不是 Redis；Node 上没有 caches 全局对象，用不了。

它按 URL 缓存，没有 Vary 那套自动机制——要按用户区分只能自己拼 key，或干脆别用这个中间件。

三句话概括

  • Spring 的强项是声明式失效和显式 key。@CacheEvict 让「什么时候该清缓存」和业务方法写在一起，SpEL key 则强迫你把分片维度写明白——本文的 F-01 与 F-02 在 Spring 的写法下都不容易发生。代价是 AOP 代理的自调用陷阱，以及注解背后到底发生了什么不够直观。
  • Django 的强项是分层完整、开箱即用，尤其模板片段缓存这一层，Spring 和 Hono 都没有对应物，而它恰恰是「页面大部分公共、小部分私有」这类场景最合适的工具。弱点是失效全靠手写，且 Vary 驱动的隐式分片容易踩坑。
  • Hono 的定位根本不同。它假设你在边缘运行，首选是 CDN / Web Cache API 这类离用户更近的缓存，而不是回源到 Redis；确实需要共享状态时，因为 Serverless 没有常驻连接池，走 HTTP 协议的 Redis（Upstash）才是常态。它什么抽象都不给你，好处是没有隐式行为可踩，坏处是每个缓存点都得自己想清楚 key、TTL 和失效。
