面向 Django 5.2 + Celery 5.4。所有关于框架行为的论断均在本机实测验证，代码分析来自本仓库 Chapter08~11 的 myshop 与 Chapter16~17 的 educa。

本文结论速览

三条最重要的结论

  1. 本仓库的 Celery 从来没有真正跑起来过。 四章 settings.py 里一个 CELERY_* 配置都没有，broker_url 解析为 None，实际落到默认的 amqp://guest:**@localhost:5672//；而 requirements.txt 装的是 redis，四章 docker-compose.yml 里既没有 broker 服务也没有 worker 服务。详见 F-01。
  2. .delay() 是同步的网络调用，它失败会让整个结算流程 500。 实测 broker 不可达时 .delay() 阻塞 610 ms 后抛 OperationalError——而此时订单已写库、购物车已清空、支付页面拿不到。详见 F-02。
  3. Stripe webhook 没有幂等守卫，重投一次就把副作用翻倍。 实测同一 event 重投 3 次：推荐分数变成 3（应为 1），发票邮件任务派发 3 次（应为 1）。而 .delay() 失败本身就会导致 500 → 触发 Stripe 重投，两个缺陷会互相放大。详见 F-03。

本文结构与前三篇指南一致：先讲 Celery 的构成与本仓库的接线现状，再逐处分析仓库里的异步代码，然后是九个已验证的问题及修复、可靠性专题，最后是上线清单与 Spring / Hono.js 对比。所有关于 Celery 行为的论断都在本机 Celery 5.4.0 + Django 5.2 上实测验证，实测输出以绿色标题的终端块标注。

一个测量环境的说明：本机恰好有进程监听 5672 端口，直接调 .delay() 反而会「成功」——这是环境巧合，不是仓库配置正确。下文所有关于「broker 不可达」的实测，都是把 broker 显式指向一个确定无人监听的端口来模拟仓库 docker-compose 的真实情形（compose 里根本没有 broker 服务）。这一点我在测试里做了区分，不想把环境噪音当成结论。

一、Celery 的四个部分与本仓库的接线现状

1.1 代码层面：写得是对的

python
# myshop/celery.py
import os
from celery import Celery

os.environ.setdefault('DJANGO_SETTINGS_MODULE', 'myshop.settings')

app = Celery('myshop')
app.config_from_object('django.conf:settings', namespace='CELERY')
app.autodiscover_tasks()
python
# myshop/__init__.py —— 让 Django 启动时就加载 Celery app
from .celery import app as celery_app

__all__ = ['celery_app']

这两段是 Celery 官方推荐的标准接线，仓库写得完全正确。namespace='CELERY' 的意思是：到 Django settings 里去找所有 CELERY_ 开头的配置项，去掉前缀后作为 Celery 配置。autodiscover_tasks() 会自动扫描每个 app 下的 tasks.py。

1.2 配置层面：什么都没有

实测 · 照抄仓库配置后解析出的实际值
settings 里的 CELERY_BROKER_URL : (不存在)

实际连接地址                    : amqp://guest:**@localhost:5672//

因为一个 CELERY_* 都没有，Celery 全部用默认值。默认 broker 是 RabbitMQ 的 amqp://localhost:5672——而仓库既没装 RabbitMQ，requirements.txt 里装的是 redis==5.0.4。

这不是「配置错了」，而是「配置根本不存在」。 Chapter08 引入 Celery，Chapter09~11 一直在用（新增了 payment_completed 任务），但四章的 settings.py 里始终没有 CELERY_BROKER_URL，四章的 docker-compose.yml 里始终没有 broker 服务、没有 worker 服务。flower==2.0.1 也躺在 requirements.txt 里从未被接线——没有对应的 compose 服务，也没有任何文档提到它。

书里是让读者在本机手动装 RabbitMQ 并手动起 worker 的，这在教学上说得通；但如果照着 docker-compose up 跑，异步任务这条链路是断的。

用 Redis 还是 RabbitMQ 做 broker？ Redis 部署简单、延迟低，缺点是它不是为消息队列设计的——没有原生的消息确认与持久化保证，worker 崩溃时靠 visibility_timeout 兜底，配置不当会导致任务重复执行。RabbitMQ 有完整的 ack / 死信 / 优先级机制，代价是多一个中间件要运维。教学项目和中小流量用 Redis 完全够；订单、支付这类丢一条就是事故的任务，RabbitMQ 更稳妥。而本仓库把 Redis 同时当缓存、通道层、推荐引擎存储用（见缓存指南第六节），再叠一个 broker 上去，就更该考虑拆实例了。

二、本仓库异步代码逐处分析

2.1 两个 Celery 任务

python
# orders/tasks.py
@shared_task
def order_created(order_id):
    order = Order.objects.get(id=order_id)
    subject = f'Order nr. {order.id}'
    message = (f'Dear {order.first_name},\n\n'
               f'You have successfully placed an order.'
               f'Your order ID is {order.id}.')
    mail_sent = send_mail(subject, message, 'admin@myshop.com', [order.email])
    return mail_sent
python
# payment/tasks.py
@shared_task
def payment_completed(order_id):
    order = Order.objects.get(id=order_id)
    email = EmailMessage(f'My Shop - Invoice no. {order.id}', ..., [order.email])
    html = render_to_string('orders/order/pdf.html', {'order': order})
    out = BytesIO()
    stylesheets = [weasyprint.CSS(finders.find('css/pdf.css'))]
    weasyprint.HTML(string=html).write_pdf(out, stylesheets=stylesheets)   # CPU 密集
    email.attach(f'order_{order.id}.pdf', out.getvalue(), 'application/pdf')
    email.send()

两处写得对的地方，值得先肯定：

  • 用 @shared_task 而不是 @app.task。前者不绑定具体的 Celery app 实例，任务所在的 app 可以被独立复用，这是可重用 Django app 的标准写法。
  • 参数传 order_id 而不是 order 对象。这是异步任务最重要的一条纪律：任务参数要经过序列化跨进程传递，传 ORM 对象既会失败（或退化成 pickle，带来安全问题），也会让 worker 拿到一份过期的快照。传 id、由 worker 自己去查最新状态，才是对的。

问题在于任务的可靠性配置（F-05）和 payment_completed 里 WeasyPrint 的资源开销（F-06）。

2.3 一个管理命令

python
# students/management/commands/enroll_reminder.py
def handle(self, *args, **options):
    emails = []
    subject = 'Enroll in a course'
    date_joined = timezone.now().today() - datetime.timedelta(days=options['days'] or 0)
    users = User.objects.annotate(
        course_count=Count('courses_joined')
    ).filter(course_count=0, date_joined__date__lte=date_joined)
    for user in users:
        message = f"""Dear {user.first_name}, We noticed that you didn't enroll..."""
        emails.append((subject, message, settings.DEFAULT_FROM_EMAIL, [user.email]))
    send_mass_mail(emails)
    self.stdout.write(f'Sent {len(emails)} reminders')

这是仓库里唯一一处「批量后台作业」，但它不是 Celery 任务，而是一个需要外部调度器（cron / systemd timer）来触发的管理命令——而仓库里没有任何调度配置，没有 crontab、没有 Celery Beat、docker-compose 里也没有对应服务。它写好了但没有任何东西会去执行它。

命令本身还有三个问题：时区处理（F-07）、缺省参数的危险语义（F-08）、以及无批处理无幂等（F-09）。

2.4 另一种异步：educa 的 Channels 消费者

python
# chat/consumers.py
class ChatConsumer(AsyncWebsocketConsumer):
    async def receive(self, text_data):
        message = json.loads(text_data)['message']
        now = timezone.now()
        # 先广播给房间里所有人
        await self.channel_layer.group_send(
            self.room_group_name,
            {'type': 'chat_message', 'message': message,
             'user': self.user.username, 'datetime': now.isoformat()},
        )
        # 再落库
        await self.persist_message(message)

这是完全不同的一种「异步」：不是把工作挪出请求周期，而是让连接活得比请求久。它用 channels_redis 做通道层，和缓存共用同一个 Redis 实例。

这里有一个顺序问题：消息先 group_send 广播出去，再 persist_message 落库。如果 acreate 失败（数据库不可用、字段超长），房间里所有人已经看到了这条消息，但它并没有被保存——刷新页面后消息就消失了，而发送者完全不知情。更稳妥的顺序是先落库再广播，或者至少在落库失败时向发送者回一条错误。

另外 connect() 里只取了 self.scope['user'] 和课程 id，没有校验这个用户是否报名了这门课——配对的 HTTP 视图是有这个检查的，WebSocket 这一侧漏掉了。这一点在 educa 深读笔记的 Chapter16 部分详细讨论过，属于鉴权问题而非任务问题，本文不展开。

F-02.delay() 是同步网络调用，broker 故障会让结算流程 500已实测 · 可用性
位置
orders/views.py · order_create
触发
broker 不可达、网络抖动、broker 过载
影响
订单已写库、购物车已清空，但用户拿到 500 且进不了支付页面
实测 · broker 指向无人监听的端口（模拟 compose 的真实情形）
order_created.delay(42) 抛出 OperationalError
  [Errno 111] Connection refused
耗时 610 ms —— 这段时间用户的结算请求一直挂着，最后收到 500

很多人对 .delay() 的误解就在这里：它的名字听起来像「稍后执行」，但把消息发到 broker 这个动作本身是同步的、阻塞的、会失败的。异步的是任务的执行，不是任务的投递。

修复思路有三层，按投入从低到高：

✗ 现状：派发失败 = 结算失败
cart.clear()
order_created.delay(order.id)
request.session['order_id'] = order.id
return redirect('payment:process')
✓ 最低成本：派发失败不阻断主流程
cart.clear()
try:
    order_created.delay(order.id)
except OperationalError:
    # 邮件没发出去不该让用户付不了款
    logger.exception('order_created dispatch failed', extra={'order_id': order.id})
request.session['order_id'] = order.id
return redirect('payment:process')
python
# 更稳妥：给 broker 连接设超时，别让它拖着请求
CELERY_BROKER_TRANSPORT_OPTIONS = {
    'socket_timeout': 2,
    'socket_connect_timeout': 2,
    'retry_on_timeout': False,
}
CELERY_BROKER_CONNECTION_RETRY_ON_STARTUP = False
CELERY_BROKER_CONNECTION_MAX_RETRIES = 0

最彻底的方案是 transactional outbox：把「要发的任务」和业务数据写进同一个数据库事务（一张 outbox 表），再由一个独立的轮询进程把 outbox 里的记录投递到 broker。这样派发不再依赖 broker 当时是否可用，也天然解决了 F-04 的事务时序问题。代价是多一张表和一个投递进程，适合订单、支付这类不容许丢失的场景。

F-03Stripe webhook 没有幂等守卫，重投一次副作用就翻倍已实测 · 正确性
位置

触发
Stripe 重投同一个 event（超时、5xx、网络问题都会触发）
影响
推荐分数被重复累加；发票邮件重复发送给客户
实测 · 同一 event 重投 3 次
=== A) 现状 ===
  推荐分数 scores[(10,20)] = 3   <- 应该是 1
  发票邮件任务派发次数      = 3   <- 应该是 1

=== B) 加一个幂等守卫后 ===

✗ 现状：无条件执行全部副作用

✓ 用已有状态做幂等守卫

    # 这个 event 已经处理过了
    return HttpResponse(status=200)

order.paid = True
order.stripe_id = session.payment_intent
order.save()

products = Product.objects.filter(id__in=product_ids)
Recommender().products_bought(products)
transaction.on_commit(
    lambda: payment_completed.delay(order.id))
python
# 更严谨：按 Stripe 的 event.id 去重，能挡住「同一订单的不同事件被重投」
class ProcessedWebhookEvent(models.Model):
    event_id = models.CharField(max_length=255, unique=True)
    created = models.DateTimeField(auto_now_add=True)

# 处理入口
_, created = ProcessedWebhookEvent.objects.get_or_create(event_id=event.id)
if not created:
    return HttpResponse(status=200)     # 已处理，直接确认

unique=True 加 get_or_create 把去重下沉到数据库的唯一约束上，即使两个 webhook 请求并发到达也只有一个能建成记录。仅靠 if order.paid 在高并发下仍有竞态窗口。

F-04任务派发没有与事务提交对齐已实测 · 正确性
位置
orders/views.py、payment/webhooks.py
触发
一旦按最佳实践给下单流程加上 transaction.atomic() 就会立刻显现
影响
任务已入队但事务回滚 → worker 拿到不存在的 order_id

当前代码没有用 transaction.atomic()，所以每次 save() 都自动提交，这个问题暂时不显现。但这本身也是个问题——order.save() 和后面 N 条 OrderItem.objects.create() 不在同一个事务里，中途失败会留下没有明细的残缺订单。

而一旦你把它们包进 atomic()（这是正确的做法），.delay() 就会在事务提交之前执行：

实测 · 用独立数据库连接扮演 worker
=== 仓库写法：delay 在 atomic 事务内部 ===
  worker 在派发瞬间查到的是      : Order.DoesNotExist
  事务回滚后这条订单还存在吗      : False
  worker 稍后重试时查到的是      : Order.DoesNotExist
  -> 任务已入队，订单却没了。worker 无论何时执行都拿不到这条订单。

=== 正确写法：transaction.on_commit ===
  回滚场景：派发次数 = 0（没有派发，正确）
  成功场景：派发次数 = 1，worker 查到 = d@x.com
✗ 事务内直接 delay
with transaction.atomic():
    order = form.save()
    for item in cart:
        OrderItem.objects.create(order=order, ...)
    order_created.delay(order.id)   # 提交前就派发了
✓ transaction.on_commit
from django.db import transaction

with transaction.atomic():
    order = form.save()
    for item in cart:
        OrderItem.objects.create(order=order, ...)
    transaction.on_commit(
        lambda: order_created.delay(order.id))

on_commit 注册的回调只在最外层事务提交成功后执行；事务回滚则回调被丢弃。它在没有显式事务时会立即执行，所以无脑加上是安全的——这也意味着你可以现在就在仓库代码里加，不必等到引入 atomic。

F-05任务的可靠性配置全部是默认值：崩溃即丢、失败无声已实测 · 可靠性

两个 @shared_task + 全局 Celery 配置
触发
worker 被 OOM kill、部署时被 SIGKILL、SMTP 临时故障
影响

实测 · 仓库采用的全是 Celery 默认值

from django.core.mail import get_connection, send_mass_mail

@shared_task(acks_late=True, soft_time_limit=600)
def enroll_reminder(days=30, batch_size=500):
    cutoff = timezone.now() - datetime.timedelta(days=days)
    qs = (User.objects
          .annotate(course_count=Count('courses_joined'))
          .filter(course_count=0,
                  date_joined__lte=cutoff,
                  profile__enroll_reminder_sent_at__isnull=True)   # 幂等：只发没发过的
          .order_by('id'))

    sent = 0
    while True:
        batch = list(qs[:batch_size])          # 每轮重新取，已标记的自动排除
        if not batch:
            break
        messages = [(SUBJECT, render_message(u), settings.DEFAULT_FROM_EMAIL, [u.email])
                    for u in batch]
        connection = get_connection()          # 一批共用一条 SMTP 连接
        send_mass_mail(messages, connection=connection)
        Profile.objects.filter(user__in=batch).update(
            enroll_reminder_sent_at=timezone.now())
        sent += len(batch)
    return sent

四、可靠性：投递语义与幂等

4.1 没有「恰好一次」

分布式消息系统只有两种现实可选的投递语义：

语义怎么来的后果Celery 里的开关
至多一次
at-most-once		取走消息就确认，然后再执行worker 崩溃 → 任务丢失acks_late=False（默认，本仓库现状）
至少一次
at-least-once		执行完成才确认worker 崩溃 → 任务重复执行acks_late=True

「恰好一次」在跨进程、跨网络的场景下无法真正实现——你能做到的是「至少一次投递 + 幂等执行」，两者合起来在效果上等价于恰好一次。所以打开 acks_late 的同时，必须让任务本身幂等。

4.2 怎么让任务幂等

python
# 方案一：用业务状态做守卫（最简单，够用于大多数场景）
@shared_task(acks_late=True)
def order_created(order_id):
    order = Order.objects.filter(id=order_id).first()
    if order is None or order.confirmation_sent_at:
        return 'skipped'
    send_mail(...)
    Order.objects.filter(id=order_id).update(confirmation_sent_at=timezone.now())
python
# 方案二：用数据库唯一约束兜住并发（防得住同时到达的两个副本）
class SentNotification(models.Model):
    order = models.ForeignKey(Order, on_delete=models.CASCADE)
    kind = models.CharField(max_length=32)
    class Meta:
        constraints = [
            models.UniqueConstraint(fields=['order', 'kind'], name='uniq_order_kind')
        ]

@shared_task(acks_late=True)
def order_created(order_id):
    try:
        with transaction.atomic():
            SentNotification.objects.create(order_id=order_id, kind='created')
    except IntegrityError:
        return 'already sent'        # 另一个副本抢先了
    send_mail(...)

方案二有一个细节值得注意：先占坑再发邮件。如果反过来（先发邮件再记录），在两者之间崩溃就会重复发送。先占坑的代价是——万一发送失败，坑已经占了，需要在异常处理里把记录删掉，或者接受「宁可漏发不可重发」。选哪种取决于业务：营销邮件宁可漏发，支付凭证宁可重发。

4.3 失败之后去哪里

重试耗尽的任务不该无声消失。Celery 没有内建死信队列，常见做法是挂 on_failure 钩子：

python
class TrackedTask(Task):
    def on_failure(self, exc, task_id, args, kwargs, einfo):
        FailedTask.objects.create(
            task_name=self.name, task_id=task_id,
            args=repr(args), kwargs=repr(kwargs),
            traceback=str(einfo), failed_at=timezone.now(),
        )
        # 同时推给错误监控（Sentry 等）
        logger.error('task failed permanently: %s', self.name,
                     extra={'task_id': task_id}, exc_info=exc)


@shared_task(base=TrackedTask, bind=True, autoretry_for=(Exception,),
             retry_backoff=True, max_retries=5, acks_late=True)
def order_created(self, order_id):
    ...

有了这张表，你既能查「今天有多少任务彻底失败了」，也能做人工重放。没有结果后端 + 没有失败记录 = 任务失败在系统里不留任何痕迹，这正是本仓库当前的状态。

4.4 一条实用的自查清单

给每个准备写成异步任务的操作，问四个问题：

  • 它执行两次会怎样？ 不能接受就要做幂等。
  • 它一次都没执行会怎样？ 不能接受就要 acks_late + 重试 + 失败记录。
  • 它依赖的数据在执行时还在吗？ 传 id 不传对象，并在任务里处理「对象已删除」。
  • 它最坏要跑多久？ 据此设 soft_time_limit，并决定要不要单独一个队列。

五、上线前检查清单

  • 01显式配置 CELERY_BROKER_URL。不配就是 amqp://localhost，而你多半没有跑 RabbitMQ。见 F-01。
  • 02docker-compose 里要有 worker 服务。任务代码写完不等于有人执行它。
  • 03只用 json 序列化：CELERY_ACCEPT_CONTENT = ['json']。pickle 反序列化等于执行任意代码，能往 broker 写数据的人就能拿到你的 worker。
  • 04任务参数传 id，不传 ORM 对象。本仓库这一点做对了。
  • 05派发用 transaction.on_commit 包一层。没有事务时它会立即执行，所以无脑加是安全的。见 F-04。
  • 06.delay() 失败不该阻断主流程。它是同步网络调用，会失败；用 try/except 兜住并记录。见 F-02。
  • 07给 broker 连接设短超时，别让一次 broker 抖动把 web 进程拖住几秒。
  • 08开 acks_late，同时把任务写成幂等的。两者是配套的，只开一个更糟。见第四节。
  • 09声明 autoretry_for + retry_backoff + retry_jitter。没有 jitter 的重试会在故障恢复瞬间形成风暴。
  • 10设 soft_time_limit 和 time_limit。不设的话一个卡住的任务能永久占用一个 worker 槽位。
  • 11重任务单独队列、单独 worker，并配 --max-tasks-per-child 缓解内存泄漏。见 F-06。
  • 12失败要留痕：on_failure 写库 + 推错误监控。失败无声比失败本身更可怕。
  • 13Webhook 处理函数必须幂等，最好按外部 event id 去重并落到数据库唯一约束上。见 F-03。
  • 14Beat 只能跑一个实例，多副本会让每个定时任务被派发多次。
  • 15批量作业要分批，别把整张表读进内存，也别在一次 SMTP 会话里投递上万封邮件。见 F-09。
  • 16会产生外部副作用的管理命令，参数要么必填、要么默认值保守，并提供 --dry-run。见 F-08。

六、同样的异步任务：Spring 与 Hono.js 怎么做

仍用本仓库的真实场景对比：「下单成功后发送确认邮件，不阻塞用户拿到支付页面」，以及它在生产环境必然要面对的「失败要重试、要能查、要有兜底」。

6.1 派发一个后台任务

Django + Celery 5.4

任务是独立进程，通过消息队列解耦。Django 本身不提供任何后台任务能力，Celery 是事实标准。

# tasks.py —— 本仓库的写法
from celery import shared_task

@shared_task
def order_created(order_id):        # 传 id，不传 ORM 对象（正确）
    order = Order.objects.get(id=order_id)
    send_mail(...)

# 视图里派发
from django.db import transaction

with transaction.atomic():
    order = form.save()
    transaction.on_commit(
        lambda: order_created.delay(order.id))

# settings.py（本仓库缺的就是这一段）
CELERY_BROKER_URL = 'redis://cache:6379/0'
CELERY_RESULT_BACKEND = 'redis://cache:6379/1'
CELERY_TASK_ACKS_LATE = True
  • @shared_task 让任务不绑定具体 app 实例，可跨项目复用
  • 事务与派发的先后要自己用 on_commit 管，框架不会提醒
  • 必须额外运维 broker + worker 两类进程

Spring Boot 3.x

三个层次可选：进程内线程池、事务事件、外部消息队列。轻量场景不需要额外基础设施。

// ① 最轻量：@Async + 线程池（进程内，重启即丢）
@Async("mailExecutor")
public void orderCreated(Long orderId) { ... }

// ② 事务绑定：Spring 原生支持提交后触发
@TransactionalEventListener(
    phase = TransactionPhase.AFTER_COMMIT)
public void on(OrderCreatedEvent e) {
    mailService.send(e.orderId());
}

// ③ 真正的分布式队列：Spring AMQP / Kafka
@RabbitListener(queues = "orders")
public void handle(OrderCreatedMessage msg) { ... }

// 重试是声明式的
@Retryable(maxAttempts = 5,
           backoff = @Backoff(delay = 1000, multiplier = 2))
public void sendInvoice(Long id) { ... }
  • @TransactionalEventListener 把「提交后才执行」做成了框架能力
  • @Async 的任务活在 JVM 内存里，重启即丢，只适合可丢失的工作
  • 要可靠投递仍需 RabbitMQ / Kafka，和 Celery 一样要运维

Hono.js

Serverless / 边缘环境没有常驻进程，「后台 worker」这个概念本身不成立。

// 边缘环境没有常驻 worker 进程，两条路：

// ① waitUntil：响应先返回，任务在后台跑完
app.post('/orders', async (c) => {
  const order = await createOrder(...)
  c.executionCtx.waitUntil(sendOrderEmail(order.id))
  return c.json({ id: order.id })   // 立刻返回
})

// ② 队列服务（Cloudflare Queues）
export default {
  fetch: app.fetch,
  async queue(batch, env) {          // 独立的消费者入口
    for (const msg of batch.messages) {
      await sendOrderEmail(msg.body.orderId)
      msg.ack()                      // 显式确认
    }
  },
}
  • waitUntil 让响应先返回、任务继续跑，但受平台 CPU 时间上限约束
  • 真正的队列要用平台服务（Cloudflare Queues、SQS）
  • 消费者是另一个入口函数，不是另一个进程

定时任务需要额外跑一个 celery beat 进程，且 beat 单实例运行，本身是个单点。

Spring Boot 3.x

// 重试：@Retryable + @Recover 兜底
@Retryable(retryFor = MailException.class,
           maxAttempts = 5,
           backoff = @Backoff(delay = 1000,
                              multiplier = 2,
                              random = true))
public void send(Long orderId) { ... }

@Recover
public void onGiveUp(MailException e, Long orderId) {
    deadLetterRepo.save(orderId, e.getMessage());
}

// 定时任务：注解即调度，无需额外进程
@Scheduled(cron = "0 0 9 * * *")
public void enrollReminder() { ... }

// 分布式环境要加锁，否则每个实例都会跑
@SchedulerLock(name = "enrollReminder")

@Recover 提供了「重试耗尽后怎么办」的显式钩子，这一点比 Celery 的 on_failure 更顺手。

@Scheduled 不需要独立进程，但多实例部署时必须配 ShedLock 之类的分布式锁，否则每个实例都会各跑一遍。

Hono.js

// Cloudflare Queues 自带重试与死信队列，
// 但配置在 wrangler.toml，不在代码里：
//
// [[queues.consumers]]
// queue = "orders"
// max_retries = 5
// dead_letter_queue = "orders-dlq"

// 代码里只决定这一条要不要重试
async queue(batch, env) {
  for (const msg of batch.messages) {
    try {
      await sendOrderEmail(msg.body.orderId)
      msg.ack()
    } catch (e) {
      msg.retry({ delaySeconds: 30 })
    }
  }
}

// 定时任务：Cron Triggers
export default {
  async scheduled(event, env, ctx) { ... },
}

重试与死信队列由平台配置决定，代码里只能决定单条消息 ack 还是 retry。

定时任务是平台的 Cron Trigger，天然单次触发，不存在多实例重复执行的问题。

三句话概括

  • Celery 能力最全，但它是「另一套系统」。重试、退避、路由、优先级、工作流（chain / group / chord）它都有，代价是你要额外运维 broker、worker、beat 三类进程，而且这些进程的健康状况 Django 一无所知——本仓库的 F-01 正是这种「代码写完了但运行时不存在」的典型。它也把事务与派发的时序完全交给了开发者，transaction.on_commit 不写就是个定时炸弹。
  • Spring 的分层选择最务实。「发个邮件、丢了也无所谓」用 @Async，零基础设施；「必须跟着事务走」用 @TransactionalEventListener，框架直接保证提交后才执行——这正是 Django 需要手写 on_commit 的那件事；「必须可靠投递」才上 RabbitMQ。而 @Recover 让「重试耗尽之后怎么办」有了标准位置，这个钩子 Celery 里要自己搭。
  • Hono 的模型完全不同：没有常驻进程，就没有 worker。waitUntil 解决的是「响应先返回、收尾继续跑」，但它受平台 CPU 时间上限约束，不能替代真正的队列。需要可靠性时用平台队列服务，重试和死信队列是配置而非代码——好处是这些能力不用自己实现也不会被写错，坏处是你被绑在平台上，本地开发和测试都要靠模拟器。
