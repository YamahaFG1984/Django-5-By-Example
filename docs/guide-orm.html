本文结论速览

三条最重要的结论

  1. 用中文标题收藏一张图片，保存成功后会立刻 500。 Image.save() 用 slugify(self.title) 生成 slug，而 slugify('日落时分的海湾') 返回空串；空 slug 让 get_absolute_url() 抛 NoReverseMatch，而 image_create 视图保存后紧接着就是 redirect(new_image.get_absolute_url())。详见 F-01。
  2. 全仓库 Meta.constraints 是空的，三个缺陷都由此而来。 unique_for_date 只在表单层生效、(course, order) 没有唯一约束、Contact 既能重复也能自己关注自己——实测全部可以通过 objects.create() 直接写进数据库。详见 F-02、F-03、F-06。
  3. bulk_create 会让 OrderField 算出一模一样的排序值。 实测批量插入 4 个模块，四个的 order 全是 0——因为四次 pre_save 都发生在同一批 INSERT 之前，各自查到的「上一条」是同一个。详见 F-03。

本文结构与前五篇指南一致：先讲 Django ORM 里「校验」的三个层次（这是理解后面全部缺陷的钥匙），再逐处分析本仓库的模型代码，然后是八个已验证的问题及修复、查询性能专题，最后是上线清单与 Spring Data JPA / Drizzle 对比。所有论断都在本机 Django 5.2 上实测验证，实测输出以绿色标题的终端块标注。

一、Django 里「校验」有三个互不相通的含义

这是本文最重要的一节。Django 允许你在三个不同的层次上表达同一条规则，而它们的生效范围完全不同：

层次写法什么时候执行能挡住谁
① 表单层clean_<field>()、unique_for_date、validatorsform.is_valid() 时只能挡住走 admin / ModelForm 的写入
② 模型层Model.full_clean()、Model.clean()只有你显式调用时几乎挡不住谁——save() 默认不调用它
③ 数据库层Meta.constraints、unique=True每一次 INSERT / UPDATE所有写入路径，包括原始 SQL

最容易踩的一条：Model.save() 不会调用 full_clean()。 很多人以为字段上写了 validators=[...] 或者 MaxValueValidator 就万无一失了，实际上 Model.objects.create(discount=99999) 会畅通无阻地写进数据库——那些 validator 只在表单校验时跑。本仓库 Order.discount 上就挂着 MinValueValidator(0), MaxValueValidator(100)，但没有对应的 CheckConstraint。

下面三节里 F-02、F-03、F-06 全部是同一个模式：规则写在了 ① 或 ②，而实际写入走的是 ③ 才能拦住的路径。

1.1 判断规则该写在哪一层

  • 凡是「数据不能这样」的规则，都应该有一条数据库约束。唯一性、取值范围、互斥关系、非空组合——这些是数据完整性，不是用户体验。
  • 表单层的校验是给人看的提示。它的价值在于给出友好的错误信息、在提交前拦住明显错误，而不是保证数据正确。
  • 两者不是二选一，而是都要。只有数据库约束，用户会看到一个 500；只有表单校验，脏数据会从别的入口溜进来。正确做法是数据库约束保证正确性，表单校验提供体验，并在视图里捕获 IntegrityError 转成友好提示。
python
# 同一条规则，两层都写
class Contact(models.Model):
    user_from = models.ForeignKey(User, related_name='rel_from_set', on_delete=models.CASCADE)
    user_to = models.ForeignKey(User, related_name='rel_to_set', on_delete=models.CASCADE)

    class Meta:
        constraints = [
            models.UniqueConstraint(fields=['user_from', 'user_to'], name='uniq_contact'),
            models.CheckConstraint(
                condition=~models.Q(user_from=models.F('user_to')),   # 不能关注自己
                name='no_self_follow',
            ),
        ]

CheckConstraint 的参数在 Django 5.1 起由 check= 改名为 condition=，旧名在 5.2 上仍可用但会发弃用警告，计划在 6.0 移除。写新代码直接用 condition=。

class Image(models.Model):

total_likes 是典型的去规范化：点赞数本可以用 users_like.count() 实时算，但为了让「按点赞数排序」能走索引，把它冗余成一个字段。这个取舍是合理的，代价是必须有人负责维护它的一致性——这里交给了 m2m_changed 信号（F-04）。

add_to_class 动态加字段是全仓库最特别的一处 ORM 用法：

python
# account/models.py 末尾
user_model = get_user_model()
user_model.add_to_class(
    'following',
    models.ManyToManyField('self', through=Contact, related_name='followers', symmetrical=False),
)

它在模块导入时往 auth.User 上挂一个多对多字段。之所以不需要迁移，是因为这个 M2M 指定了 through=Contact——连接表就是已有的 Contact 表，不需要新建任何表或列。仓库的 account/migrations/ 里确实没有任何迁移包含 following，我核对过。

这个技巧在教学上很直观，但不建议照搬进生产：它让 User 模型的定义散落在两个 app 里，只有 import 过 account.models 之后这个字段才存在，任何直接操作 auth.User 的脚本都可能看不到它。Two Scoops of Django 的标准建议是：一开始就用自定义 User 模型，需要加字段就正常加。

2.4 educa：自定义字段与抽象基类

python
class OrderField(models.PositiveIntegerField):
    def __init__(self, for_fields=None, *args, **kwargs):
        self.for_fields = for_fields
        super().__init__(*args, **kwargs)

    def pre_save(self, model_instance, add):
        if getattr(model_instance, self.attname) is None:
            try:
                qs = self.model.objects.all()
                if self.for_fields:
                    query = {f: getattr(model_instance, f) for f in self.for_fields}
                    qs = qs.filter(**query)
                last_item = qs.latest(self.attname)              # 每次插入多一条 SELECT
                value = getattr(last_item, self.attname) + 1
            except ObjectDoesNotExist:
                value = 0
            setattr(model_instance, self.attname, value)
            return value
        return super().pre_save(model_instance, add)

重写 pre_save() 是自定义字段的标准做法，思路清晰。问题是这个「读上一条再加一」的模式在批量插入和并发下都会出问题（F-03）。

python
class ItemBase(models.Model):
    owner = models.ForeignKey(User, related_name='%(class)s_related', on_delete=models.CASCADE)
    title = models.CharField(max_length=250)

    class Meta:
        abstract = True

    def render(self):
        return render_to_string(f'courses/content/{self._meta.model_name}.html', {'item': self})


class Text(ItemBase):
    content = models.TextField()

class Video(ItemBase):
    url = models.URLField()

%(class)s_related 是抽象基类里给 related_name 去重的标准写法——四个子类分别得到 text_related、video_related 等，不会撞名。这里用的是抽象基类而不是多表继承，每个子类一张独立的表，没有隐式 JOIN，这个选择是对的。

                            allow_unicode=True)

        if not self.slug:

                                allow_unicode=True) or 'image'

只改模型还不够。 Django 内置的 <slug:...> 路径转换器正则是 [-a-zA-Z0-9_]+，不匹配中文。要让 Unicode slug 真的能用在 URL 里，还得换掉这一段路由：

re_path(r'^detail/(?P<id>\d+)/(?P<slug>[-\w]+)/$', views.image_detail, name='detail')

\w 在 Python 正则里默认匹配 Unicode 字母，所以中文能过。那个 or 'image' 的兜底也不能省——纯 emoji 标题在 allow_unicode=True 下依然会得到空串。

Django 文档对 unique_for_date 写得很明确：它由 Model.validate_unique() 实现，而 validate_unique() 只在 ModelForm 校验时被调用。它不会生成任何数据库约束。

python
# 补一条真正的数据库约束
from django.db.models.functions import TruncDate

class Post(models.Model):
    slug = models.SlugField(max_length=250)      # unique_for_date 可以留着做表单提示
    publish = models.DateTimeField(default=timezone.now)

    class Meta:
        constraints = [
            models.UniqueConstraint(
                'slug', TruncDate('publish'),
                name='uniq_slug_per_publish_date',
            ),
        ]

UniqueConstraint 支持表达式（Django 4.0 起），所以可以直接对 TruncDate('publish') 建唯一索引，语义与 unique_for_date 完全一致。PostgreSQL 和 SQLite 都支持表达式索引；MySQL 需要 8.0.13+。

# 并发场景：用一次原子的聚合代替「读-加一-写」
from django.db import transaction
from django.db.models import Max

with transaction.atomic():
    last = (Module.objects
            .select_for_update()          # 锁住同一课程下的行
            .filter(course=course)
            .aggregate(m=Max('order'))['m'])
    Module.objects.create(course=course, title='X', order=0 if last is None else last + 1)
python
# 无论如何，先把约束加上——让重复变成一个响亮的错误而不是静默的乱序
class Module(models.Model):
    class Meta:
        ordering = ['order']
        constraints = [
            models.UniqueConstraint(fields=['course', 'order'], name='uniq_module_order'),
        ]

加了唯一约束之后，拖拽排序那段代码也要改。 ModuleOrderView 是逐条 update(order=...) 的，中间过程必然出现两条记录暂时同号，会直接撞约束。解决办法是把约束设为 DEFERRABLE INITIALLY DEFERRED（PostgreSQL 支持，Django 的 UniqueConstraint(deferrable=Deferrable.DEFERRED)），让它在事务提交时才检查。

F-04m2m_changed 处理函数没判 action 与 reverse已实测 · 性能 + 健壮性
位置
Chapter07/bookmarks/images/signals.py
触发
每一次点赞 / 取消点赞
影响
每次多一轮 count + 整行 UPDATE；反向添加会抛 AttributeError
实测 · 一次 image.users_like.add(user)
信号被触发的 action 序列: ['pre_add', 'post_add']
期间执行的 SQL 条数      : 8
最终 total_likes         : 1

UPDATE 语句片段:
  UPDATE "app_image" SET "title" = 'Sunset', "slug" = 'sunset', "total_likes" = 0
  WHERE "app_image"."id" = 1
  -> 没有传 update_fields，整行字段都会被写回

反向操作 user.images_liked.add(image):
  抛 AttributeError: 'User' object has no attribute 'users_like'

三个问题叠在一起：m2m_changed 对每次操作会成对触发（pre_add 和 post_add），处理函数不判 action 就会跑两遍，其中 pre_add 那次算出的还是旧值；instance.save() 没有 update_fields，会把整行字段写回去，覆盖掉别的请求对同一行其它字段的修改；处理函数也没判 reverse。

✗ 现状
@receiver(m2m_changed, sender=Image.users_like.through)
def users_like_changed(sender, instance, **kwargs):
    instance.total_likes = instance.users_like.count()
    instance.save()
✓ 判 action、判 reverse、只写目标字段
@receiver(m2m_changed, sender=Image.users_like.through)
def users_like_changed(sender, instance, action,
                       reverse, pk_set, **kwargs):
    if action not in ('post_add', 'post_remove', 'post_clear'):
        return
    if reverse:
        images = Image.objects.filter(pk__in=pk_set or [])
    else:
        images = [instance]
    for image in images:
        Image.objects.filter(pk=image.pk).update(
            total_likes=image.users_like.count())

用 queryset.update() 而不是 instance.save() 还有一个好处：update() 不会触发 post_save 信号，避免了「信号里改数据又触发信号」这类循环风险。代价是它也跳过 save() 里的自定义逻辑——在这个场景下正是我们想要的。

F-05订单总价在 Python 侧遍历，单次调用两条 SQL，列表页 N+1已实测 · 性能
位置

触发

影响

python
def get_total_cost_before_discount(self):
    return sum(item.get_cost() for item in self.items.all())      # 遍历一次

def get_discount(self):
    total_cost = self.get_total_cost_before_discount()            # 又遍历一次
    if self.discount:
        return total_cost * (self.discount / Decimal(100))
    return Decimal(0)

def get_total_cost(self):
    total_cost = self.get_total_cost_before_discount()            # 第 1 次
    return total_cost - self.get_discount()                       # 里面还有第 2 次

def get_discount(self, total_cost=None):
    if total_cost is None:
        total_cost = self.get_total_cost_before_discount()
    if self.discount:
        return total_cost * (self.discount / Decimal(100))
    return Decimal(0)

def get_total_cost(self):
    total_cost = self.get_total_cost_before_discount()
    return total_cost - self.get_discount(total_cost)

4.2 把计算推到数据库里

python
# 数着算 -> 交给数据库算

# 字段间的运算用 F()，避免「读出来改完再写回去」的竞态
from django.db.models import F
Image.objects.filter(id=pk).update(total_likes=F('total_likes') + 1)

from django.db.models import Sum, F, DecimalField, ExpressionWrapper
Order.objects.annotate(
    subtotal=Sum(ExpressionWrapper(
        F('items__price') * F('items__quantity'),
        output_field=DecimalField(max_digits=12, decimal_places=2))))

annotate(Count(...)) 会引入 GROUP BY，而 GROUP BY 会让 Meta.ordering 静默失效——Django 源码里的原话是「A default ordering doesn't affect GROUP BY queries」。本仓库的 SubjectViewSet 正踩在这上面，导致分页顺序不稳定。完整复现与修复见 DRF 指南 F-02。

五、上线前检查清单

  • 01凡是「数据不能这样」的规则，都要有数据库约束。表单校验只是提示，objects.create() 一行就能绕过。见第一节。
  • 02Model.save() 不调用 full_clean()。字段上的 validators 在 create() 路径上完全不生效。
  • 03unique_for_date / unique_for_month 不是数据库约束，需要额外加 UniqueConstraint。见 F-02。
  • 04关联表要有唯一约束（如「谁关注了谁」「谁收藏了什么」）。get_or_create 的原子性依赖这个约束。见 F-06。
  • 05排序字段要有 (父, 序号) 的唯一约束，并考虑用 deferrable 让重排能在事务内完成。见 F-03。
  • 06slug 由用户输入生成时要处理非 ASCII 与空值：allow_unicode=True 加一个兜底默认值。见 F-01。
  • 07计数器自增用 F() 表达式，不要「读出来加一再存回去」——后者在并发下会丢更新。
  • 08信号处理函数要判 action 和 reverse，并用 update() 或 save(update_fields=[...]) 只写目标字段。见 F-04。
  • 09bulk_create / update() 跳过 save() 与信号。依赖 save() 里逻辑的字段，批量操作时要显式赋值。见 F-03。
  • 10列表页一律检查 N+1：外键用 select_related，多值关系用 prefetch_related，GenericForeignKey 用 GenericPrefetch。见 F-05、F-08。
  • 11关键端点写 assertNumQueries 断言。这是唯一能在 CI 里挡住 N+1 回归的手段。
  • 12能在数据库算的就别在 Python 里算：Count、Sum、annotate。但要留意 annotate 引入的 GROUP BY 会让 Meta.ordering 失效。
  • 13判空用 .exists()，除非之后还要用这批数据。见 F-07。
  • 14每个 on_delete 都单独想一下。CASCADE 是最省事的默认，但订单、日志、审计记录多半应该是 PROTECT 或 SET_NULL。
  • 15第一个定义的管理器就是默认管理器。带过滤的自定义管理器不要放在 objects 前面，否则 admin 和关联访问都会看到被过滤的数据。
  • 16新项目一开始就用自定义 User 模型，不要靠 add_to_class 往 auth.User 上挂东西。

6.1 模型 / schema 的表达方式

Django ORM

模型类同时是表结构定义、校验规则和业务方法的载体。迁移由框架从模型差异自动生成。

class Course(models.Model):
    owner = models.ForeignKey(
        User, related_name='courses_created',
        on_delete=models.CASCADE)
    title = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, unique=True)
    students = models.ManyToManyField(
        User, related_name='courses_joined', blank=True)

    class Meta:
        ordering = ['-created']
        indexes = [models.Index(fields=['-created'])]
        constraints = [
            models.UniqueConstraint(
                fields=['owner', 'title'],
                name='uniq_course_per_owner'),
        ]

# 迁移由框架生成，与模型定义强绑定
# python manage.py makemigrations && migrate
  • 模型即真相：改字段 → makemigrations → 迁移文件，一条链路
  • Meta.constraints 才是真约束；表单校验挡不住 create()
  • 关联的删除行为（on_delete）是必填参数，逼你每次都想一下

Spring Data JPA

实体类描述对象映射，建表脚本通常独立管理（Flyway / Liquibase），两者要人工保持同步。

@Entity
@Table(name = "course",
    indexes = @Index(columnList = "created DESC"),
    uniqueConstraints = @UniqueConstraint(
        columnNames = {"owner_id", "title"}))
public class Course {
    @Id @GeneratedValue Long id;

    @ManyToOne(fetch = FetchType.LAZY)   // 默认 EAGER，必须显式改
    User owner;

    String title;

    @ManyToMany
    @JoinTable(name = "course_students")
    Set<User> students = new HashSet<>();
}

// 建表默认交给 Flyway / Liquibase，
// 与实体定义是两份独立的东西
  • 实体与迁移分离：更可控，也更容易写着写着就不一致
  • 单值关联默认 EAGER，是 N+1 的头号来源，必须显式改 LAZY
  • 约束写在注解里，但真正建表的是迁移脚本——注解只在自动建表模式下生效

schema 是普通 TypeScript 对象，类型直接从 schema 推导，没有运行时的对象映射层。

6.2 查询与 N+1

Django ORM

# 惰性：这一行不查库
qs = Course.objects.filter(owner=u)

# 这些都还是惰性的，只是在拼 SQL
qs = qs.exclude(title='').order_by('-created')[:20]

# 直到求值才真正执行
for c in qs: ...           # 迭代
list(qs); bool(qs); len(qs)  # 都会求值

# 解决 N+1：外键用 select_related（JOIN）
Course.objects.select_related('owner', 'subject')

# 多对多 / 反向关系用 prefetch_related（额外一次查询）
Course.objects.prefetch_related('modules__contents')

# 聚合放数据库里做
Order.objects.annotate(
    subtotal=Sum(F('items__price') * F('items__quantity')))

QuerySet 是惰性且可链式的，同一个 queryset 求值一次后会缓存结果——但每次 .all() 都会得到新对象，这正是本文 F-05 里同样的明细被查两次的原因。

select_related（JOIN，用于外键 / 一对一）与 prefetch_related（额外查询 + Python 侧关联，用于多对多 / 反向 / GenericForeignKey）分工明确，是解决 N+1 的主力。

Spring Data JPA

// JPA 默认 EAGER 抓单值关联，很容易一不留神就多查
@ManyToOne(fetch = FetchType.LAZY)   // 务必显式写

// 解决 N+1：@EntityGraph 或 fetch join
@EntityGraph(attributePaths = {"owner", "subject"})
List<Course> findByOwnerId(Long id);

@Query("SELECT c FROM Course c JOIN FETCH c.modules "
     + "WHERE c.owner.id = :id")
List<Course> findWithModules(@Param("id") Long id);

// 聚合：JPQL 或 Criteria
@Query("SELECT new CourseStat(c.id, SUM(i.price * i.qty)) "
     + "FROM Course c JOIN c.items i GROUP BY c.id")
List<CourseStat> stats();

// LazyInitializationException 是这套模型的经典陷阱：
// 出了事务边界再碰懒加载字段就会炸

JPA 有持久化上下文这一层，实体在事务内是「被托管」的，改了字段不 save 也会写回——威力大，但也让「这行代码到底会不会发 SQL」变得难以一眼看清。

LazyInitializationException 是这套模型最经典的陷阱：出了事务边界再访问懒加载字段就会抛异常。Django 没有对应问题，代价是它也没有自动脏检查。

Hono + Drizzle

// Drizzle：写起来接近 SQL，没有惰性代理这一层
const rows = await db
  .select()
  .from(course)
  .where(eq(course.ownerId, uid))
  .orderBy(desc(course.createdAt))
  .limit(20)

// 关联查询是显式的，没有「不小心触发一次查询」这回事
const withModules = await db.query.course.findMany({
  with: { modules: { with: { contents: true } } },
})

// 聚合
await db
  .select({ id: order.id,
            subtotal: sum(sql`${item.price} * ${item.qty}`) })
  .from(order)
  .leftJoin(item, eq(item.orderId, order.id))
  .groupBy(order.id)

没有惰性代理、没有持久化上下文，写了几个 await 就发几条 SQL，查询开销完全可预测。

代价是所有便利都要自己搭：没有 get_or_create、没有信号、没有模型级校验，也没有 admin。

三句话概括

  • Django ORM 的优点和缺点是同一件事：模型类承担得太多。它同时是表结构、校验规则、业务方法和序列化起点，这让小项目推进极快——本仓库四个项目加起来不到两千行模型代码就跑通了博客、电商、社交和在线教育。代价是「校验」这个词在 Django 里有三个互不相通的含义（表单层、full_clean()、数据库约束），而默认的 save() 一层都不走。本文的 F-02、F-03、F-06 全部源于此：规则写在了不该写的层次上。
  • JPA 的持久化上下文更强大，也更难预测。实体在事务内被托管、脏检查自动写回、一级缓存去重，这些在复杂业务里很有价值；但「这行代码会不会发 SQL」在 JPA 里往往要看事务边界和抓取策略才能回答，而 Django 里基本是「你写了查询才有查询」。JPA 单值关联默认 EAGER 更是一个反直觉的默认值，是它 N+1 问题的主要来源。
  • Drizzle 代表的方向是「把 ORM 变薄」。没有惰性代理、没有持久化上下文，写几个 await 就发几条 SQL，配合 TypeScript 从 schema 推导出的类型，查询结果的形状在编译期就是确定的。它换来的是可预测性，付出的是所有便利设施——Django 那套 admin、信号、表单、get_or_create 在这里一个都没有。选它的团队通常是明确不想要那层抽象，而不是还没来得及搭。
