「Bookmark it」书签工具到底是怎么实现的

涉及文件：account/templates/account/dashboard.html、images/templates/bookmarklet_launcher.js、images/static/js/bookmarklet.js、images/views.py、images/forms.py、images/models.py、images/urls.py、images/templates/images/image/create.html。

基于 Chapter06/bookmarks 逐行阅读整理 含 5 张手绘架构 / 时序示意图

一句话总览

「Bookmark it」不是一个普通的「收藏当前网页」按钮，而是一个 Bookmarklet（书签工具）——它是一段存进浏览器书签栏的 JavaScript 代码。点击它，不会打开新页面，而是在你当前正停留的任意第三方网站上原地执行这段代码：扫描这个网页里的所有图片，弹出一个悬浮选择框，等你点选一张后，把这张图的地址「带回」你自己的 Bookmarks 网站，帮你把它存进数据库。

整个功能横跨四个文件、两次页面往返、一次服务端出站请求，本文按「先看全貌，再逐段拆解」的顺序讲清楚。涉及代码全部来自 Chapter06/bookmarks/images/ 与 account/templates/account/dashboard.html。

完整时序图：从选图到入库

先看整体：一次完整的「Bookmark it」操作，实际上跨越了两个域名（第三方网页 / 你的 Bookmarks 站点）、两次浏览器往返（先注入脚本，再新开标签页跳转）、一次服务端出站请求（Django 服务器主动去下载图片）。下图把从「用户在别的网站点一下书签」到「图片文件真正落到你服务器磁盘、数据库多一条记录」的全过程画在一张时序图里，后面几节再逐段放大讲解每一步。

一、Bookmarklet 是什么：javascript: 协议的巧妙用法

普通书签存的是一个网址，点击后浏览器跳转到那个地址。Bookmarklet 存的不是网址，而是一段 javascript: 开头的代码——浏览器看到链接是 javascript: 协议，就不会跳转页面，而是在当前打开的这个页面的上下文里直接执行这段代码，效果等价于你打开浏览器控制台，把这段代码粘贴进去回车。

这正是 dashboard 页面里那个按钮的写法（account/templates/account/dashboard.html 第 10 行）：

html
<p>Drag the following button to your bookmarks toolbar to bookmark images from other websites →
  <a href="javascript:{% include "bookmarklet_launcher.js" %}" class="button">Bookmark it</a></p>

href 属性的值不是一个 URL，而是直接把 bookmarklet_launcher.js 这个模板文件的内容原样嵌进去——用户把这个按钮拖到浏览器收藏栏，浏览器就把这段 JS 代码存成了一个「网址」。以后不管用户身处哪个网站，只要点一下这个书签，这段代码就会在当前网站的页面里跑起来。

这是 Bookmarklet 的核心价值：不需要浏览器扩展、不需要用户安装任何东西，纯靠浏览器对 javascript: 协议的原生支持，就获得了「在任意网页上运行自己代码」的能力。

二、为什么拆成两段：启动器 + 真正逻辑

如果你把 bookmarklet.js 里几十行的完整逻辑全部塞进 href 属性，会有两个问题：一是 href 属性能塞多长、能不能带特殊字符都不太可靠；二是以后想修 bug、加功能，用户书签栏里存的代码是「死」的——除非让用户重新拖一次书签，否则永远是旧版本。

Chapter06 的方案是拆成两段——href 里只放一个几行的「启动器」（bookmarklet_launcher.js），启动器的唯一任务是去加载真正干活的 bookmarklet.js：

javascript
(function(){
  if(!window.bookmarklet) {
    bookmarklet_js = document.body.appendChild(document.createElement('script'));
    bookmarklet_js.src = '//127.0.0.1:8000/static/js/bookmarklet.js?r='+Math.floor(Math.random()*9999999999999999);
    window.bookmarklet = true;
  }
  else {
    bookmarkletLaunch();
  }
})();

逐行看这个判断逻辑：

  • 第一次点击：window.bookmarklet 还没定义，走 if 分支——往当前页面的 <body> 动态插入一个 <script> 标签，src 指向你自己站点的 bookmarklet.js；同时把 window.bookmarklet 标记为 true。
  • ?r=Math.random() 是缓存穿透（cache busting）：每次请求带一个不同的随机查询参数，让浏览器不要用缓存里的旧版本脚本，保证用户始终跑的是你服务器上最新的逻辑——书签栏里的启动器代码本身永远不用变，真正的功能可以随时在服务端悄悄升级。
  • 再次点击（同一个页面上，比如用户关掉悬浮框后又点了一次）：window.bookmarklet 已经是 true，直接走 else 分支调用 bookmarkletLaunch()——不用再重新插入 <script> 标签、不用再发一次网络请求。

三、bookmarklet.js：扫描页面 + 悬浮框选图

真正的逻辑在 images/static/js/bookmarklet.js 里，先加载一份 CSS，再往页面注入一个悬浮框骨架，最后定义 bookmarkletLaunch() 函数并立即调用一次：

javascript
function bookmarkletLaunch() {
  bookmarklet = document.getElementById('bookmarklet');
  var imagesFound = bookmarklet.querySelector('.images');
  imagesFound.innerHTML = '';
  bookmarklet.style.display = 'block';

  // find images in the DOM with the minimum dimensions
  images = document.querySelectorAll('img[src$=".jpg"], img[src$=".jpeg"], img[src$=".png"]');
  images.forEach(image => {
    if(image.naturalWidth >= minWidth && image.naturalHeight >= minHeight)
    {
      var imageFound = document.createElement('img');
      imageFound.src = image.src;
      imagesFound.append(imageFound);
    }
  })

  // select image event
  imagesFound.querySelectorAll('img').forEach(image => {
    image.addEventListener('click', function(event){
      imageSelected = event.target;
      bookmarklet.style.display = 'none';
      window.open(siteUrl + 'images/create/?url='
                  + encodeURIComponent(imageSelected.src)
                  + '&title='
                  + encodeURIComponent(document.title),
                  '_blank');
    })
  })
}

拆开看四步：

  • 扫描：document.querySelectorAll('img[src$=".jpg"], ...') 用 CSS 属性选择器的「结尾匹配」语法（$=），把当前页面 DOM 里所有 src 以 .jpg/.jpeg/.png 结尾的 <img> 全部找出来。
  • 过滤：minWidth/minHeight 都是 250，只保留 naturalWidth/naturalHeight（图片的真实像素尺寸，不是 CSS 显示尺寸）都不小于 250 的——把网站导航栏图标、装饰性小图、一像素统计埋点图都挡在外面，只留下「看起来像正文配图」的大图。
  • 展示：把筛出来的图片地址克隆成新的 <img> 塞进悬浮框的 .images 容器里，靠 bookmarklet.css（z-index 拉到最高）盖在原网页最上层，形成一个「选图面板」。
  • 选中并转交：每张候选缩略图都绑定一个 click 监听。用户点了哪张，就拿到它的 src，调用 window.open() 新开一个标签页，跳到你自己的 Bookmarks 站点，把选中图片的地址和当前网页标题作为 GET 查询参数拼在 URL 里。

这一步是整套设计里最容易被忽略但最关键的一点：浏览器全程没有对图片发起任何跨域网络请求——没有 fetch、没有 XMLHttpRequest 去读取那张图的内容，只是读了一下 DOM 上已经在渲染的 <img> 元素的 src 字符串属性，然后把这个字符串当普通文本，通过 URL 参数「转达」给自己的站点。既不需要目标网站开放 CORS，也不违反同源策略，因为压根没有发生跨域请求这回事。

四、image_create 视图的双重身份：GET 预填 / POST 提交

新标签页打开后命中的是 images/urls.py 里的这一条路由：

python
urlpatterns = [
    path('create/', views.image_create, name='create'),
    path('detail/<int:id>/<slug:slug>/', views.image_detail, name='detail'),
    path('like/', views.image_like, name='like'),
    path('', views.image_list, name='list'),
]

而 image_create() 这一个视图函数，同时服务于两种完全不同的请求场景——这是新手读这段代码时最容易看晕的地方：

python
@login_required
def image_create(request):
    if request.method == 'POST':
        # form is sent
        form = ImageCreateForm(data=request.POST)
        if form.is_valid():
            cd = form.cleaned_data
            new_image = form.save(commit=False)
            new_image.user = request.user
            new_image.save()
            messages.success(request, 'Image added successfully')
            return redirect(new_image.get_absolute_url())
    else:
        # build form with data provided by the bookmarklet via GET
        form = ImageCreateForm(data=request.GET)
    return render(
        request,
        'images/image/create.html',
        {'section': 'images', 'form': form},
    )
  • GET 分支（书签工具新开标签页跳过来的第一次请求）：request.GET 里带着 url 和 title 两个参数，直接用它们实例化一个未绑定提交、只是预填了初始值的表单，渲染出确认页面——用户在页面上看到的图片预览和自动填好的标题，就是从这里来的。
  • POST 分支（用户在确认页面点了「Bookmark it!」按钮之后）：这才是真正的表单提交与校验，校验通过后调用 form.save() 把图片存下来，成功后 redirect() 跳到图片详情页。

对应的模板 images/templates/images/image/create.html：

html
{% extends "base.html" %}
{% block content %}
  <h1>Bookmark an image</h1>
  <img src="{{ request.GET.url }}" class="image-preview">
  <form method="post">
    {{ form.as_p }}
    {% csrf_token %}
    <input type="submit" value="Bookmark it!">
  </form>
{% endblock %}

注意 <img src="{{ request.GET.url }}"> 这一行：预览图直接从浏览器去加载第三方网站的原图地址显示出来，此时还没有发生任何服务端下载——用户看到的预览，其实是浏览器直接向那个第三方 URL 发起的图片请求，跟你的 Django 服务器毫无关系。真正的「服务端下载」发生在用户点击提交之后，见下一节。

为什么提交成功后用 redirect() 而不是直接 render() 详情页？这是经典的 PRG（Post/Redirect/Get）模式：如果 POST 成功后直接渲染结果页，用户按浏览器刷新键会导致表单被重复提交（重复创建图片记录）；改成重定向后，浏览器地址栏变成详情页的 GET 请求，刷新只是重新 GET 一次详情页，不会重复提交表单。

五、真正的服务端下载：ImageCreateForm.save()

表单定义在 images/forms.py：

python
class ImageCreateForm(forms.ModelForm):
    class Meta:
        model = Image
        fields = ['title', 'url', 'description']
        widgets = {
            'url': forms.HiddenInput,
        }

    def clean_url(self):
        url = self.cleaned_data['url']
        valid_extensions = ['jpg', 'jpeg', 'png']
        extension = url.rsplit('.', 1)[1].lower()
        if extension not in valid_extensions:
            raise forms.ValidationError(
                'The given URL does not match valid image extensions.'
            )
        return url

    def save(self, force_insert=False, force_update=False, commit=True):
        image = super().save(commit=False)
        image_url = self.cleaned_data['url']
        name = slugify(image.title)
        extension = image_url.rsplit('.', 1)[1].lower()
        image_name = f'{name}.{extension}'
        # download image from the given URL
        response = requests.get(image_url)
        image.image.save(
            image_name,
            ContentFile(response.content),
            save=False
        )
        if commit:
            image.save()
        return image

几个值得注意的设计点：

  • widgets = {'url': forms.HiddenInput}——用户在确认页面看不到、也不需要手填 url 这个字段，它是 GET 参数预填进来、原样跟着表单一起提交的「隐藏字段」，用户界面上只露出标题和描述两个可编辑项。
  • clean_url() 是 Django 表单的标准校验钩子（clean_<fieldname> 命名约定自动生效），这里只做了一件事：看 URL 结尾的文件扩展名是不是 jpg/jpeg/png。
  • 真正「下载图片」发生在重写过的 save() 方法里：requests.get(image_url) 由 Django 服务器本身发起一次真实的出站 HTTP 请求，把响应体 response.content（图片的原始二进制数据）包进 ContentFile，再通过 image.image.save(name, ContentFile(...), save=False) 存进 ImageField 关联的媒体目录。

存储目标由 images/models.py 里的 Image 模型定义：

python
class Image(models.Model):
    user = models.ForeignKey(settings.AUTH_USER_MODEL, related_name='images_created', on_delete=models.CASCADE)
    title = models.CharField(max_length=200)
    slug = models.SlugField(max_length=200, blank=True)
    url = models.URLField(max_length=2000)
    image = models.ImageField(upload_to='images/%Y/%m/%d/')
    description = models.TextField(blank=True)
    created = models.DateTimeField(auto_now_add=True)
    users_like = models.ManyToManyField(settings.AUTH_USER_MODEL, related_name='images_liked', blank=True)

url 字段本身也留了下来——数据库里同时保存着「原始来源地址」（url，纯文本）和「服务器本地这份图片文件」（image，真正的文件字段）。以后详情页展示的是本地这份拷贝，不再依赖原网站是否还在线。

安全性提醒 —— clean_url 校验的盲区

没有校验目标主机：只要 URL 结尾看着像 .jpg，http://127.0.0.1/admin.jpg、http://169.254.169.254/latest/meta-data.jpg（云厂商的实例元数据接口，常被用来窃取云凭据）这类指向内网或本机的地址都能通过校验——服务器会代替攻击者去请求这些原本无法从公网直接访问的内部地址，这是一个典型的 SSRF（服务端请求伪造）场景。

没有超时、没有大小限制：requests.get(image_url) 既没有传 timeout 参数，也没有限制响应体大小。一个恶意的「图片」地址可以让这次请求长时间挂起（拖垮 worker 进程），或者返回一个几个 GB 的文件把磁盘和内存吃满——低成本的资源耗尽/简易 DoS。

六、几个常见疑问

Q：为什么选完图要新开一个标签页，而不是用 AJAX 直接把图片传回去？

因为 AJAX（fetch/XMLHttpRequest）请求受同源策略约束：当前页面属于第三方网站的域名，脚本想直接向你的 Bookmarks 域名发起带数据的跨域请求，除非目标服务器显式配置 CORS 允许，否则会被浏览器拦截。window.open() 新开标签页则完全不受此限制——它只是导航到一个新地址，地址里带的查询参数不算「跨域请求数据」，这正是本文第三节末尾强调的巧妙之处。

Q：为什么服务端还要重新下载一遍图片，而不是直接把 url 存进数据库当图片地址用？

如果只存远程 URL，展示图片时永远依赖原网站在线、图片没被删除或改动；原网站也可能随时对图片打水印、限制防盗链（Referer 校验），导致你的页面显示不出图。服务端下载一份「据为己有」，是把图片变成自己站点长期稳定可控的资产——代价就是上一节提到的 SSRF/资源耗尽风险，这是本章设计上一个「图方便」但不完全安全的取舍。

Q：如果同一张图被两个不同用户各自 bookmark 一次，会存两份文件吗？

会。Image 模型没有对 url 做唯一性约束或去重查询，每次提交都会重新触发一次 requests.get() 下载并生成一条新记录、一份新文件——多用户收藏同一张网图，服务器磁盘上会有多份物理拷贝。这不是本章要解决的问题，但读代码时值得留意。

七、一句话讲给完全不懂的人听

把整个「Bookmark it」按钮想象成一个「远程遥控器」：你把遥控器（一段 JS 代码）挂在浏览器书签栏上，走到哪个网站都能掏出来按一下；按下去之后，遥控器先叫来一个「帮手」（bookmarklet.js），帮手在你当前站着的这个网页里东张西望，把看着像样的大图都摆出来给你挑；你选中一张后，帮手不会自己动手去「拿」这张图，而是写一张纸条（URL 参数：图片地址 + 网页标题），让你亲自带着纸条走回自己家（新标签页跳转回 Bookmarks 站点）；到家门口，管家（image_create 视图）看了纸条内容，先给你看一眼预览、问你确认标题和描述；你点头确认后，管家才真正派人出门（服务端 requests.get()）把那张图完整地搬回家里存好（Image 模型 + 媒体文件）。

全程你的浏览器只做了「看图、选图、走一趟」三件事，真正「动手搬东西」的是你自己的服务器——这也是为什么下载环节的安全边界（校验搬回来的到底是不是一张安全的、来路正当的图）必须在服务器这一端做扎实，而不能指望浏览器帮你把关。
