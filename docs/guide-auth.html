本文结论速览

三条最重要的结论

  1. 拖拽排序端点同时缺了两道防线。 ModuleOrderView / ContentOrderView 既没有 LoginRequiredMixin，又主动加了 CsrfExemptMixin。实测：已登录用户不带 CSRF token 的 POST 返回 200 且数据被修改；去掉 CsrfExemptMixin 后返回 403。这是一个可被跨站利用的写端点。详见 F-02。
  2. 课程聊天室的 WebSocket 入口没有任何鉴权。 用真实 WebsocketCommunicator 实测：匿名用户和未报名用户都能连接成功，并完整收到房间里的广播。而配对的 HTTP 视图对同样的两种身份分别返回登录跳转和 403。详见 F-03。
  3. 自定义认证后端引入了一个 1700 倍的用户枚举计时侧信道。 实测 EmailAuthBackend：邮箱存在时 297 ms、不存在时 0.17 ms；Django 内置 ModelBackend 的对应比值是 1.00 倍——因为它故意跑一遍哈希把两条路径拉平。详见 F-05。

一、认证与授权的分界，以及 Django 的四种粒度

两个词经常被混着说，但它们回答的是完全不同的问题，出错方式也不同：

  • 认证（Authentication）回答「你是谁」。 出错的典型形态是：让不该进来的人进来了（弱口令、停用账号仍可登录），或者泄露了「谁存在」这类元信息（用户枚举）。
  • 授权（Authorization）回答「你能做什么」。 出错的典型形态是：越权读到别人的数据、越权修改别人的数据，或者某个入口压根忘了检查。

Django 的授权有四种粒度，它们互相独立、需要主动叠加——这是理解本文后面所有缺陷的关键：

python
# ① 登录与否
class CourseUpdateView(LoginRequiredMixin, UpdateView): ...

# ② 模型级权限（Django 为每个模型自动创建 add/change/delete/view 四种）
class CourseUpdateView(PermissionRequiredMixin, UpdateView):
    permission_required = 'courses.change_course'

# ③ 所有权过滤 —— 「能改课程」不等于「能改这门课程」
def get_queryset(self):
    return super().get_queryset().filter(owner=self.request.user)

# ④ 对象级权限（DRF）
class IsEnrolled(BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.students.filter(id=request.user.id).exists()

第 ② 和第 ③ 层的区别是最容易被忽略的。 Django 的模型级权限只能表达「这个用户能不能修改课程这类对象」，无法表达「能不能修改这一门课程」。所以只加 PermissionRequiredMixin 而不做所有权过滤，等于让任何有 change_course 权限的讲师都能改别人的课。本仓库 OwnerCourseMixin 把 ①②③ 三层叠在一起，这一点做得是对的。

python
# educa 的做法：三层叠加
class OwnerMixin:
    def get_queryset(self):                                   # ③
        return super().get_queryset().filter(owner=self.request.user)

class OwnerCourseMixin(OwnerMixin, LoginRequiredMixin, PermissionRequiredMixin):   # ①②
    model = Course

class CourseUpdateView(OwnerCourseEditMixin, UpdateView):
    permission_required = 'courses.change_course'

还有一层常被忘记的：列表的可见性不由对象级权限保证。DRF 的 has_object_permission 只在 get_object() 被调用时触发，list 动作完全不会逐条调用它。列表能看到什么，只能靠 get_queryset() 过滤。这一点在 DRF 指南第五节详细讨论过。

        try:

            if user.check_password(password):

2.2 educa：课程管理的三层叠加

这是全仓库授权写得最规范的一处，前面已经引用过。值得补充的是 PermissionRequiredMixin 依赖的是 Django 自动创建的模型权限：每个模型迁移时都会生成 add_x / change_x / delete_x / view_x 四条，通过 Group 分配给讲师。

一个容易忽略的细节：PermissionRequiredMixin 默认 raise_exception = False，意味着权限不足的已登录用户会被重定向到登录页，而不是收到 403。这在体验上很奇怪（用户明明登录了却被要求再登录一次），也让「未登录」和「权限不足」两种情况变得难以区分。生产上通常设 raise_exception = True。

F-01clean_email 引用了未导入的 User，注册功能整体 500已实测 · 功能 + 安全
位置
Chapter05~07/bookmarks/account/forms.py
触发

影响
表单校验抛 NameError → 500；且邮箱唯一性检查从未真正生效
python
from django import forms
from django.contrib.auth import get_user_model      # 导入的是这个

from .models import Profile
# 注意：模块里没有 `User = get_user_model()`，也没有 from ... import User


class UserRegistrationForm(forms.ModelForm):
    class Meta:
        model = get_user_model()                     # 这里用对了
        fields = ['username', 'first_name', 'email']

    def clean_email(self):
        data = self.cleaned_data['email']
        if User.objects.filter(email=data).exists():  # <- User 从未被定义

实测 · 逐字照抄仓库的表单
form.is_valid() 抛出 NameError: name 'User' is not defined

影响：clean_email 是表单校验的一部分，任何一次注册提交都会走到这里。
      NameError 不是 ValidationError，Django 不会把它转成表单错误，
      它会一路冒到视图外面 —— 也就是说注册功能整体返回 500。
      同时那个「邮箱唯一性」检查从来没有真正生效过。

✗ 现状

class UserRegistrationForm(forms.ModelForm):
    def clean_email(self):
        data = self.cleaned_data['email']
        if User.objects.filter(email=data).exists():

✓ 补上模块级绑定

User = get_user_model()          # <- 补这一行

        data = self.cleaned_data['email']
        if User.objects.filter(email__iexact=data).exists():

顺带把 filter(email=...) 改成 email__iexact：邮箱的域名部分大小写不敏感，Alice@Example.com 和 alice@example.com 在实践中应当视为同一个地址。只做精确匹配的话，唯一性检查可以被大小写变体绕过。

F-02拖拽排序端点既不要求登录，又豁免了 CSRF已实测 · 安全
位置
Chapter13~17/educa/courses/views.py · ModuleOrderView / ContentOrderView
触发
任意第三方页面向该端点发起跨站 POST
影响
已登录讲师的课程模块顺序可被任意站点篡改；匿名 POST 触发 500
实测 · 两个缺口分别验证
=== A) 匿名用户直接 POST（没有 LoginRequiredMixin）===
  HTTP 状态 : 500
  数据有变吗: 未变
  -> 没有 LoginRequiredMixin，请求直接进到了 post() 方法体；
     course__owner=AnonymousUser 让 ORM 抛 TypeError（AnonymousUser 没有 pk），
     于是返回 500 而不是 403/302。数据确实没被改，但这是「崩掉了」而非「被拒绝」。

=== B) 已登录用户跨站 POST（CsrfExemptMixin 的真正代价）===
  不带 CSRF token 的 POST -> 200  {"saved": "OK"}
  数据被改了吗: 是，顺序已被修改

  对照：同一个视图去掉 CsrfExemptMixin 之后
  不带 CSRF token 的 POST -> 403   <- 被 CSRF 中间件拦住
  数据被改了吗: 未变

为什么书里要加 CsrfExemptMixin？ 因为前端用 html5sortable 拖拽后发的是原始 fetch POST，作者为了省去传 CSRF token 的步骤直接豁免了校验。但正确做法是把 token 带上，而不是关掉检查——同一个项目的 base.html 里其实已经有读取 CSRF token 的代码了。

✗ 现状：关掉检查
class ModuleOrderView(
        CsrfExemptMixin,
        JsonRequestResponseMixin,
        View):
    def post(self, request):
        for id, order in self.request_json.items():
            Module.objects.filter(
                id=id, course__owner=request.user
            ).update(order=order)
        return self.render_json_response({'saved': 'OK'})
✓ 补齐登录检查，保留 CSRF
class ModuleOrderView(
        LoginRequiredMixin,
        PermissionRequiredMixin,
        JsonRequestResponseMixin,
        View):
    permission_required = 'courses.change_course'

    def post(self, request):
        for id, order in self.request_json.items():
            Module.objects.filter(
                id=id, course__owner=request.user
            ).update(order=order)
        return self.render_json_response({'saved': 'OK'})

F-03WebSocket 入口没有任何鉴权，匿名用户可进入任意课程聊天室已实测 · 安全
位置
Chapter16~17/educa/chat/consumers.py · ChatConsumer.connect()
触发
直接连接 ws://host/ws/chat/room/<任意 course_id>/
影响
未报名者与匿名者可读取付费课程聊天内容，并向房间广播消息
实测 · 真实 WebsocketCommunicator 连接
=== HTTP 侧（chat/views.py）的行为，作为对照 ===
  @login_required + request.user.courses_joined.get(id=course_id)
  未登录 -> 重定向到登录页 ；已登录但未报名 -> 403 Forbidden

=== WebSocket 侧（chat/consumers.py connect()）的实际行为 ===
  匿名用户（完全未登录）                连接是否被接受: True
  已登录但未报名该课程                 连接是否被接受: True

=== 未报名者能不能收到房间里的广播 ===
  匿名连接收到了: '我不是这门课的学生'
  -> 未报名者发的消息，匿名者也完整收到了：房间对任何人开放读写。

asgi.py 里的 AllowedHostsOriginValidator 容易让人误以为已经有防护了——但它只校验 Origin 请求头，防的是「从别的站点发起的 WebSocket 连接」（跨站 WebSocket 劫持），完全不管「连接的是不是正确的用户」。

✗ 现状：无条件 accept
async def connect(self):
    self.user = self.scope['user']
    self.id = self.scope['url_route']['kwargs']['course_id']
    self.room_group_name = f'chat_{self.id}'
    await self.channel_layer.group_add(
        self.room_group_name, self.channel_name)
    await self.accept()
✓ 先鉴权再 accept
from channels.db import database_sync_to_async

@database_sync_to_async
def _is_enrolled(user, course_id):
    if not user.is_authenticated:
        return False
    return user.courses_joined.filter(id=course_id).exists()

async def connect(self):
    self.user = self.scope['user']
    self.id = self.scope['url_route']['kwargs']['course_id']
    if not await _is_enrolled(self.user, self.id):
        await self.close(code=4003)      # 拒绝，不要 accept
        return
    self.room_group_name = f'chat_{self.id}'
    await self.channel_layer.group_add(
        self.room_group_name, self.channel_name)
    await self.accept()

顺序也很重要：必须在 group_add 和 accept() 之前拒绝。如果先 accept() 再检查，连接已经建立、也已经加入了广播组，在你关闭它之前就可能收到消息。

另外 receive() 里是先广播再落库的：group_send 成功但 persist_message 失败时，所有人都看到了一条并未保存的消息。这个顺序问题在异步任务指南第 2.4 节讨论过。

F-04自定义认证后端不检查 is_active，停用账号可通过 authenticate()已实测 · 安全
位置
Chapter05~07/bookmarks/account/authentication.py
触发
被停用的用户用邮箱作为凭据
影响
任何直接调用 authenticate() 并信任返回值的代码都会放行停用账号
实测 · 同一个 is_active=False 的账号
用「用户名」认证 (ModelBackend)     -> None
用「邮箱」认证   (EmailAuthBackend) -> alice   <- 停用账号被放行

但走 Django 内置 LoginView 时表单还会拦一道：
  AuthenticationForm.is_valid() -> False
  错误信息 -> This account is inactive.

要如实说明缓解因素：仓库当前的 URL 配置用的是 Django 内置 LoginView，它的 AuthenticationForm.confirm_login_allowed() 会额外拦下停用账号，所以登录入口这条路是安全的。真正的风险在于：任何直接调用 authenticate() 并信任返回值的代码都会放行——仓库里那个被注释掉的 user_login 视图就额外写了 if user.is_active 来兜底，说明作者是知道这件事的。但依赖「每个调用点都记得自己检查」是脆弱的，正确的位置是后端内部。

F-05自定义认证后端缺少计时拉平，形成 1700 倍的用户枚举侧信道已实测 · 安全
位置
Chapter05~07/bookmarks/account/authentication.py
触发
攻击者拿一份邮箱清单逐个尝试登录，只观察响应时间
影响
可精确判定任意邮箱是否在本站注册过，无需猜对任何密码
实测 · 每组 40 次取中位数
=== EmailAuthBackend（仓库写法）===
  邮箱存在、密码错误 :  297.53 ms
  邮箱不存在         :    0.17 ms
  比值               : 1700.9×

=== Django 内置 ModelBackend（对照）===
  用户名存在、密码错误 :  296.98 ms
  用户名不存在         :  297.91 ms
  比值                 :    1.00×

=== 修复后（补上 set_password 拉平）===
  比值                 :    0.99×

Django 内置后端为什么慢？因为它是故意的。 源码里写得很清楚：

python
# django/contrib/auth/backends.py（5.2 源码）
try:
    user = UserModel._default_manager.get_by_natural_key(username)
except UserModel.DoesNotExist:
    # Run the default password hasher once to reduce the timing
    # difference between an existing and a nonexistent user (#20760).
    UserModel().set_password(password)
else:
    if user.check_password(password) and self.user_can_authenticate(user):
        return user

修复：继承 ModelBackend，而不是从零实现。 这样 user_can_authenticate()、权限相关方法（get_all_permissions、has_perm 等）也都自动带上了，一并解决 F-04：

✗ 现状：从零实现
class EmailAuthBackend:
    def authenticate(self, request, username=None, password=None):
        try:
            user = User.objects.get(email=username)
            if user.check_password(password):
                return user
            return None
        except (User.DoesNotExist,
                User.MultipleObjectsReturned):
            return None
✓ 继承 ModelBackend
class EmailAuthBackend(ModelBackend):
    def authenticate(self, request, username=None,
                     password=None, **kwargs):
        if username is None or password is None:
            return None
        try:
            user = User.objects.get(email__iexact=username)
        except User.DoesNotExist:
            User().set_password(password)   # 拉平耗时
            return None
        except User.MultipleObjectsReturned:
            return None
        if (user.check_password(password)
                and self.user_can_authenticate(user)):
            return user
        return None

顺带说明为什么加 **kwargs：Django 的 authenticate() 会检查每个后端的函数签名，签名不匹配的后端会被静默跳过。原实现的签名是固定的三个参数，社交登录传来的其他 kwargs 会让它被跳过——这恰好是期望行为，但依赖签名不匹配来实现「跳过」是隐晦的，显式接受 **kwargs 更清楚。

三个问题叠在一起：Django 默认 User.email 没有唯一约束；表单层的唯一性检查因 F-01 从未生效；而后端把 MultipleObjectsReturned 和「用户不存在」用同一个 except 吞掉了。

真正的修复是在数据库层加约束——表单校验挡不住并发提交，也挡不住 admin、管理命令、数据导入这些路径：

python
# 自定义 User 模型时直接声明（新项目的正确起点）
class User(AbstractUser):
    email = models.EmailField('email address', unique=True)

# 已经用了默认 User、不便迁移时，可以加约束
class Meta:
    constraints = [
        models.UniqueConstraint(
            Lower('email'), name='uniq_user_email_ci',
            condition=~Q(email=''),      # 允许多个空邮箱
        )
    ]

Two Scoops of Django 里最常被引用的一条建议就是「项目一开始就用自定义 User 模型」，哪怕它一开始只是 class User(AbstractUser): pass。原因正是这类需求——邮箱唯一、加字段、改认证字段——事后迁移默认 User 模型的代价极高。本仓库用的是默认 auth.User，还靠 add_to_class() 往上动态挂字段（Chapter07 的关注关系），这在教学上很直观，但不是可以照搬到生产的做法。

四、Django 的安全默认值，以及本仓库动了哪些

把前面七条放在一起看，有一个很清楚的规律：本仓库的安全问题，几乎全部出现在「主动关掉或绕过 Django 默认保护」的地方。

Django 的默认保护默认状态本仓库的情况
CSRF 校验（中间件）开启被 CsrfExemptMixin 在两个端点上关掉（F-02）
ModelBackend 的 is_active 检查开启自定义后端从零实现，绕过了（F-04）
ModelBackend 的计时拉平开启同上，绕过了（F-05）

这条规律本身就是最实用的一条经验：当你要写 csrf_exempt、要自己实现认证后端、要绕开 LoginRequiredMixin 时，就是在拆掉框架替你装好的护栏。这些时刻值得停下来问一句「我是不是在用一个更麻烦的方式解决一个框架已经解决了的问题」——F-02 的 CSRF 豁免就是典型：正确做法是把 token 带上，而不是关掉校验。

4.1 生产环境该补的几项

python
# 传输与 Cookie（本仓库 educa 的 prod.py 已有前三项）
SECURE_SSL_REDIRECT = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True

# 这几项本仓库没有
SECURE_HSTS_SECONDS = 31536000          # 先用小值验证，确认无误再加到一年
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True
SECURE_REFERRER_POLICY = 'same-origin'
SECURE_CONTENT_TYPE_NOSNIFF = True      # 默认已是 True
X_FRAME_OPTIONS = 'DENY'                # 默认 'DENY'

# 会话
SESSION_COOKIE_AGE = 60 * 60 * 24 * 14
SESSION_EXPIRE_AT_BROWSER_CLOSE = False

# 密码哈希：把 Argon2 放最前，旧密码会在下次登录时自动升级
PASSWORD_HASHERS = [
    'django.contrib.auth.hashers.Argon2PasswordHasher',
    'django.contrib.auth.hashers.PBKDF2PasswordHasher',
    'django.contrib.auth.hashers.PBKDF2SHA1PasswordHasher',
    'django.contrib.auth.hashers.BCryptSHA256PasswordHasher',
]

PASSWORD_HASHERS 列表的第一项是「新密码用什么算法」，其余是「还能验证哪些历史算法」。用户下次成功登录时，Django 会自动把旧哈希重新算成第一项的算法——所以换哈希算法不需要强制所有人改密码。启用 Argon2 需要 pip install django[argon2]。

4.2 Django 不提供、但生产必须有的

  • 登录失败限流。Django 完全不内置。django-axes 是最常用的方案，能按 IP / 用户名限制失败次数并临时封锁。没有它，撞库攻击不受任何阻力——而本文的 F-05（用户枚举）恰好为撞库提供了精准的目标清单，两者叠加危害显著放大。
  • 二次验证（2FA）。django-otp / django-two-factor-auth。
  • 敏感操作的重新认证。改邮箱、改密码、删账号前要求再输一次密码。Django 的 PasswordChangeForm 做到了（要求 old_password），但改邮箱这类操作没有对应机制。本仓库的 UserEditForm 允许直接改邮箱而不需要验证当前密码——如果攻击者拿到了一个已登录的会话，就能把账号邮箱改成自己的，再走密码重置流程完成接管。
  • 会话审计与主动失效。「查看我的登录设备」「退出所有其他设备」这类功能需要自己实现。

五、上线前检查清单

  • 01新项目一开始就用自定义 User 模型，哪怕内容是空的。事后迁移的代价极高。见 F-06。
  • 02邮箱唯一性要落到数据库约束上，不能只靠表单校验——表单挡不住并发、admin、管理命令和数据导入。
  • 03自定义认证后端要继承 ModelBackend，不要从零实现。否则会漏掉 is_active 检查、计时拉平和一整套权限方法。见 F-04、F-05。
  • 04用户不存在时也要跑一遍密码哈希，把响应时间拉平。否则就是一个用户枚举接口。
  • 05装上登录失败限流（django-axes 等）。Django 不内置，而这是撞库的唯一阻力。
  • 06不要用 csrf_exempt 来省事。AJAX 端点应当把 CSRF token 放进 X-CSRFToken 头。真正需要豁免的只有外部回调（如 Stripe webhook），且必须用签名校验替代。见 F-02。
  • 07每新增一种入口类型就重新审一遍鉴权：AJAX 端点、WebSocket 消费者、管理命令、Webhook、定时任务——它们都不在标准视图的 mixin 惯例里。见 F-02、F-03。
  • 08WebSocket 要在 accept() 之前鉴权，先 accept 再检查等于已经把人放进了广播组。
  • 09模型级权限不等于对象级权限。「能改课程」和「能改这门课程」是两件事，必须叠加所有权过滤。
  • 10列表可见性靠 get_queryset()，不靠对象级权限。has_object_permission 对 list 动作完全不生效。
  • 11PermissionRequiredMixin 设 raise_exception = True，否则权限不足的已登录用户会被莫名其妙重定向到登录页。
  • 12登出必须用 POST 表单。Django 5.0 起 LogoutView 不再接受 GET。见 F-07。
  • 13敏感操作要求重新认证：改邮箱、改密码、删账号。否则一个被盗的会话就足以完成账号接管。
  • 14生产补齐 HSTS、Referrer-Policy、Cookie Secure，并跑一遍 python manage.py check --deploy。
  • 15把 PASSWORD_HASHERS 的第一项设为 Argon2，旧密码会在下次登录时自动升级，无需强制改密。
  • 16缓存不能绕过授权。给需要登录的视图加 cache_page 会让缓存在权限检查之前命中——这个坑在缓存指南 F-01 里有完整复现。

六、同样的认证与授权：Spring 与 Hono.js 怎么做

仍用本仓库的真实场景对比：「只有课程的拥有者才能编辑课程，只有报名的学生才能看内容」，以及支撑它的「认证方式与安全默认值」。

6.1 认证与授权的表达方式

Django 5.2

认证是后端链，授权靠在视图上叠加 mixin。默认是「没写检查就是公开」。

# 认证：后端链，依次尝试
AUTHENTICATION_BACKENDS = [
    'django.contrib.auth.backends.ModelBackend',
    'account.authentication.EmailAuthBackend',
]

# 授权：四种粒度，靠叠加
class CourseUpdateView(
        LoginRequiredMixin,          # ① 要登录
        PermissionRequiredMixin,     # ② 要有模型权限
        UpdateView):
    permission_required = 'courses.change_course'

    def get_queryset(self):          # ③ 只能改自己的
        return super().get_queryset().filter(
            owner=self.request.user)

# ④ 对象级（DRF）
class IsEnrolled(BasePermission):
    def has_object_permission(self, request, view, obj):
        return obj.students.filter(
            id=request.user.id).exists()
  • 四种授权粒度各自独立，需要开发者主动叠加
  • PermissionRequiredMixin 只到模型级；对象级要靠 queryset 过滤或 DRF 权限类
  • 默认放行：忘了加 mixin 的视图就是公开的——本文 F-02 正是如此

Spring Boot 3.x

Spring Security 的过滤器链集中声明整站规则，方法级注解再做细化。

// 认证：过滤器链，集中配置
@Bean
SecurityFilterChain chain(HttpSecurity http) throws Exception {
    return http
        .authorizeHttpRequests(a -> a
            .requestMatchers("/api/public/**").permitAll()
            .requestMatchers("/api/admin/**").hasRole("ADMIN")
            .anyRequest().authenticated())     // 默认拒绝
        .formLogin(Customizer.withDefaults())
        .build();
}

// 授权：方法级注解，SpEL 可调 Bean
@PreAuthorize("hasAuthority('COURSE_EDIT') and "
            + "@ownership.isOwner(#id, authentication)")
public Course update(Long id, CourseDto dto) { ... }

// 对象级：@PostAuthorize 在返回后校验
@PostAuthorize("returnObject.owner.username "
             + "== authentication.name")
public Course find(Long id) { ... }
  • .anyRequest().authenticated() 让「默认拒绝」成为一行配置
  • @PreAuthorize 的 SpEL 能直接调 Bean，把业务判断写成可复用组件
  • 路由规则集中在一处，可以整体审查，不必逐个视图翻

Hono.js

认证和授权都是普通中间件，执行顺序就是代码顺序，没有任何隐式行为。

// 认证与授权都是中间件，顺序即语义
import { jwt } from 'hono/jwt'

app.use('/api/*', jwt({ secret: env.JWT_SECRET }))

const requireEnrolled = createMiddleware(async (c, next) => {
  const { sub } = c.get('jwtPayload')
  const ok = await db.isEnrolled(c.req.param('id'), sub)
  if (!ok) return c.json({ error: 'forbidden' }, 403)
  await next()
})

app.get('/api/courses/:id/contents',
  requireEnrolled,          // 显式挂在这一条路由上
  handler)

// 没有「默认拒绝」——没挂中间件的路由就是公开的
  • 最容易读懂：先认证后鉴权一目了然
  • 没有默认拒绝，也没有集中式规则表，漏挂一条路由就是漏洞
  • 对象级授权没有抽象，每处自己查库

    'django.contrib.auth.hashers.Argon2PasswordHasher',

# 登录限流：Django 不内置，需 django-axes 等

Django 的安全默认值相当扎实：CSRF 中间件默认开启、会话 Cookie 默认 HttpOnly、密码默认 PBKDF2 加盐。本仓库的问题几乎都出在主动关掉或绕过这些默认值的地方（CsrfExemptMixin、自定义认证后端）。

缺的一块是登录限流——Django 不内置，撞库防护要靠 django-axes 这类第三方包。本仓库没有。

Spring Boot 3.x

// Spring Security 的默认拒绝是框架级的
.anyRequest().authenticated()

// CSRF 默认开启，且默认只豁免安全方法
.csrf(c -> c.csrfTokenRepository(
    CookieCsrfTokenRepository.withHttpOnlyFalse()))

// 会话固定攻击防护：默认开启
.sessionManagement(s -> s
    .sessionFixation().migrateSession()
    .maximumSessions(1))          // 同账号并发会话上限

// 密码哈希：默认 bcrypt，可切 Argon2
@Bean
PasswordEncoder encoder() {
    return PasswordEncoderFactories
        .createDelegatingPasswordEncoder();
}

// 登录限流：需 Bucket4j 或自己实现 AuthenticationFailureHandler

会话固定攻击防护、并发会话上限这类细节是框架内建的，Django 里要自己想着做（login() 会轮换 session key，但并发会话上限没有对应物）。

DelegatingPasswordEncoder 会在哈希串里存算法前缀，换算法时旧密码能平滑升级——Django 的 PASSWORD_HASHERS 列表也是同样思路。

Hono.js

// 什么默认都没有，安全项全是显式选择
import { csrf } from 'hono/csrf'
import { secureHeaders } from 'hono/secure-headers'

app.use(secureHeaders())     // CSP / HSTS / X-Frame-Options
app.use('/form/*', csrf())   // 只保护你点名的路由

// 会话通常不用 Cookie，用 JWT：
// 好处是无状态；代价是签发后无法直接吊销，
// 必须靠短有效期 + refresh token 轮换

// 密码哈希在边缘环境是个真问题：
// bcrypt/argon2 是原生模块，Workers 上跑不了，
// 通常改用 Web Crypto 的 PBKDF2，
// 或者干脆把认证外包给平台（Auth0 / Clerk）

边缘环境下密码哈希是个真实的工程约束：bcrypt / argon2 依赖原生模块，Workers 跑不了。这直接推动了「认证外包给平台」的做法。

什么都没有默认开启，意味着安全性完全取决于团队的自觉——没有框架帮你兜底，但也没有你以为开着、实际被某行代码关掉的情况。

三句话概括

  • Django 的安全默认值很扎实，但授权是「默认放行」的。CSRF 中间件默认开、会话 Cookie 默认 HttpOnly、密码默认加盐哈希——本仓库的所有缺口，几乎都出现在主动关掉或绕过这些默认值的地方：CsrfExemptMixin 关掉了 CSRF，自定义认证后端绕过了 ModelBackend 的两项保护，WebSocket 消费者完全走在 HTTP 的检查体系之外。而授权规则散落在各个视图的 mixin 上，导致「哪个视图漏了检查」这个问题很难通过通读代码回答。
  • Spring 最大的结构性优势是「默认拒绝 + 集中声明」。.anyRequest().authenticated() 一行就把「忘了加保护」这类错误从「静默漏洞」变成了「访问被拒」，而整站规则集中在一个 Bean 里意味着安全审查有一个明确的入口。本文的 F-02（拖拽排序端点没有任何登录检查）在 Spring 的默认拒绝模型下不会发生。
  • Hono 什么都不给，但也什么都不藏。认证和授权就是按顺序执行的中间件，读代码就能确定一条路由受哪些保护，不存在「以为开着、其实被某行代码关掉了」的情况。代价是没有任何兜底：漏挂一条路由就是一个公开端点，而且边缘环境连密码哈希都受限，这也是「认证外包给平台」在这个生态里格外流行的原因。
